# I18N.md — i18n scaffold + first locales (T110)

> Companion to `CLAUDE.md` §6/§7 and `docs/PRODUCT_SPEC.md` §5. This document
> is the single source of truth for how the i18n layer works, what is (and
> is not) translated today, and what must happen before any non-English
> locale is ever served to a real user.

## 1. What ships today

**Nothing ships in a new language.** The app is English-only in production.
This task adds a complete, tested *pipeline* (locale registry, typed
overrides, resolver, fallback, coverage lint, safety lint, served-locale
gate) plus three machine-translated dictionaries — but every non-`en` locale
is `reviewed: false`, and `resolveServedLocale` mechanically forces any
unreviewed locale back to `en` at serve time. A user in Madrid, São Paulo, or
Mumbai sees English today.

## 2. Locale registry

| id | direction | reviewed | pseudo | source |
|---|---|---|---|---|
| `en` | ltr | **true** | false | authored |
| `es` | ltr | false | false | machine |
| `pt-BR` | ltr | false | false | machine |
| `hi` | ltr | false | false | machine |
| `ar` | rtl | false | false | machine (no dictionary shipped) |
| `en-XA` | ltr | false | **true** | generated (dev/CI only) |
| `ar-XB` | rtl | false | **true** | generated (dev/CI only) |

`en-XA`/`ar-XB` are the Android-standard pseudolocale identifiers (accented
expansion and RTL-bidi respectively). They are generated at runtime directly
from the English strings tree (`pseudoTree`) — never authored, never
selectable from real device/header negotiation, and exercised only via the
`EXPO_PUBLIC_I18N_LOCALE` / `NEXT_PUBLIC_I18N_LOCALE` dev/CI override.

`ar` is registered for text-direction/negotiation purposes only and ships
**no dictionary** in this task (see §6). Authoring fake Arabic — especially
Arabic safety copy nobody in this loop can read — would be dishonest and
unreviewable; RTL smoke instead uses the `ar-XB` RTL pseudolocale, which
exercises the identical direction code path without inventing any Arabic
copy.

## 3. Architecture: identity fast-path for `en`

`strings` (mobile: `apps/mobile/src/strings.ts`; web: `apps/web/src/strings.ts`)
stays exactly what it was before this task — a module-scope constant with
the same shape and the same literal types:

```
enStrings  (the existing literal tree, renamed in place)
     |
     v
resolveActiveStrings(enStrings)   -> "en": returns enStrings BY IDENTITY
     |                                else: deep-merges the locale override
     v
export const strings              -> type is `typeof enStrings`
```

While `en` is the only served locale, `strings === enStrings` (reference
identity). This is what keeps every existing import site, snapshot, and
safety-lint pin structurally untouched by this task — no provider, no hook,
no prop drilling. Locale changes require an app reload on mobile (an honest
RN semantic, since `I18nManager.forceRTL` requires one anyway).

Shared core: `packages/config/src/i18n/{locales,resolve,pseudo}.ts`. Per-app
runtime: `apps/{mobile,web}/src/i18n/runtime.ts` (+ `locale-registry.ts` +
`locales/{es,pt-BR,hi}.ts`).

## 4. Zero new dependencies

The resolver, pseudolocale generator, and locale registry are hand-rolled
(~250 lines total) rather than i18next/react-i18next/react-intl. Adopting
one of those would require replacing the typed `as const` strings trees with
flat JSON catalogues, destroying literal types, function-valued
interpolators, and the T097 safety-lint tree-walking collector. We will need
real plural/gender/ICU semantics once human-reviewed translations exist for
languages with non-English plural rules (Hindi, Arabic) — tracked as a
follow-up in §8, not solved by this task.

## 5. Translated sections (pipeline coverage today)

Each machine locale (`es`, `pt-BR`, `hi`) translates **exactly** these
top-level sections, 100% of each:

- **Mobile:** `tabs`, `nav`, `home`, `switcher`, `care`, `addPet`
- **Web:** `globalError`

Every other top-level section stays English by construction —
`SAFETY_PINNED_PREFIXES` in each app's `locale-registry.ts` is the computed
complement of the translated-sections list, and a test in
`i18n-locale-coverage.test.ts` / `locale-coverage.spec.ts` asserts the two
can never silently drift.

**Web `footer` is deliberately NOT a translated section**, even though it
looked like ordinary chrome copy at first glance: `footer.notice` ("...
provides general guidance only and is not a substitute for veterinary
care") is itself a §5 safety-disclaimer sentence, and the whole `footer`
section moved to the safety-pinned complement rather than carrying a
narrower per-key carve-out (a corrected plan defect — the original plan
named `footer` as translatable, which contradicted the plan's own "no §5/§7
surface is ever machine-translated" rule; see the review note below).

This is a deliberately **bounded** body of machine translation: whole-tree
translation would mean ~600 mobile leaves × 3 locales of unreviewable LLM
output (including legal paragraphs and §5/§7 safety copy) for locales that
will never be served unreviewed — a large hallucination surface with zero
shipped value. Extending coverage later is additive: add keys to a
dictionary file and grow `TRANSLATED_SECTIONS`.

## 6. Safety copy is never machine-translated

**No §5/§7 safety surface is ever machine-translated.** This is the load
bearing safety rule of this task. Concretely, on mobile the safety-pinned
top-level sections include `check.` (the entire triage result/emergency
surface), `chat.` (incl. the safe-fallback), `medForm.` (medication tracker
copy), and every other section outside `TRANSLATED_SECTIONS`; on web,
`disclaimer`, `legal.`, `landing.`, `foodPage.`, `layout.`, and `footer.`
(incl. the vet-care-substitute sentence `footer.notice` — see §5 above).

`i18n-safety-pins.test.ts` (mobile) and `locale-coverage.spec.ts` (web) each
run TWO independent nets over every machine dictionary:

1. **Byte-identity pins** — disclaimer, emergency copy, the fallback
   notice, the safe-fallback chat copy, medication-form copy, both
   kill-switch bodies (mobile), and `disclaimer`/`legal`/`landing`/
   `foodPage`/`layout`/`footer` (web) are asserted identical to the English
   source after merging.
2. **A digit+unit dose-pattern scan and a diagnosis-lexeme scan
   (`diagnóstico`, `diagnosticar`, `निदान`)**, applied to EVERY leaf of
   EVERY machine dictionary. Both scans **invoke function leaves** (dummy
   args built from `fn.length`, the same idiom `strings-detector-lint.test.ts`
   uses) and scan the returned string, rather than skipping them — a
   dictionary's one interpolated leaf (mobile: `addPet.common.stepOf`) is
   not a blind spot. Each scan carries its own positive control (a planted
   dose/diagnosis string) AND a function-leaf non-vacuity control (a planted
   string reachable only by invoking a fixture function leaf), so a
   regression that silently stopped invoking function leaves again would
   itself fail a test.

The reason this can't be relaxed by translating more carefully: the T038
safety detector (`scanUnsafeText`) is **English-pattern-only**. It cannot
validate Spanish/Portuguese/Hindi dosing or diagnosis language, so serving a
machine-translated safety string would be exactly the failure
`docs/PRODUCT_SPEC.md §5` exists to prevent.

## 7. Date / number / unit localization audit

**Wired in this task** (`apps/mobile/src/i18n/format.ts`):

- `formatEntryDate(iso, locale)` — `en` stays pinned to the app's existing
  ISO `YYYY-MM-DD` convention (changing English date presentation is a
  product decision, not an i18n-scaffold decision, and would churn frozen
  snapshots); every other locale formats via `Intl.DateTimeFormat` with a
  **fixed UTC time zone**, so output is deterministic in CI regardless of
  the host's `TZ`. Wired into `apps/mobile/src/checks/check-history.ts`'s
  `formatCheckDate`.
- `formatDecimal(value, locale, fractionDigits?)` — locale-correct decimal
  separator via `Intl.NumberFormat`, grouping disabled. Wired into
  `apps/mobile/src/weight/weight-units.ts`'s `formatWeight` (optional
  `locale` parameter, default `"en"`). The app's weight domain
  (`WEIGHT_MIN_GRAMS`..`WEIGHT_MAX_GRAMS` = 1–200,000 g = 0.001–200.0 kg /
  0.002–440.9 lb) never produces a value large enough to reach a grouping
  separator, so this is byte-identical to the pre-T110 `toFixed(1)` output
  for `en` across the whole legal domain (mechanised by
  `i18n-format.test.ts`).

**Audited, NOT wired (out of card scope — recorded here per the card's
"audit" clause, and as a founder/R2 follow-up):**

- `app/care-plan/[petId].tsx:35` — a date *input* value the user types,
  not a display string; localizing a text-input placeholder is a UI-input
  decision, not a display-formatting one.
- Every `Intl.DateTimeFormat().resolvedOptions().timeZone` call site
  (`app/settings/notifications.tsx:24`, `app/care-plan/[petId].tsx:18`,
  `app/reminders/edit.tsx:20`, `src/components/medication-course-form.tsx:21`)
  — these resolve the device's IANA time zone identifier, not a
  locale-formatted date/number, so `formatEntryDate`/`formatDecimal` do not
  apply.
- Raw-number interpolations inside pluralized **English** templates
  (`agenda.queuedBanner`, `activity.today.*`, `intake.maxSelectionsHint`) —
  correct pluralization for `es`/`pt-BR` (two-form, same as English) is
  low-risk, but `hi`/`ar` do not use English-style two-form plurals at all.
  Fixing this properly needs a plural-rules engine (ICU `MessageFormat` or
  equivalent), which is explicitly out of this card's scope (§8).
- Web's hardcoded USD price strings (pricing/marketing copy) — regional
  pricing is a commercial/legal decision tracked separately from this i18n
  scaffold task.

## 8. RTL follow-up (before `ar` can ever be served)

T110 delivers the RTL **smoke test** (crash-free render + correct copy
resolution under an RTL-tagged pseudolocale), not RTL **layout mirroring**.
It deliberately never calls `I18nManager.forceRTL` (that requires an app
reload and would change layout for real users of a locale we do not serve).
Before `ar` can ever be flipped to `reviewed: true` and actually served, the
following must land:

1. **Physical-direction NativeWind class migration.** The app uses
   physical-direction utility classes throughout (`ml-*`, `mr-*`, `pl-*`,
   `pr-*`, `text-left`, `text-right`, `flex-row`) rather than logical
   properties. These must be audited and migrated to logical/RTL-aware
   equivalents (or conditionally flipped) before mirroring is safe.
2. **`I18nManager.forceRTL` + app-reload flow.** RN requires a full JS
   reload to apply a direction change; this needs its own UX (a
   confirmation + restart prompt), which does not exist today.
3. Re-running the full a11y/visual sweep once mirroring lands — pixel
   layout under RTL is not proven by anything in this task's test suite
   (jest renders no native layout).

## 9. Human-review pipeline (required before flipping any `reviewed: true`)

1. A **native-speaker human translator** reviews that locale's dictionary
   end to end.
2. Because our guidance is health-adjacent, a **veterinarian (or
   clinically-qualified reviewer) fluent in the target language** signs off
   on every safety string — which are currently **not translated at all**
   and must be translated *by a human first*, since machine translation of
   safety copy is refused by design (§6).
3. The T038 safety detector works only in English. Serving a locale means
   either commissioning language-specific detector patterns or explicitly
   accepting that the automated §7 net does not cover that locale — a real,
   recurring cost per language that should be budgeted for.
4. Only then flip `reviewed: true` in `packages/config/src/i18n/locales.ts`,
   in its own task with its own §7 review.

## 10. Known follow-ups (not solved by this task)

- **Per-request locale negotiation on web.** Today `getActiveLocale()` is
  resolved once per Node process, not per request — fine while English-only,
  but blocking for ever serving multiple locales on the marketing site (SSR
  must not leak one visitor's locale to another). `negotiateLocale` /
  `parseAcceptLanguage` ship pure and tested; wiring them into
  middleware/SSR is the future fix, and it is a call-site change, not a
  redesign, since `getStrings(locale)` already takes an explicit locale.
- **A plural-rules engine.** Hindi and Arabic do not use English-style
  two-form plurals; our hand-rolled `n === 1 ? … : …` templates are
  incorrect for them the moment real translations land.
- **No language switcher UI, no persisted locale override.** Offering a
  picker while only English is served would be a broken promise.

## 11. Running a pseudo-locale build (dev/CI)

Set the override env var and reload:

```
# mobile (Expo)
EXPO_PUBLIC_I18N_LOCALE=en-XA pnpm --filter mobile start   # accented pseudolocale
EXPO_PUBLIC_I18N_LOCALE=ar-XB pnpm --filter mobile start   # RTL-bidi pseudolocale

# web (Next.js)
NEXT_PUBLIC_I18N_LOCALE=en-XA pnpm --filter web dev
```

The override is honored only when `NODE_ENV` is EXACTLY `"development"` or
`"test"` (an **allowlist**, not a denylist of `!== "production"` — a safety
gate must fail closed on an unrecognized or missing `NODE_ENV`, not open;
see the T110 review's F3 finding). It is ignored in production builds AND
in any environment that never set `NODE_ENV` at all (a bare `node` process,
a custom server entry, a script), so this can never leak to a real user.
See `.env.example` for the pinned comment on both variables.
