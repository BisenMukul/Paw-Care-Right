## 2. BLOCKING findings

### F1 (mandatory-FAIL: false claim about what is sent + a recipient missing from the inventory) — the Expo push body carries user-generated `Reminder.title`

`docs/store-privacy.md:30` (§2, Reminders row) states:

> `Shared? … No (processor) — recipients: none`

This is false. When exactly one reminder is due, the push body is built as
`` `Care reminder: ${singleTitle}` `` (`apps/api/src/workers/push-sender.service.ts:37-38`), where
`singleTitle = enabledGroup[0]?.reminder.title` (`push-sender.service.ts:196`) is the **user's own
free-text reminder title**, and that string is sent to the Expo push service as
`body:` on the outgoing message (`push-sender.service.ts:209-215`), which then transits
APNs/FCM. The doc itself classifies "reminder titles/med-as-entered fields" as
**User Content → Other User Content** (`store-privacy.md:94`), so this is user content leaving to a
third party.

§3's Expo push paragraph (`store-privacy.md:82`) says only "the reminder payload needed to render a
push notification (title/body — no symptom-check content)" — that phrasing does not disclose that
`body` is verbatim user-typed text, and a reader filling in the store forms from §2 would answer
"reminder data: shared with no one". Consequences that flow from the error:
- §5 Play row `App activity → Other user-generated content | Shared: No` (`store-privacy.md:125`) is wrong for the push path;
- neither Expo, APNs nor FCM appears anywhere as a recipient of *content* (only of the token);
- this is the same class of claim the card's acceptance criterion exists to guarantee.

Required (doc-only, no code change): correct the §2 Reminders row's recipient/shared cells; expand
§3 "Expo push" to state that the notification body embeds the user's reminder title verbatim (and
that Expo relays via APNs/FCM); reconcile the §4/§5 User-Content rows accordingly. If a
content-free push body is considered desirable, that is a separate card — record it in §8, do not
build it here.
