## 6. Findings

### F1 — MEDIUM (process, non-blocking). `pnpm --filter @pawcareright/web test` bypasses turbo and can run the build-output specs against a **stale** `.next`.
The plan's self-verification section states *"`pnpm --filter @pawcareright/web test` (turbo chains the
build)"* (`T086.plan.md:522-523`). **This is false.** `pnpm --filter <pkg> <script>` runs the package's own
script (`apps/web/package.json` → `"test": "jest"`) directly; only the **root** `pnpm test`
(`turbo run test`) honours `apps/web/turbo.json:6`'s `"test": { "dependsOn": ["^build", "build"] }`.

Discovered empirically: M3 and M4 — the two mutations whose *only* killers are built-HTML assertions —
initially **SURVIVED** under `pnpm --filter … test`. Re-run with an explicit
`pnpm --filter @pawcareright/web build` first, both were killed cleanly (rows M3/M4 above; the M3 run also
confirms `class="sr-only"` reached `privacy.html` before jest ran).

Impact assessment:
- **The shipped gate is sound.** Root `pnpm test` routes through turbo and rebuilds, so DoD/CI verification
  of AC1/AC2/AC3 is trustworthy — I confirmed this on a wiped `.next`.
- **No executor proof is invalidated.** Its subset was M1, M2, M5, M7, M8; each is *also* killed by a
  model-level or rendered-markup assertion that needs no build (M1/M2 by `legal-content.spec.ts:58` and
  `:188`, M8 by `render.spec.tsx:107`). The two build-output-only mutations were not in its subset — I ran
  them, and they pass.
- **Residual risk** is future-facing: anyone iterating with the filtered command can see green
  build-output specs against an artefact that no longer matches the source.

Recommendation (backlog, not a T086 blocker): make freshness self-evident rather than conventional —
e.g. have `build-output.spec.ts` assert `prerender-manifest.json`'s mtime is newer than the newest
`src/**`/`app/**` source mtime (fail loudly with "run the build"), or change `apps/web`'s `test` script to
`turbo run build --filter=@pawcareright/web && jest`. Route via T095 (CI) or the next web card.

### F2 — LOW. The `render.spec.tsx` positive control no longer mirrors the production vet-equivalence regex.
Production uses `\bprescribe\b` (`render.spec.tsx:76`); the positive control at `:196` still uses the
bare `prescribe` alternation. The control still proves liveness (the planted string also trips
`replaces? your vet`), but it no longer byte-matches the pattern it is controlling for. My **EXTRA-1**
proof closes the gap empirically for now. Suggest syncing the two literals in a future touch of this file.

### F3 — LOW. `links.spec.ts`'s anchor extractor only matches anchors with plain-text children.
`extractAnchors` uses `/<a\s([^>]*)>([^<]*)<\/a>/g` (`links.spec.ts:25`), so an anchor wrapping an element
(e.g. a future `<a><img/></a>` store badge) would be silently skipped by the allowlist and non-empty-text
assertions. Not a defect today — every anchor on all three pages is plain text, and the independent
store-domain string scan (`links.spec.ts:168`) provides defence in depth. Worth widening if any nested
anchor is ever introduced.

### F4 — LOW (C3 legal-review item). Two privacy claims are true-but-untested in this repo.
(a) *"EXIF … is stripped from your images before upload, so it is never sent to us or to our AI
providers"* (`strings.ts:172`). The **server-side** half is proven by tests; the **"before upload"** half

hand-off explicitly lists these two sentences for counsel.

## 7. Adjudication of the executor's four declared deviations

1. **`strings.reviewNotice` rewired to derive from `LEGAL_REVIEW_MARKER` — ACCEPTED as a correctness fix,
   not scope creep.** Both files were already on the plan's file list, and the change is what makes
   plan-row M2 meaningful: with the token hardcoded in `strings.ts`, renaming the constant would have
   changed no rendered byte, so the built-HTML `LEGAL-REVIEW` grep and `legal-content.spec.ts:188` would
   both have stayed green — a textbook vacuous mutation. Self-reporting it was the right call. Two minor
   notes: it introduces a `strings.ts → legal/legal-document.ts` import, a mild inversion of D8's
   "copy in strings, structure in legal/*" layering (acceptable — D1 designates that constant canonical),
   and I verified there is **no import cycle** (`legal-document.ts` imports nothing).
2. **`links.spec.ts` uses `createElement` instead of JSX — ACCEPTED.** The plan's file list specifies
   `.ts`; using `createElement` keeps the file faithful to the list instead of silently renaming it to
   `.tsx`. `renderToStaticMarkup` output is identical either way, and the choice is documented in-file
   (`links.spec.ts:43-44`). Correct instinct: obey the plan, document the consequence.
3. **`\bprescribe\b` word boundary — ACCEPTED and independently verified.** A bare substring would
   false-positive on the *sanctioned* §7.2 clause "records what a veterinarian has already **prescribed**"
   — which `legal-content.spec.ts:156-161` requires verbatim — making the copy unshippable. I proved the
   boundary still catches real violations: **EXTRA-1** planted "We prescribe the right medicine for them."
   and the scanner fired (1 test failed, restore sha1 `58ba1c98` verified). See F2 for the residual
   positive-control mismatch.
4. **Three privacy sentences reworded to avoid compliant-context `diagnos*` — ACCEPTED.** The
   substitutions are "crash reports" (`strings.ts:158`), "error-reporting providers to identify and fix
   crashes" (`:186`), and "described … as guidance rather than a determination of what is wrong with your
   pet" (`:172`). All three remain accurate descriptions of what the product does, and the third is
   arguably *more* §7-sound than the phrasing it replaced — it restates the guidance-not-diagnosis framing
   in plain language. The plan's literal no-`diagnos*`-byte rule is stricter than §7.1 requires; erring
   strict on a public legal page is the right direction, and it keeps the AC-critical scanner a simple,
   unarguable substring test rather than a context-sensitive one.
