## 3. Event-name integrity (core risk) — PASS

The registry (`packages/analytics/src/events.ts:16-33`) declares exactly three events:
`first_check_completed`, `paywall_view`, `trial_start`; `AnalyticsEventName = keyof
AnalyticsEventMap`.

Every event referenced by a payload builder is one of those three, verified three ways:

1. **By type.** `TrendsSeriesNode.event`, `FunnelStepNode.event` and `RetentionEntityNode.event`
   are all declared `AnalyticsEventName` (`posthog-insights.ts:36, 54, 65`).
2. **By source-text re-parse.** `posthog-insights.spec.ts:90-112` reads `../events.ts` from
   disk, parses the `AnalyticsEventMap` body, asserts a non-vacuity floor of ≥3 declared names,
   then asserts every `"event":"…"` in every serialised insight is in that set. This defends
   against `AnalyticsEventName` itself widening.
3. **By negative assertion.** `:114-121` asserts no `UNTRACKED_FUNNEL_GAPS[].missingEvent`
   string appears anywhere in the serialised payloads.

**Cast-escape hunt (requested).** I grepped every new file for `as `, `as unknown`, `@ts-`,
`: any`, `<any>`. There is **no `as AnalyticsEventName` anywhere**. The only casts are
(a) index-access narrowing in specs under `noUncheckedIndexedAccess` (`match[1] as string`) and
(b) `(await res.json()) as {…}` response shapes in the two CLIs — both legitimate.

**MP-A (my mutation proof) settles the exploitability question.** I injected
`{ kind: "EventsNode", event: "app_open" as AnalyticsEventName, order: 0 }` into
`buildPaywallFunnelInsight`:

- `pnpm --filter @bombaypetcompany/analytics typecheck` → **EXIT 0 (GREEN)**
- `pnpm lint --force --filter @bombaypetcompany/analytics` → **EXIT 0 (GREEN)**
- `pnpm --filter @bombaypetcompany/analytics test` → **EXIT 1, 3 tests RED**:
  - `builds the paywall funnel from paywall_view -> trial_start in that order`
  - `references only event names declared in AnalyticsEventMap`
  - `does not reference any untracked gap event`

So the compile-time guard alone *is* bypassable by a cast — but plan D2's second half (the
source-parse spec) catches it. Defence-in-depth is real, not decorative. Restore
sha1-verified OK. **No finding.**

**Doc allowlist narrowness (scrutiny item 9-4).** `ALLOWED_NON_EVENT_TOKENS =
["sessions_crashed", "pet_created"]` (`observability-doc.spec.ts:45`). `sessions_crashed` is a

## 7. Findings

### F1 — `as AnalyticsEventName` bypasses tsc but is caught by specs — INFO, no action
Established by MP-A: the cast compiles and lints clean, so plan D2's *compile-time* claim alone
is not airtight. However `posthog-insights.spec.ts`'s source-parse guard turns it RED. The
mitigation the plan promised is present and effective. Recorded so the loop does not
over-trust "an invented event name is a tsc error" as a standalone guarantee.

### F2 — PostHog/Sentry payload schema fidelity is unverified against a live API — MED (accepted, non-blocking)
Reading the payloads critically against the endpoints the scripts target:

- **(a)** PostHog saved insights normally carry `query` as an `InsightVizNode` wrapper
  (`{kind:"InsightVizNode", source:{kind:"TrendsQuery",…}}`). The builders post a bare
  `TrendsQuery`/`FunnelsQuery`/`RetentionQuery` (`posthog-insights.ts:106, 125, 145`). A saved
  insight may 400 or fail to render as a viz in the UI.
- **(b)** `retentionFilter.targetEntity`/`returningEntity` are emitted as
  `{kind:"EventsNode", event:"first_check_completed"}` (`:148-149`). PostHog's `RetentionEntity`
  conventionally keys the event by `id` (with `type`/`order`), not `event`. Most likely wrong
  field name of the four items here.
- **(c)** `FunnelStepNode.order` (`:128-129`) is not part of the node-based `FunnelsQuery`
  schema (step order is array position). Harmless extra field, but it is what
  `posthog-insights.spec.ts:66` asserts on, so the spec pins a field the API may ignore.
- **(d)** Sentry's metric alert-rule POST generally expects a `query` field (empty string is
  valid) and often `eventTypes`/`owner`; none are present (`sentry-alerts.ts:35-44`). A 400 on
  first real run is plausible.
- **(e)** The doc does **not** carry the R2 mitigation text the plan required — plan R2 says
  *"the doc states which API version the payloads target and what to do on a 400"*. No API
  version and no 400-remediation guidance appears in `docs/observability-dashboards.md`. The
  "paste the payload into PostHog's insight 'edit as JSON' panel" hint exists only in the source
  header (`posthog-insights.ts:24-26`), which the founder will not read. Doc §8 does document
  exit code 3 ("status code and a truncated response body"), which is partial cover.

**Severity rationale:** ops-only, zero user-facing and zero animal-safety consequence. The
failure mode is a founder running the command and getting a 4xx with the raw body printed and
exit 3 — fully recoverable, and the mandatory `--dry-run` step means the payload is reviewed
before any write. Plan R2 explicitly pre-authorized exactly this uncertainty and the checker was
asked to rate by consequence. **MED, non-blocking.** Recommend the follow-up card carry (e) as a
one-line doc addition.

### F3 — `reads exactly the documented env vars` overclaims; one-directional + substring-matched — LOW
`observability-scripts.spec.ts:65-82` asserts every `process.env.X` read appears **as a
substring** of the doc's env block, and never the converse (a documented var need not be read).
**MP-D proves the hole:** I made the posthog CLI read `process.env.POSTHOG_HOST` as a fallback
credential — the ingestion host that plan D8 exists specifically to keep separate — and all 72
tests stayed GREEN, because `POSTHOG_HOST` is mentioned in the §4 table's prose note. The test
name promises more than it delivers. Shipped behaviour is correct; the guard is weak.

### F4 — nothing pins *which* env vars are required — LOW
**MP-C:** I deleted the `SENTRY_ENVIRONMENT` requirement from
`provision-sentry-alerts.ts:63-65`. `pnpm --filter api typecheck` GREEN and all 72 analytics
tests GREEN — **no spec caught it**. The AC1-c spec only asserts the literals `process.exit(2)`
and `missing required env` exist *somewhere* in each source file
(`observability-scripts.spec.ts:84-89`). Mitigating context: the spec header (`:9-11`) is honest
that "the CLIs themselves are exercised as real keyless commands in the executor report, not by
this fast unit spec", and I reproduced those keyless runs myself (§5), confirming the shipped
required-var sets are correct. So this is an acknowledged-and-documented coverage limit, not a
misrepresentation — but the required-var set is unprotected against future regression.

### F5 — doc event-token allowlist is global, not scoped to the gaps section — LOW
Plan AC1-d specified *"any other event-shaped snake_case token appears **only inside the gaps
section**"*. The implementation (`observability-doc.spec.ts:88-95`) is a flat doc-wide
allowlist with no section scoping, so `pet_created` (or any gap event) could later be added to
§5 as a real insight step and the doc spec would stay green. Weaker than planned; the actual
payload-level guarantee is unaffected (§3).

### F6 — insight `description` prose is worded to avoid its own substring test — INFO, no action
`does not reference any untracked gap event` (`posthog-insights.spec.ts:114-121`) scans the
**whole serialised payload**, descriptions included. The descriptions consequently say
"app-open" not `app_open` (`posthog-insights.ts:144`), "the third conversion step" not
`trial_to_paid` (`:124`), "activation-entry event" not `signup_completed` (`:105`).
**My call: legitimate, not evasive.** The test's load-bearing purpose is that no untracked event
reaches a query step, and MP-A shows it fires on a genuine violation. The prose stays accurate,
and the doc names all three gap events explicitly in §3 where they belong. The alternative
(loosening the test to scan only `query`) would be strictly weaker.

### F7 — no pagination follow on the upsert list calls — LOW
`findExistingRule` (`provision-sentry-alerts.ts:87-92`) GETs `/alert-rules/` and matches within
the first page only; Sentry paginates via `Link` headers. On an org with many rules the by-name
match could miss and POST a duplicate. PostHog's `findExisting` (`:97-102`) is lower risk
because it is `?search=`-narrowed. Ops-only, founder-visible, trivially fixable.

### F8 — `DASHBOARD_NAME` hardcodes the display name rather than composing `APP_DISPLAY_NAME` — LOW
`posthog-insights.ts:29` hardcodes `"Bombay Pet Company — Activation & Retention"`, while
CLAUDE §1a says the display name should come from `APP_DISPLAY_NAME`
(`packages/config/src/constants.ts:1`). Mitigating: a PostHog ops dashboard title is not one of
§1a's enumerated user-facing surfaces (store listing, on-screen title, marketing/legal copy,
push sender, email); `@bombaypetcompany/config` is only a **devDependency** of
`packages/analytics`, so importing the constant at runtime would require a manifest +
lockfile change that plan §3 forbids; and there is existing precedent for hardcoding in
non-store contexts (`apps/api/src/chat/chat.service.ts:93`). Correct call given the constraints;
noted for the naming audit.

### F9 — `.env.example` ops block omits `SENTRY_ENVIRONMENT` — INFO, no defect
Doc §6 lists `SENTRY_ENVIRONMENT` as required-for-a-real-run and the CLI enforces it, but the
new ops block does not repeat it. It is already present at `.env.example:59` from T089, so
there is no actual gap. Noted only because the §6 table and the new block are not one-to-one.

**Scrutiny item 9-5 (required-vs-default env split) — judged correct.** Secrets and
identity-bearing values (`POSTHOG_PERSONAL_API_KEY`, `POSTHOG_PROJECT_ID`,
`SENTRY_AUTH_TOKEN`, `SENTRY_PROJECT`, `SENTRY_ENVIRONMENT`) are required with no default —
right, since a defaulted environment would silently scope an alert to the wrong stage. Only
non-secret hosts and the org slug default, and `SENTRY_ORG`'s default `bombaypetcompany`
matches CLAUDE §1a's technical identifier exactly.
