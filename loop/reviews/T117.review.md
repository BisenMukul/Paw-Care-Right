## 4. Pending-applied telemetry (D2) — semantics probe

The persistence semantics are correct: the record is written at **download** with `fromUpdateId = currentUpdateId`, and `ota_applied` fires on the **next launch** whose `readOtaInfo().updateId` differs from that value (`use-update-flow.ts:117-138` + `ota-telemetry.ts:computeAppliedEvent`). Two details I checked that the plan did not call out and that the executor got right:

- The applied-effect is declared **before** the cold-start cycle effect, so a download inside the *same* session cannot be mistaken for an apply; even if the order flipped, the `current === pending.fromUpdateId` guard blocks it.
- `clearPendingApplied()` runs only after `captureEvent`, and the signed-out branch returns *before* clearing — so a signed-out apply genuinely survives to the next signed-in launch (asserted on the wire).

Edge probes: double-fire on the same `updateId` is blocked twice over (clear + dedupe guard); a poisoned/non-JSON/negative-timestamp store reads back as absent; a >7d record is dropped; a backwards clock clamps `latencyMs` to 0; the boundary case (exactly `PENDING_MAX_AGE_MS`) is pinned as still valid. Fetch-then-crash-before-persist loses the event — accepted and disclosed in plan R5; the transport contract (`http-transport.ts:20-41`, "never throws synchronously", rejections swallowed) means `captureEvent` cannot realistically throw before the write. Non-vacuity is proven, not assumed (mutation B).

## 5. Endpoint (`/v1/meta/client-versions`) — security & privacy

- **Guard**: hash-then-`timingSafeEqual` (so unequal-length input never throws and length is not leaked), rejects missing/empty/array header, and — unlike `RcWebhookGuard` — rejects when `ADMIN_API_TOKEN` is empty, so an unconfigured deployment exposes nothing. Faithful mirror plus the correct extra. The empty-configured-token case is table-tested against all three header shapes.
- **Read-only**: no non-GET handler exists in `apps/api/src/meta/**` (I grepped the whole module), the service issues a single `SELECT`, and the e2e proves 404 on all four mutating verbs plus an unchanged row snapshot and device count across a GET.
- **Injection**: `Prisma.sql` tagged template with `${cutoff}` as a bound parameter; `days` is `@IsInt() @Min(1) @Max(90)` before it ever reaches arithmetic.
- **Index**: `@@index([lastSeenAt])` in the schema and `CREATE INDEX "Device_lastSeenAt_idx"` in migration `20260730102934_t117_device_client_version` — same migration as the columns, per CLAUDE §6.
- **Response privacy**: `{day, appVersion, updateId, deviceCount}` only — no user id, no push token, no device id.
- **Export/erasure (D1 completeness)**: both new columns are in the export mapping (`account-export.service.ts:272-276`) and in the `.strict()` `exportDeviceSchema`; `expoPushToken` is still never exported. `account-erasure-cascade-completeness.spec.ts` enumerates models, not columns, and PASSes. I verified `accountExportSchema` is parsed only when *building* a bundle (`account-export.service.ts:37`) and never against an already-stored S3 bundle, so making the new fields required-nullable cannot break the 7-day retained bundles.

**Finding 2 — LOW — the aggregate is a "last-seen-day bucketing", not the per-day census §7's wording could imply.**
Evidence: `apps/api/src/meta/client-versions.service.ts:38-48` filters `lastSeenAt >= cutoff` and groups by `date_trunc('day', "lastSeenAt")`, so each device appears in exactly **one** day bucket (its last-seen day), never in every day since. §7 says the endpoint "aggregates reported `{appVersion, updateId}` per day". Combined with F9's finding that `lastSeenAt` effectively only advances at (JIT) push registration, the series is coarse and lagging rather than a daily adoption curve. This is exactly plan D5 and it is disclosed in three places — the Swagger `@ApiOkResponse` description (`client-versions.controller.ts:37-40`), runbook §17's bolded **Limitation**, and the Zod module's doc comment — each naming PostHog `ota_applied` as the authoritative adoption curve. That is the honest posture the plan promised, so this is not a defect; it is the scope decision that still needs the founder's accept/reject (plan §9.4). Escalating it would mean building the per-launch re-report path the plan deliberately descoped from an M card.

**Finding 3 — LOW — the endpoint's only data source (the JIT reporter) has zero test coverage; nothing pins the request payload shape.**
Evidence: mutation C added `ownerEmail: "leaked@example.com"` to the `POST /v1/devices` body in `apps/mobile/src/push/use-push-registration.ts` and the **entire** mobile suite stayed green (201 suites / 1750 tests) with typecheck also green. `grep -rl "usePushRegistration"` finds no test file that exercises the hook, and no mobile test references `/v1/devices` at all. Two consequences: (a) if a future refactor drops `appVersion: getAppVersion()`, `/v1/meta/client-versions` silently degrades to all-null rows with no red test; (b) nothing test-level red-lines an added property.
Why LOW rather than a privacy escalation: the API is a hard structural backstop — `apps/api/src/app.setup.ts:61` configures `ValidationPipe({ whitelist: true, transform: true, forbidNonWhitelisted: true })`, so an extra property **400s the whole registration** (fail-loud, nothing persisted, no third party involved), and `RegisterDeviceDto`'s two new fields are `@MaxLength(64) @Matches(/^[A-Za-z0-9._+-]+$/)` so free text cannot land in the columns even if sent. The plan's step-22 test list never asked for a client-side payload test, so this is a plan-level coverage gap rather than an executor omission. Suggested one-liner for T118, mirroring how T116's Finding 1 was closed: a `use-push-registration` test asserting `apiClient.post` is called with exactly `{expoPushToken, platform, appVersion}` (and `otaUpdateId` only when non-null).
