## 5. Findings

### F1 (BLOCKING) — the 401 test does not pin the dedicated 401 branch; the missed regression silently drops a completion

`flush-outbox.ts:49-55` breaks the loop on 401 without `markAttempt`, so a queued
completion survives indefinitely across re-auth (plan D6). Deleting **only** that
dedicated branch leaves all 18 outbox tests **GREEN**: 401 then falls through
`isTerminalDrop` (which excludes 401) and `isTransient` (401 matches none of
408/429/5xx/0) into the defensive-transient fallback at `:75`, which calls
`markAttempt` + `break`. Every assertion in
`"auth expiry: a 401 STOPS the flush and keeps every item queued"` (`:215`) still
holds — `{synced:0,dropped:0,remaining:2}`, `items.length === 2`, one POST — because
the test never inspects `attempts`.

I proved the behavioural delta with my own probe (6 consecutive 401 flushes):

- shipped code → `items` length **1** (retained, correct)
- mutated code → `items` length **0** (**the user's completion is silently dropped
  on the 5th auth failure**)

The shipped product is correct — this is a test-hardening gap, not a live defect —
but it is exactly the "outbox silently dropping completions" hazard, left unpinned.

**Fix (1 line, in-plan file):** add to `:215`
`expect(useOutboxStore.getState().items.every((i) => i.attempts === 0)).toBe(true);`

*Note:* the plan's M4 wording ("401 falls through to the terminal-drop branch") is
ambiguous. Read as "rewrite the 401 branch body into a terminal drop", M4 **is** RED,
which is likely what the executor ran. Read as "delete the branch", it is GREEN. The
second reading is the realistic regression, and it is unguarded.

### F2 (BLOCKING) — M6 is vacuous under CI; the executor's reported fix does not hold

The executor reported M6 as a documented deviation, "found and fixed" by a new test:
`"switching petId does not corrupt the LIVE hook's state when the old stream's abort
settles later (guard 2 pin)"` (`chat-stream.test.tsx:507`). That fix does not hold in
the configuration that gates the loop:

```
M6 (delete guard 2), full-file run  ->  Tests: 22 passed, 22 total   (GREEN)
M6 (delete guard 2), isolated -t     ->  Tests: 1 failed, 21 skipped  (RED)
```

The test is **order-dependent** — earlier tests in the file leave mock/store state that
changes the microtask timing of the aborted transport's rejection, so the assertion at
`:536` runs before the `.catch` settles. I confirmed the underlying behavioural delta by
forcing the state to be revealed: unmutated → `"streaming"`; under M6 → `"dropped"`.
So guard 2 genuinely matters (without it a `petId` switch corrupts the live hook into a
retryable `dropped` state, offering a spurious Retry for navigation the *user* initiated),
but **`pnpm test` would not catch its removal.**

Two compounding weaknesses in that assertion: it is order-dependent, and
`not.toBe("dropped")` is a negative assertion that passes for any of the other five
states.

**Fix (in-plan file `chat-stream.test.tsx`):** make the case order-independent
(reset `useChatStore` / re-seed `mockedStreamSse` in a `beforeEach` for this `describe`,
or `await waitFor` on the settled `.catch`) **and** assert the exact state,
`expect(result.current.state).toBe("streaming")`.

Per the plan's own hard rule — *"If any mutation comes back GREEN, the test is vacuous —
fix the test, do not weaken the mutation"* — this must be corrected before the card lands.

  `Promise.resolve()` hops;
