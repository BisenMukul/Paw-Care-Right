## 10. Findings

**F1 — [MEDIUM, follow-up] Post-header persistence can still throw out of the handler.**
`chat.service.ts:237-238` and `:247-248` (`persistAssistantMessage` + `logCost`) are awaited **after**
`sse.writeHead` and **outside** the `try/catch` at `:192-232`. If the DB or cost-log I/O fails there,
`streamMessage` rejects after headers are sent; `AllExceptionsFilter.catch` then calls
`response.status(...).json(...)` with **no `headersSent` guard**
(`apps/api/src/common/all-exceptions.filter.ts:44`), which raises `ERR_HTTP_HEADERS_SENT` and ends
with a destroyed socket, no `done` frame and no ASSISTANT row. This contradicts the service's own
doc-comment ("nothing after that point may throw out of this method", `:95`) and plan step 12.
Mitigating: **no unsafe content can be delivered by this path** (all released text already passed the
scanner), it needs an infrastructure failure to trigger, and the full fix touches
`all-exceptions.filter.ts`, which is **not on T081's exhaustive file list** — so it was out of scope
for this executor. Recommended for T082/T083: wrap the two post-header awaits in `try/catch` (emit
`done` regardless) and add a `if (response.headersSent) { response.destroy(); return; }` guard to the
filter.

**F2 — [MEDIUM, follow-up] Two safety-relevant branches are implemented but untested.**
Coverage reports `chat.service.ts` lines `195, 223, 237-239` uncovered:
- `:221-224` — the **empty-completion ⇒ SAFE_FALLBACK** convergence, which plan Safety statement 2
  names explicitly as a failure mode. It is correctly implemented; nothing exercises it.
- `:194-195` and `:234-239` — the **client-disconnect (`res.on("close")`) abort + persist-what-was-
  delivered** path (plan step 12). Correctly implemented; untested.
Neither is a listed AC test, so this is a gap in the plan's test matrix rather than a deviation from
it. Two cheap unit tests (a fake yielding zero chunks; an `onClose` fired mid-stream) would close it.

**F3 — [MEDIUM, documented residual / T082] Chunk-boundary evasion of the release scan.**
The scan is applied to `pending` only, with no overlap: at the forced
`CHAT_RELEASE_BOUNDARY_CHARS = 160` release (`chat.service.ts:44`) the split point is arbitrary, so an
unsafe pattern straddling that split ("… give 5" | "mg/kg …") is seen by neither scan. This is exactly
the design the plan pins in step 9, and the T081 posture (abort the whole answer) is strictly safer
than what preceded it, but the residual should be closed by T082's moderation hardening — e.g. scan
`lastReleasedTail(64) + pending` instead of `pending`. Sentence-boundary releases (`. `, `! `, `? `,
`\n`) are not affected in practice; the 160-char forced release is the exposed case.

**F4 — [LOW] Unit inconsistency between digest and pet block.** `digest.ts` deliberately spells
"kilograms" to dodge the DOSING `NUMBER kg` pattern, while `build.ts:46` renders `- Weight: 12.5 kg`
in the PET block. Harmless (prompt **input**, never scanned, never user-facing), but the asymmetry is
worth a one-line comment or the same treatment for consistency.

**F5 — [LOW] Generated eval-report artifacts in `loop/`.** `loop/eval-reports/latest.md` is modified
and two timestamped reports are new; my own `pnpm test:ai-evals` run added a third
(`2026-07-24T20-20-23-606Z.md`). These are tool-generated by a plan-mandated command, not hand-edits,
and `loop/loop-state.json` / `loop/journal.md` are untouched by the code diff. Flagging only so the
committer knows to include or ignore them deliberately.

**F6 — [LOW] `ChatThread_petId_createdAt_idx` is currently unused** (no list endpoint in T081). Plan-
mandated; no action.

Nothing on the mandatory-FAIL list occurred: no emit path bypasses the scanner; the safety prompt is
byte-identical and shared, not forked; the chat quota touches no check/emergency surface; the digest
carries a med **count** only; every new query pattern is index-covered in the same migration; both
routes are guarded (no `@Public`); and all three mutation proofs failed exactly as required and
