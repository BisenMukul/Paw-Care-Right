## 0. Verdict summary (round 1 — superseded by §11)

The implementation is, on almost every axis, high quality: the parser matches the server byte format, the
Zod-validated event mapping fails upward, the disclaimer is structurally unconditional, the nudge card routes
with the exact param shape, every gate is green, and 9 of 9 mutations (plus one substituted load-bearing
variant) are proven non-vacuous.

It nevertheless trips one **mandatory-FAIL** condition. A transport error arriving **after** a complete
`done{status:"SAFE_FALLBACK"}` frame converts the terminal safety state into the retryable `dropped` state:
the safe-fallback notice and its copy are **deleted from the transcript** and a **pressable Retry button is
rendered**. Proven empirically at both hook and screen level (§6, PROBE-1/PROBE-2). This is exactly the
"the two states cannot be conflated by any event ordering" invariant the plan asserts in D7 / Safety
statement 3, and exactly the `retry reachable from safeFallback` mandatory-FAIL in my brief.

The fix is small and local (guard `runStream`'s terminal handling on `sawDone`), which is why this is a
FAIL-and-fix, not a redesign.

### (b) The D7 dichotomy (SAFE_FALLBACK vs. dropped) — **FAIL**
Retry is rendered by exactly one JSX branch: `app/chat/index.tsx:163` `chat.state === "dropped" || chat.state === "error"`.
`safeFallback` and `blocked402` do not satisfy it, and `retry()` itself early-returns outside
`dropped`/`error` (`use-chat-stream.ts:185`). The happy paths are correct and M3-proven.

**But the state can be conflated by event ordering.** `runStream`'s `.catch`
(`use-chat-stream.ts:132-135`) is unconditional:

```ts
    .then(() => { if (!sawDone) { …removeMessage…; setState("dropped"); } })
    .catch((err: unknown) => {
      useChatStore.getState().removeMessage(petId, assistantId);   // <-- no sawDone guard
      setState(classifyError(err));                                 // <-- no sawDone guard
    });
```

The `.then` branch correctly guards on `sawDone`; the `.catch` branch does not. So `done(SAFE_FALLBACK)`
followed by a transport close-with-error ⇒ **`dropped` wins**. Proven in §6.

Reachability is real, not theoretical: `expoSseTransport` keeps iterating `reader.read()` after the chunk
carrying `done` until EOF, so any read failure in that window (cell handoff, app backgrounding, proxy
timeout, TLS reset) lands in `.catch`. `streamSseRequest`'s `parser.flush()` loop
(`packages/api-client/src/stream.ts:103-105`) can also throw there.

## 8. Findings (numbered, severity-tagged)

**BLOCKER-1 · Safety (§7 rule 5, PRODUCT_SPEC §5, plan D7 / Safety statement 3) — MANDATORY FAIL.**
`apps/mobile/src/chat/use-chat-stream.ts:132-135`: the `.catch` in `runStream` is not guarded on `sawDone`,
unlike the `.then` at `:126-131`. A transport error arriving after a complete `done{status:"SAFE_FALLBACK"}`
frame therefore (a) deletes the assistant bubble *including* the `chat-safe-fallback` notice and the
fallback copy, and (b) sets state `dropped`, which renders the `chat-retry` button
(`app/chat/index.tsx:163-167`). Proven by PROBE-1 (`state = "dropped"`) and PROBE-2
(`retry-present= true | safe-fallback-notice-present= false | fallback-text-nodes= 0`).
Reachable whenever the byte source fails between the `done` chunk and EOF — a routine mobile-network event
given `expoSseTransport` keeps reading to EOF (`expo-sse-transport.ts:28-36`), and also via a `flush()`-phase
throw (`stream.ts:103-105`).
*Fix:* once `sawDone` is true the outcome is final — skip both the `removeMessage` and the `setState` in the
`.catch` (or return early). Add a regression test: `chunk` → `done{SAFE_FALLBACK}` → transport throw ⇒ state
`safeFallback`, `chat-safe-fallback` present, `chat-retry` null; plus the `done{OK}` twin.

**FINDING-2 · Medium (same root cause).** The identical path erases a **completed `OK` answer** and offers a
Retry that re-sends a message the server has already persisted and quota-charged — duplicating the DB
message and double-decrementing the user's 200/month fair-use allowance
(`CHAT_FAIR_USE_MONTHLY_LIMIT`, `packages/types/src/chat.ts:27`). Fixed by the same `sawDone` guard.

**FINDING-3 · Medium (UX dead-end).** `blocked402` is terminal for the session: `composerDisabled`
(`app/chat/index.tsx:108-109`) includes it, and nothing ever clears the state, because the only transition
out is `send()`, which the disabled composer makes unreachable. After a *successful* purchase through
`/paywall?source=chat` the user returns to a permanently dead screen until they navigate away and back.
Design-system §7.5 "no flow dead-ends" — the very rule the plan invokes for R1. Suggest resetting to `idle`
on paywall return or on `premiumStatus` becoming `entitled`.

**FINDING-4 · Low (copy honesty).** The `error` state (a non-402 `ApiError`, e.g. HTTP 500) reuses the
`chat-stream-dropped` block and its copy *"We lost the connection before finishing that answer."*
(`app/chat/index.tsx:163-165`, `strings.ts` `chat.dropped.title`) — a claim about what happened that is false
