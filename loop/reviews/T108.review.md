Exactly D3. Empty history → `startsAt === now` (seed `0` can never beat a real epoch-ms `now`).
- **Clock edge "grant issued at exactly the tip moment".** `Math.max(now, tip)` with `now === tip` yields the same instant either way — the window is deterministic and identical; no double-count and no gap. Test `referral-grant.util.spec.ts:18-24` pins `second.startsAt === first.expiresAt`.

## Findings

**F1 — MEDIUM (non-blocking) — the `P2002` "silent skip" cannot actually work inside the Postgres transaction, and a grant-write failure can now fail a household join.**
Evidence: `referral-grant.service.ts:75-95` catches `P2002` and continues; the call site is inside
`prisma.$transaction` (`households.service.ts:129,167`). Prisma interactive transactions do not wrap
individual statements in savepoints, so a real unique-constraint violation aborts the Postgres transaction —
every subsequent statement (`tx.household.findUnique` at `:173`) would fail with `25P02` and the whole
accept would roll back. The unit test at `referral-grant.service.spec.ts:107-120` passes only because `tx`
is a mock. Why this is not HIGH: the branch is **unreachable** in production (single-use invite claim + two
distinct recipients per accept), and the service doc comment (`:22-26`) discloses that a non-`P2002` error
rolls the accept back. Residual: T108 introduces a *new* failure source into a core flow (a referral-table
write can now 500 a join), in tension with D6's "an abuse guard must never fail a household join".
Follow-up option: issue grants outside the claim transaction, or use an explicit savepoint.

**F2 — MEDIUM (non-blocking) — under READ COMMITTED both the cap and the chaining are racy; the plan's "never lost to concurrency" claim overstates the guarantee.**
Evidence: `referral-grant.service.ts:63-73` reads the recipient's grants then inserts, with no row lock, no
`SELECT … FOR UPDATE`, and no DB-level count constraint. Two accepts naming the same recipient
(realistically: two joiners accepting two of the same inviter's invites concurrently) can each read
`existing.length === 2`, both pass `isGrantCapReached`, and both insert — 4 rows, so the "hard lifetime cap
of 3" is a soft cap under concurrency. The same race makes two windows overlap (`startsAt` both `now`), so
the recipient silently *loses* 14 days of chained coverage, contradicting plan D3's "never lost to
concurrency" (true only for serialized issuance). Blast radius is one extra 14-day window per concurrent
burst; not blocking, but the plan's wording should be corrected.

**F3 — LOW — share copy over-promises in the capped and already-subscribed cases.**
"When you join, we each get 14 days of Premium" (`strings.ts`, `family.shareMessage`) is unconditional, but
(a) a recipient at the lifetime cap receives nothing (silent skip, by design), and (b) per D9 a recipient
already covered by an own/family subscription gets a window that elapses unused underneath the RC
entitlement — which is the mainstream case, since the usual reason to invite is a family plan. The
owner-facing `referralCaption` discloses "(up to 3 times)", but the message the invitee reads does not. No
§7 safety rule is broken (no medical/dosing/earnings claim) and the card's literal AC is met, so this is a
copy/legal-honesty item for the founder; `docs/referral-grants.md` §2/§7 already flags D9 for decision.

**F4 — LOW — doc §4 vs §5 tension on "a referral chain can only start from an already-paying account".**
True of the first hop only; §5 bullet 3 correctly states grant-funded users can mint invites. Suggest
qualifying §4 guard 4. Not a code defect.

**F5 — INFO (pre-existing, NOT T108) — accepting an invite destroys the joiner's own `Subscription` row.**
`households.service.ts:151-153` deletes the joiner's solo household; `schema.prisma:376` cascades
`Subscription` from `Household`. An owner with their own paid RC mirror row who joins another household
loses that row. This is T026 + T072 behaviour, untouched by this diff, and it is the correct reason the AC6
byte-identical probe uses the inviter's row — the executor's attribution is accurate. Flagged for the
planner as a separate pre-existing concern; out of scope for T108.

## R6. New findings from this round

**F8 — HIGH (BLOCKING) — the fix round's own residual is undisclosed: a failed or interrupted issuance loses both grants permanently, silently, with no retry and no repair path.**
Moving issuance outside the accept transaction converts it from "atomic with the join" to **best-effort,
at-most-once, fire-and-forget**. Concretely, all of the following end with a committed join and **zero**
grant rows, invisible to the user and to the invitee who was promised the grant:
- the process is killed / the pod is evicted / the request is aborted between the join commit
  (`households.service.ts:172`) and the issuance call (`:184`);
- issuance throws for any reason — caught and swallowed at `:190-194`;
- the issuance transaction hits Prisma's **default 5 s interactive-transaction timeout** (no options are
  passed at `referral-grant.service.ts:72`) while queued behind the advisory lock of a popular inviter →
  `P2028` → swallowed;
- a Postgres deadlock or a serialization abort inside that transaction → swallowed;
- an error on the *second* recipient rolls back the *first* recipient's already-inserted row (F10).
There is **no BullMQ job, no outbox, no reconciliation sweep, and no retry** — and there cannot be a
retrigger, because the invite's `usedAt` is already set, so a re-POST is a 404. I demonstrated the exact
end state with mutation E: **200 OK, zero grants, no user-visible signal.**
This cost is the honest price of the F1 fix and it is defensible — but `docs/referral-grants.md` currently
presents the post-commit design **only** as an upside (§1: "no grant-path error … can ever roll back a join
that already succeeded"; §4 guard 2: "logs it and swallows it there"), and never states that a swallowed
failure means the grants are never issued at all. The card's AC includes "— documented", and AC8 is the
criterion this omission breaks. **Required fix (single, narrow edit): add the residual to
`docs/referral-grants.md` — issuance is best-effort/at-most-once; the enumerated failure modes above;
no retry/outbox/reconciliation exists and the invite cannot be re-accepted; the 5 s transaction-timeout
exposure; and an explicit `[FOUNDER]` line in §7 on whether a retry/outbox is wanted before launch.**
A matching sentence in `referral-grant.service.ts`'s class doc comment and/or the `catch` at
`households.service.ts:190` would be good practice but is not required. No code change is required by
this finding.

**F9 — LOW — no test pins the "grant failure does not fail the join" property at the e2e level.**
It is pinned only in `households.service.spec.ts:298-309` with a mocked rejecting service. My mutation E
shows the property genuinely holds through the real stack, so this is a coverage nit, not a defect;
consider it optional. (Suggested if cheap: an e2e that provider-overrides `ReferralGrantService` to throw

**F10 — INFO — issuance is both-or-neither across the two recipients.** One transaction covers both; a
failure on the second recipient discards the first's insert. Reasonable, but it belongs in the F8
disclosure.

**F11 — INFO — deadlock-avoidance sort is on the id string, not on the lock key.** `lockOrder` sorts
userIds lexicographically while the lock is `hashtext(userId)`. Order inversion between two transactions
needs two independent int4 collisions; the consequence would be a detected deadlock aborting a swallowed
issuance transaction. Negligible; no change recommended.

**F12 — INFO — `$transaction` uses default options.** `referral-grant.service.ts:72` passes no
`{ timeout, maxWait }`. Fine at current write rates; relevant only as part of F8's disclosure.
