## 3. PII adversarial audit (duty 1) — what actually reaches the wire

Method: real `@sentry/node` (api workspace) + the **real shipped scrubber** from
`packages/analytics/dist/index.cjs`, custom capturing transport, one process per probe, markers
injected at **runtime via env** (my first probe run was contaminated by the SDK's
`contextLinesIntegration`, which attaches source lines around stack frames — every marker literal in
the probe *source* showed up in the envelope; v2 fixes this and the result changed, which is itself
worth knowing).

| Probe | Payload | Reached the wire? |
|---|---|---|
| **E** | `request.data.symptomText`, `request.cookies.session`, `request.query_string=token=…` | **none** — structural drops hold end-to-end through the real SDK ✔ |
| **A** | `console.log("[AllExceptionsFilter] 500 INTERNAL: <marker>")` then `captureException` | **LEAKED** — Sentry's default `consoleIntegration` turns it into a breadcrumb; scrubber keeps `breadcrumb.message` |
| **D** | `addBreadcrumb({message: "intake=<marker>"})` | **LEAKED** (same channel, explicit) |
| **B** | `new Error("failed to save note: <marker>")` | **LEAKED** — free text inside `exception.values[].value` |
| **C** | `request.env.REMOTE_ADDR = 203.0.113.9` | **LEAKED** — `scrubRequest` is a *deny*-list (`DROPPED_REQUEST_KEYS = {data, cookies, query_string, url, headers}`); every other `request.*` key is copied through verbatim (`scrub.ts:114-125`) |

Reading of the results:

- The card's core claim — *"no intake text in events"* — **holds for the §5-sensitive payload**:
  intake text and chat content travel in request bodies, and probe E proves they are dropped
  structurally inside a real SDK pipeline (and M1 proves a test catches it if that ever regresses).
- `redactDeep` **does** walk `message`, `exception.values[].value`, breadcrumb messages, `extra`
  and `contexts` (probe B/D leaks are of *free text*, which the pattern-based redactor by design
  cannot catch — emails/`Bearer`/JWT in those same fields *are* redacted, each with its own test).
- The **new** thing my probes surface, which the plan's D3/R3 did not consider, is the *amplifier*:
  `@sentry/node`'s `consoleIntegration` is a **default** integration and `@nestjs/common`'s
  `ConsoleLogger` writes through **`console.log`** (verified:
  `node_modules/.pnpm/@nestjs+common@*/…/services/console-logger.service.js:159,177`). So **every
  Nest `Logger` line in the process becomes a Sentry breadcrumb** on the next captured 5xx. Same on
  mobile for the two justified `console.error` call sites.
- I then audited whether anything user-identifying is on that channel **today**: 65 non-spec
  `logger.*` call sites in `apps/api/src`. `chat.service.ts:239,269` are content-free by
  construction (T082 D3 — codes only). `auth/otp-transport.ts:25` logs `OTP for ${email}: ${code}`
  but is hard-gated by `nodeEnv !== "production"` (and the email would be redacted by the deep walk;
  the code would not). So: **a live, wide-open PII *channel*, with no *proven* PII payload on it
  today.** That is why Finding 1 below is HIGH-severity-but-not-mandatory-FAIL rather than the
  automatic fail the brief reserves for a demonstrated PII path.

Positive controls I also ran (all correct): email/`Bearer`/JWT redaction across all five surfaces;
`user` reduced to `{id}` (email/ip/username gone) and an email *in* `user.id` is still redacted by
the deep walk; case-insensitive header allowlist (`Authorization`, `Cookie`, `X-Api-Key` all
dropped, `host`/`user-agent` kept); breadcrumb `data` allowlist + `?`-truncation; fail-closed `null`
on a throwing getter; `[Circular]` on cycles; input never mutated.

## 5. Findings

**F1 — [HIGH] Console/breadcrumb channel carries arbitrary logged text to Sentry; neither scrubbed
nor tested.** Proven by probes A and D (§3). `consoleIntegration` is on by default in
`@sentry/node`/`@sentry/react-native`, and Nest's `Logger` goes through `console.log`, so the
scrubber's careful structural body-drop is bypassed for anything an operator ever logs. `scrub.ts`
allowlists `breadcrumb.data` but leaves `breadcrumb.message` to the pattern redactor only, and
`baseSentryOptions` sets no `beforeBreadcrumb`/`maxBreadcrumbs`. No test pins this either way. The
card's own words are *"PII scrubbing so no intake text … ever reaches Sentry"*; this is the gap in
that claim. Two acceptable resolutions: (a) add `beforeBreadcrumb` to the **shared** factory
dropping (or allowlisting) `category === "console"` breadcrumbs, with a scrub/options spec case and
an api envelope case proving a `console.log` marker never reaches the wire; or (b) consciously
accept the residual, add the test that *pins* current behaviour, and journal the acceptance with the
`auth/otp-transport.ts:25` dev-only exception named. Not (c): ship it undocumented and untested.

**F2 — [HIGH] Mobile capture call sites are untested — proven vacuous (CP-F3).** Both
`captureError` calls can be deleted with the full 159-suite/1262-test mobile suite staying green.
The plan named this test; it is missing. `apps/mobile/__tests__/sentry.test.ts` tests
`initMobileSentry` and `captureError` in isolation but never asserts the two wiring points. Fix:
two small tests (mock `../observability/sentry`, render/throw through `AppErrorBoundary`
`componentDidCatch`, and invoke the installed `ErrorUtils` handler via the existing
`__resetStartupGuardForTest()` seam) that fail when either call is removed.

**F3 — [MED] `scrubRequest` is a deny-list, not an allowlist.** `scrub.ts:114` drops exactly
`{data, cookies, query_string, url, headers}` and copies every other `request.*` key verbatim; probe
C shows `request.env.REMOTE_ADDR` (a client IP) survives. The JS SDK does not populate
`request.env` today, so this is latent rather than live — but it contradicts the allowlist
discipline used two lines later for headers and for breadcrumb data, and R3's own mitigation
argument ("bodies dropped structurally so a new endpoint can never leak by omission") does not
extend to a *new SDK field*. Cheapest fix: invert to an allowlist
(`{url, method, headers}` + the truncation already there) with a test asserting an unknown
`request.*` key does not survive.

**F4 — [LOW, accuracy of a safety claim] `initMobileSentry()` is *not* fully try/catch-wrapped.**
`apps/mobile/src/observability/sentry.ts` calls `getConfig()` **before** the `try` block, yet
`apps/mobile/app/_layout.tsx:25-28` asserts "`initMobileSentry` is itself try/catch-wrapped
internally so it can never throw regardless of call order". `getConfig()` is optional-chained and
realistically cannot throw, so the risk is nil — but the comment is the *justification* for the
deviation adjudicated in §6, and a justification that overstates its guarantee should be corrected
(move `getConfig()` inside the `try`, or soften the comment).

**F5 — [LOW] CI hardcodes the release version.** `.github/workflows/ci.yml` uploads with
`version: "pawcareright@0.0.0+${{ github.sha }}"` while the runtime release is
`pawcareright@${APP_VERSION}+${GIT_SHA}`. The moment T099 sets a real `APP_VERSION`, the uploaded
artifact bundle and the runtime release name diverge and source maps stop resolving — silently.
D6 explicitly said "no hardcoded duplicate of a package.json version". Journal it as a T099 seam at
minimum (`R7` already flags the drift; this is the CI half of it).

**F6 — [LOW] `apps/web/app/global-error.tsx` uses inline `style={{…}}` objects and has no test.**
Web is a Tailwind app (§3/§6); jest `roots` is `<rootDir>/src`, so nothing under `app/` is covered.
Defensible (the boundary replaces the root layout, so layout-loaded CSS may not be present) but
undocumented — one sentence in the file or the journal settles it. Copy itself is clean: externalised
to `strings.ts:387-394`, generic, no §5/§7 surface.

**F7 — [LOW, noise] `apps/web/package.json` was reformatted wholesale** (deps alphabetised, jest
arrays expanded) — 41 changed lines for a 2-line dependency addition. On-list file, zero behaviour
change, but it inflates the diff and hides the real edit.

**F8 — [caveat, mandatory before commit] Loop bookkeeping is absent.** No `loop/journal.md` T089
entry; `loop-state.json` still `pending`; no commit. The journal owes, specifically: (a) AC1
evidence naming `apps/api/src/observability/sentry.spec.ts` with the **explicit limitation** "no
staging DSN in this environment; the forced-error proof is the mock-transport spec"; (b) the founder
to-do — create Sentry org/projects, set real DSNs + `SENTRY_AUTH_TOKEN`, run one real forced-error
smoke per platform; (c) the dev-client rebuild / fingerprint note for the new native module
(OTA_UPDATES §1); (d) **three** §2 rule 7 dependency justifications (`@sentry/node`,
`@sentry/nextjs`, `@sentry/react-native`); (e) the D2/R2 mobile-release deviation and its T117
hand-off; (f) mobile source maps ride EAS, not CI (D7). Also decide what to do with the
`loop/eval-reports/*` files my eval run produced (§0).

**Informational, not a finding:** the web build prints
`[@sentry/nextjs] ACTION REQUIRED: … export an onRouterTransitionStart hook from
instrumentation-client` — that is navigation *tracing*, explicitly out of scope
(`tracesSampleRate: 0`). It also usefully proves Next 15 picked up `instrumentation-client.ts`.

## 6. Deviation adjudications

**D-1 — `initMobileSentry()` call placed after all imports (import-x/order) — ACCEPTED.**
ES-module imports are hoisted and evaluated before any statement in `_layout.tsx`, so
`import "../src/startup-guard"` (line 4, first) — which self-installs the global handler at module
scope (`startup-guard.ts` ends with a bare `installStartupGuard()`) — runs strictly before
`initMobileSentry()` at line 29, regardless of where in the file the call sits. The startup-guard-
first claim therefore holds. Two riders: the init body's own `try/catch` is real but does **not**
cover `getConfig()` (F4), and `startup-guard.ts` now *imports* `./observability/sentry` →
`@pawcareright/analytics` + `../config`, so the guard is no longer the import-free module the plan
described ("it has no imports and must trap everything"). A module-load failure in that small,
dependency-light graph would now prevent the guard from installing. Acceptable, but it is a real
narrowing of the guard's guarantee and belongs in the journal.

**D-2 — email regex TLD tightening — ACCEPTED, verified empirically, not just read.** Running the
shipped scrubber over a case list: `owner@example.com`, `a.b+c@sub.domain.co.uk`,
`first.last@mail.example.io`, `OWNER@EXAMPLE.COM` → all `[REDACTED]`; `user@example.co1` →
`[REDACTED]1` (still redacted, just not the trailing digit); `pawcareright@0.0.0+abc1234`,
`pawcareright@1.2.3+deadbeef`, `pawcareright@0.0.0-rc.1+sha` → **untouched** (the bug the deviation
fixes: the pre-tightening pattern ate the release string). Residual non-matches are
`user@localhost`, `x@y.z` (1-char TLD) and `test@192.168.0.1` (IP-literal domain) — none are
real-world deliverable addresses; I judge the trade correct. The regression is guarded by
`scrub.spec.ts:131` which pins `release: "pawcareright@0.0.0+abc1234"` through the scrubber.

**D2/R2 — mobile release slot — ACCEPTED.** `buildSentryRelease(getAppVersion(), config.gitSha)`
preserves the §1a shape `pawcareright@{version}+{buildId}`; `OTA_UPDATES.md:73`'s

## 8. Verdict

The engineering here is genuinely good: the offline AC1 proof is the honest, rigorous kind (a real
SDK, a real envelope, planted markers asserted absent — and it says out loud that no staging DSN
exists rather than inventing one), the scrubber fails closed for real (M10), the release shape is
exactly §1a, CI is green by construction without secrets (M9), and the filter's existing semantics
are untouched (M7). Six mutations re-run by me all died on the exact named tests.

But two holes are of the class this loop fails on. My probe CP-F3 shows the **mobile crash-reporting
wiring can be deleted outright with 1262 mobile tests still green** — a plan-named test that was not
written, on the card's own headline deliverable ("Sentry init api/web/mobile"). And my probes A/D
show a **live, unscrubbed, untested channel to the Sentry wire** (`console.*` → default
`consoleIntegration` → `breadcrumb.message`, fed by every Nest `Logger` line in the process) that
the card's "PII scrubbing so no intake text ever reaches Sentry" promise does not cover. I stop
short of calling F1 a demonstrated PII leak — I audited all 65 api logger sites and found no live
user-content payload (chat logging is content-free by construction; the OTP line is dev-gated) — but
"no PII on it today, by luck of what we happen to log" is not a control, and there is no test to
keep it that way.

Both fixes are small and local. Nothing needs redesign.

VERDICT: fail

Reasons:
1. **[HIGH, F2]** Checker probe CP-F3: deleting **both** mobile `captureError` call sites
   (`error-boundary.tsx` `componentDidCatch`, `startup-guard.ts` global handler) leaves
   `pnpm --filter mobile test` at **159 suites / 1262 tests, exit 0**. The plan's AC1 test list names
   "error boundary and startup guard forward to captureError"; it was not written. Mobile crashes
   could silently stop reaching Sentry with every gate green. Fix: two tests that die when either
   call is removed.
2. **[HIGH, F1]** Probes A/D (real `@sentry/node` + real scrubber + capturing transport): a
   `console.log` line and an `addBreadcrumb` message both reach the serialized envelope verbatim.
   `consoleIntegration` is a default integration and `@nestjs/common`'s `ConsoleLogger` writes via
   `console.log`, so every api log line rides along as a breadcrumb; `baseSentryOptions` sets no
   `beforeBreadcrumb`, and no test covers free-text breadcrumb content. Close it in the shared
   factory (+ a test proving a planted console marker never reaches the envelope), or explicitly
   accept it with a behaviour-pinning test **and** a journal entry — but not silently.
3. **[MED, F3]** Probe C: `scrubRequest` deny-lists five keys and passes every other `request.*` key
   through (`request.env.REMOTE_ADDR` = client IP survives). Latent today because the JS SDK does not
