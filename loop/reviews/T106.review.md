## 7. Numbered findings

**F1 — MEDIUM — `503 → FEATURE_DISABLED` is a global mapping and mislabels health-check failures.**
`apps/api/src/common/all-exceptions.filter.ts:23` maps *every* 503 to `FEATURE_DISABLED`. The only other 503 producer in the repo is `apps/api/src/health/health.service.ts:24` (`throw new ServiceUnavailableException("Dependency health check failed.")` when Postgres or Redis is unreachable). So a Postgres/Redis outage on `GET /v1/health` now answers `{ error: { code: "FEATURE_DISABLED", … } }` — and `GET /v1/health` is exactly the verify signal the new runbook §12/§16 instructs the operator to read during a deploy or a rollback. No test broke and no client consumes that code (verified: no `/v1/health` consumer in `apps/mobile/src`, `packages/api-client/src`, `apps/web`), and the HTTP status that monitors key off is unchanged — so this is a diagnosability defect, not a functional or safety one. Fix options: a dedicated exception subclass mapped explicitly, a `FeatureDisabledException` carrying its own code, or (cheapest) one line in §12's `apps/api` verify cell noting that a 503 from `/v1/health` currently reports `FEATURE_DISABLED`. Not blocking — plan D6 specified exactly this mapping, so the collision was missed at plan time rather than introduced carelessly.

**F2 — MEDIUM — the container-coverage drift guard is doc-wide, not §12-table-scoped, so a whole container row can vanish undetected.**
`release-runbook-doc.test.ts:118-123` asserts `expect(runbook).toContain(container)` against the entire file. My **MUT-D** deleted the whole `| \`apps/web\` | Standard Next.js redeploy … |` row from §12's coverage table: `release-runbook-doc.test.ts` stayed **13/13 GREEN**, because §16 item 4 mentions `apps/web` incidentally. Two-line fix: slice the runbook to `indexOf("## 12.") … indexOf("## 13.")` before the `toContain` loop — the same slicing idiom the file already uses for §13 and §15.

**F3 — MEDIUM — every kill-switch rejection emits a Sentry event plus an error-level log, for the entire duration of a kill.**
`all-exceptions.filter.ts:40-56`: the filter logs at `logger.error` unconditionally and calls `captureApiException` whenever `status >= 500`. Because the kill switch rejects with 503, each blocked `POST /checks` or chat call during an incident produces one Sentry error event and one error log line. A kill is expected to last minutes-to-hours (§15's containment step), so the practical effect is alert fatigue and Sentry quota burn at exactly the moment observability matters most — and §14 does not warn the operator about it. (I saw this concretely: the api suite log carries `FeatureFlagGuard.canActivate` stack traces logged at error level from the kill-switch e2e cases.) Recommend either excluding the kill rejection from Sentry capture (its own exception type, checked before `captureApiException`) or an explicit §14 note: "expect elevated 503/`FEATURE_DISABLED` volume in Sentry while a switch is off; this is not a new incident." Operational, not safety; non-blocking.
