## Findings

### F1 — HIGH — the machine-translation safety scan skips function leaves entirely, and does not exist on web; `docs/I18N.md §6` claims otherwise

`docs/I18N.md:109-115` states, as the load-bearing safety claim of this task:

> "`i18n-safety-pins.test.ts` (mobile) **and the folded-in assertions in `locale-coverage.spec.ts` (web)** byte-pin every §5/§7 frozen string … **and additionally scan every translated value** for a digit+unit dose pattern and for diagnosis lexemes in the target language"

Both halves of the emphasised claim are false, and I proved it by mutation:

1. **Web has no such scan whatsoever.** `apps/web/src/i18n/locale-coverage.spec.ts` (read in full,
   99 lines) contains only coverage assertions and English byte-pins — no `DOSE_PATTERN`, no
   `DIAGNOSIS_LEXEMES`. Mutation **D** planted *"administre 5mg de ibuprofeno. Este es un
   diagnóstico."* into a translated web dictionary value and produced **zero** safety-test failures.
2. **The mobile scan silently skips function leaves.** `apps/mobile/__tests__/i18n-safety-pins.test.ts:107-114`
   and `:132-139` — `collectStringLeaves` handles `typeof node === "string"`, `Array.isArray`, and
   `typeof node === "object"`; a **function** is none of those, so it returns `[]`. Mutation **E**
   planted dosing + diagnosis text in `es.addPet.common.stepOf` and produced **zero** failures.
   (Contrast T097's `strings-detector-lint`, which deliberately *invokes* function leaves via
   `fn.length` — the pattern this test should have copied.)

There is exactly **one function leaf per dictionary** (`grep -c "=>"` → 1 in each of the 6 dicts),
and on web that one leaf is `footer.notice` — the most safety-adjacent string in the entire web
dictionary (see F2). The hole lands precisely on the value that most needs the net.

No user impact today (nothing non-`en` is served — see the serve-gate probe), but `docs/I18N.md` is
the document the founder is told to trust *before flipping a locale to `reviewed:true`*, and it
asserts a mechanical guarantee that does not exist. Per CLAUDE §7 (checker-enforced) and the plan's
own R3 ("the burden of proof sits on the change, not on the pin"), an unbacked safety claim in the
safety doc is a defect, not a nit.

**Remediation (small, contained):** make `collectStringLeaves` invoke function leaves (mirroring
`strings-detector-lint`'s `fn.length`-based collector) in `i18n-safety-pins.test.ts`; add the same
dose/diagnosis scan to `apps/web/src/i18n/locale-coverage.spec.ts`; keep the existing planted
positive controls and add one for a function leaf. Then `docs/I18N.md §6` is true as written.

### F2 — HIGH — web `footer.notice` is a §5 safety-disclaimer sentence and it IS machine-translated in all three web dictionaries

`apps/web/src/strings.ts:388-390`:

```
notice: (appName: string) =>
  `${appName} provides general guidance only and is not a substitute for veterinary care.`,
```

`footer` is a declared translated section (`apps/web/src/i18n/locale-registry.ts:18-22`), so this
sentence is machine-translated in `apps/web/src/i18n/locales/es.ts:16-17`, `pt-BR.ts` and
`hi.ts:16-17`. That directly contradicts the plan's own central rule (plan §2 line 13: *"No §5/§7
safety surface is ever machine-translated"*; plan §8: *"No translation of legal, pricing,
food/toxin, breed-guide or any §5/§7 copy"*) and the executor's report claim that "§5/§7/legal keys
stay English in every dict".

By the review rubric this is exactly the HIGH case: a §7-relevant string that is **not** in
`SAFETY_PINNED_PREFIXES` and **would be machine-served the moment a locale flips to
`reviewed:true`** — with no English-pattern detector able to validate it (plan R3) and, per F1, no
substitute scan covering it either.

Mitigating facts (why this is latent rather than an active safety failure): the three translations I
read are faithful and preserve the English hedge exactly (es: "ofrece orientación general y **no
sustituye** la atención veterinaria"; hi: "…**पशु चिकित्सा देखभाल का विकल्प नहीं है**"); the string is
**not** among T097's frozen §5 byte-pins (those — `disclaimer`, `landing.emergencyNote`,
`foodPage.emergency.*`, `foodPage.whatToDo.*` — are all correctly English-pinned and asserted at
`locale-coverage.spec.ts:75-98`); and nothing non-`en` is served today.

This is a **plan defect faithfully executed** (the planner named `footer` as a translatable web
section in plan §2.5), not an executor invention — but the checker judges the shipped state.

**Remediation options (either acceptable):** (a) narrow the web `TRANSLATED_SECTIONS` to
`["globalError"]` and add `footer.` to `SAFETY_PINNED_PREFIXES` (the complement test regenerates
mechanically) — cleanest, and consistent with R3; or (b) keep `footer` translatable but pin
`footer.notice` as English via a nested exception with a written §7 justification, recorded in
`docs/I18N.md §6` as a named carve-out. Option (a) is preferred.

### F3 — MEDIUM — `selectActiveLocale` fails *open* when `nodeEnv` is undefined

`packages/config/src/i18n/locales.ts:171`:

```ts
if (override && nodeEnv !== "production" && isSupportedLocale(override)) return override;
```

Probe C: `selectActiveLocale({override:"es"})` (no `nodeEnv`) → **`"es"`**, i.e. an unreviewed
machine locale bypasses `resolveServedLocale`. The dev-override bypass itself is intentional and
well documented (`locales.ts:155-164` — it is the only way to exercise the pseudolocales), but the
condition is a denylist. Any runtime that does not set `NODE_ENV` (a bare `node` process, a custom
server entry, a script importing the config package) plus a stray `*_I18N_LOCALE` value serves
unreviewed copy. §5's "fail upward" principle argues for an allowlist:
`(nodeEnv === "development" || nodeEnv === "test")`. Two things must both go wrong today and
`.env.example` ships both vars empty with an explicit warning, so this is not blocking on its own.

### F4 — LOW — `getStrings(locale)` is an exported serve-gate bypass returning `unknown`

`apps/web/src/i18n/runtime.ts:57-61` resolves an arbitrary caller-supplied locale without passing
through `resolveServedLocale`. It exists for the F7 resolver-level web tests and is used only by
`pseudo-locale.spec.ts` today, but it is a public export of the app's i18n runtime whose name
invites use from a page/route, and its `unknown` return type gives no type-level friction. Suggest
routing it through `resolveServedLocale` (the pseudo-locale specs can call the module-private
`resolveForLocale` instead) or renaming it to something explicitly unsafe.

### F5 — LOW — the static hardcoded-string scan is close to vacuous as a leak detector

`apps/mobile/__tests__/hardcoded-string-scan.test.ts:65` — `JSX_TEXT_PATTERN` excludes any text node
containing `{` or `}` and requires a same-name closing tag on the matched region, yielding **0
findings and an empty allowlist** over `app/**` + `src/components/**`. The limitation is stated
honestly in the file header (`:10-19`), there is a real positive control (`:121-126`) and a negative
control (`:128-132`), and the rendered leak test is the strong proof — so this is acceptable as
shipped. Flagged only so nobody later mistakes a green static scan for coverage.

### F6 — INFO — web `SAFETY_PINNED_PREFIXES` contains `"disclaimer."` for a root *leaf*

`apps/web/src/i18n/locale-registry.ts:31` — `disclaimer` is a function leaf at the tree root, not a
section, so the trailing-dot prefix can never match its leaf path `"disclaimer"`. It is internally
consistent (the complement test at `locale-coverage.spec.ts:63-72` computes the same `${key}.`
form) and the leaf is separately byte-pinned at `:79-81`, so nothing is unguarded — the prefix is
decorative rather than functional.

### F7 — INFO — `formatWeight` defaults to `"en"` while `formatCheckDate` uses `getActiveLocale()`

`weight-units.ts:45` vs `check-history.ts:39`. Both match plan §2.6 exactly and both are correct
while `en` is the only served locale, but the asymmetry means the weight surface will silently stay
English-formatted when the first locale is served. `docs/I18N.md §7` documents the default; worth a
line in the follow-up list.

### F8 — INFO / accepted — `ar` ships no dictionary (plan R4/D4)

The card says "RTL smoke (ar)". T110 registers `ar` with `direction: "rtl"`, asserts
`getTextDirection("ar") === "rtl"` directly (`rtl-smoke-snapshot.test.tsx:226`,
`locales.spec.ts:34-57`) and runs the smoke through the Android-standard `ar-XB` RTL pseudolocale
rather than inventing unreviewable Arabic — including unreviewable Arabic safety copy. I agree with
that reading of the card: it is the honest, §5-consistent choice, and the RTL code path exercised is
identical.

## Verdict rationale

all three ACs pass literally with non-vacuous proofs, every gate reproduces exactly as claimed, the
diff is minimal and precisely scoped, and the `reviewed:false` serve gate survived every bypass

on mobile (F1) — both proved by planting real dosing/diagnosis copy and watching every test stay
green, while `docs/I18N.md §6` tells the founder that scan covers "every translated value". Nothing
unsafe reaches a user today, but the next task in this pipeline is "flip a locale to
`reviewed:true`", and that task would be run against a safety guarantee that is not there.
