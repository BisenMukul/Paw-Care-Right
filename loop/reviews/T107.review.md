## 3. Findings

### F1 — HIGH — `paywall_experiment_assigned` is never emitted for arm A, and unreliable for arm B

The dedupe latch is consumed before the emit guard is evaluated, and the first evaluation is always made while signed out.

- `apps/mobile/src/experiments/paywall-experiment.ts:19-25` — `captureAssignmentOnce` sets `assignedThisSession = variant` **unconditionally**, then calls `captureEvent`.
- `apps/mobile/src/analytics/analytics.ts:26-32` — `captureEvent` **silently returns** when `useAuthStore.getState().user?.id === undefined`.
- `apps/mobile/src/auth/auth-store.ts:43-48` — the store initialises `status: "restoring", user: null`; `restore()` is `async` and awaits `readRefreshToken()` (SecureStore) then `authApi.refresh()` (network).
- `apps/mobile/app/_layout.tsx:74-76, 82` — `restore()` is kicked off in `AppRoot`'s own mount effect, and `usePaywallExperimentAssignment()` is called in the same commit. Its effect (`use-paywall-experiment-assignment.ts:19-21`) has deps `[variant]`.

So on **every** cold start the assignment effect runs while `user === null`: the latch is consumed, **no event is emitted**, and the effect never re-runs unless `variant` changes. Concretely:

| Case | Outcome |
|---|---|
| Arm A user (variant never changes A→A) | `paywall_experiment_assigned` **never fires**, ever |
| Arm B user, warm MMKV cache (variant already B) | **never fires** |
| Arm B user, fresh install (fallback A → server B) | fires once as `variant: "B"` — only if auth restored before the flip |

This is deterministic, not a race: `restore()` cannot complete synchronously before the next effect in the same commit.

**AC1 impact:** doc §7.3 tells the founder to "confirm both `paywall_experiment_assigned` and `paywall_experiment_exposed` appear in PostHog's Live Events". Under normal conditions the assignment event will not appear. AC1's assignment half is **not achievable as built**.

**Mutation proof (MP4b):** adding the missing guard (`if (useAuthStore.getState().user?.id === undefined) return;` *before* consuming the latch) leaves the **entire 203-suite / 1784-test mobile suite green** — proving both that F1 is invisible to the test suite and that the fix is non-breaking. `paywall-experiment-events.test.tsx:87` sets a signed-in user in `beforeEach` before every render, so the signed-out-then-signed-in path is never exercised.

### F2 — HIGH — both events can report the anonymous fallback `"A"`; one person can land in both arms

The variant fed to the emitters is not guaranteed to be a *resolved* variant.

- `apps/mobile/src/billing/paywall-queries.ts:34-41` — `initialData: readCachedConfig() ?? DEFAULT_APP_CONFIG`, and `DEFAULT_APP_CONFIG.variant = "A"` (`app-config-queries.ts:47`). The hook can therefore never distinguish "the server said A" from "we have not heard from the server yet".
- `packages/api-client/src/query-client.ts:19-35` — no `staleTime` is configured anywhere, so `staleTime = 0` and **every new observer mount refetches** `["app-config"]`.
- `apps/mobile/src/api/client.ts:13,24` — `getAuthToken: () => useAuthStore.getState().accessToken`, which is `null` throughout auth restore. **The first `/v1/config` request of every cold start is unauthenticated.**
- `apps/api/src/remote-config/remote-config.controller.ts` — the route is `@Public()` + `OptionalJwtAuthGuard`, so `assignPaywallVariant(undefined, "AUTO")` returns `"A"` (`variant-assignment.ts:38-46`). The server answers **"A" for every user** on that first fetch, and `fetchAppConfig` writes it to the MMKV last-known-good cache.
- `apps/mobile/app/paywall.tsx:75-82` — the exposure effect keys on `[variant]` with a ref compare, so it deliberately **re-fires on any variant change while the paywall is mounted**. Opening the paywall mounts a second observer on the stale `["app-config"]` query → authenticated refetch → `A → B` flip mid-view → a **second** `paywall_experiment_exposed` carrying `"B"`.

This refetch is routine, not hypothetical — the codebase already documents it: `apps/mobile/src/config/use-upgrade-state.ts:13-18` ("a post-mount config refetch (e.g. driven by the shared `["app-config"]` cache's other observers — the paywall)").

`paywall_experiment_exposed` is the experiment's declared **custom exposure event and metric denominator** (doc §3, §7.2). Systematically inflating arm A with users who are really arm B, and placing single persons in both arms, biases the success metric (`trial_start` per exposed user per arm) in an undetectable direction.

**Honesty gap:** doc §3 attributes a variant change *only* to "the api's `PAYWALL_VARIANT` env flipped while a client is already running", and §6.5 voids a run only for that reason. The routine anonymous-fetch / fallback-seed path is undisclosed, and §3's phrase "the first time the **resolved** variant is observed" is inaccurate. Per the checker brief, silence here is itself a finding.

**Test blindness:** `paywall-experiment-events.test.tsx:57-60` mocks `../src/billing/paywall-queries` wholesale, so the `initialData` fallback that causes this is never exercised.

Suggested minimal fix for F1+F2 together: emit only once the config query has resolved from an **authenticated** fetch *and* auth status is `signedIn` (e.g. gate on `isFetchedAfterMount`/`isSuccess` plus the auth status), and do not consume the dedupe latch until an event is actually emitted.

### F3 — MEDIUM — the documented PostHog analysis path will likely not work

Doc §7.2 instructs creating a PostHog experiment **on feature-flag key `paywall_copy_ab`**. Nothing in this codebase evaluates a PostHog feature flag: the mobile emitter is a raw HTTP `capture` (`packages/analytics/src/http-transport.ts`, envelope = `api_key/event/distinct_id/properties/timestamp` only), and bucketing is our own server-side FNV-1a (`variant-assignment.ts`), independent of PostHog's hashing. PostHog's Experiments product derives each person's variant from its own flag evaluation (`$feature/<key>` / `$feature_flag_response`), which our events never carry — so its results view will either show no exposures per variant, or split people by a PostHog-side assignment uncorrelated with the arm the user actually saw.

The events themselves are fine and carry `variant`, so the experiment *is* analysable — but only via the path the doc currently lists as an afterthought ("Optionally add a trend broken down by the `variant` property"). Recommendation: make the `variant`-breakdown funnel/trend the **primary** documented analysis, or emit `$feature/paywall_copy_ab` alongside `variant`. Not blocking on its own (founder/console-side, correctable without code), but it should not be discovered mid-run.

### F4 — MEDIUM — the trial CTA interpolates the **intro** price, not the recurring price (pre-existing, now duplicated into a second arm)

`apps/mobile/app/paywall.tsx:285-290` renders `copy.trialCtaWithPrice(monthly.introPriceString)`, and `introPriceString` is `pkg.product.introPrice.priceString` (`apps/mobile/src/billing/purchases.ts:211-212`) — the *introductory-offer* price, i.e. the trial price (typically "$0.00"), **not** the post-trial recurring price (`monthly.priceString`). Both arms can therefore render "Start your 7-day free trial — then $0.00" / "Try it free for 7 days — then $0.00". The committed snapshot makes the nonsense visible: `paywall-snapshot.test.tsx.snap:883` now reads *"Try it free for 7 days — then Free for 7 days"*.

`git show HEAD:apps/mobile/app/paywall.tsx` confirms the same argument pre-dates T107, so this is **not a T107 regression**. But this card is explicitly "copy + **trial framing**", it ships a second arm of exactly this string, and a misleading post-trial price carries App Store 3.1.2 / consumer-law exposure. Recorded so it is not lost; belongs in a follow-up card.

**Answers to the specific questions raised:**

- *Any path where `resolved` flips true with a still-anonymous variant?* Effectively no. `resolved` requires `status === "signedIn"`, and `auth-store.ts:73-78` sets `status` and `accessToken` in the **same atomic `set()`**, so the explicit `refetch()` always carries the token. `refetch()` defaults to `cancelRefetch: true`, so an in-flight anonymous request is superseded rather than reused. `variant` is read from the same shared `["app-config"]` cache entry as the screen's render value, so once `resolved` is true the emitted arm and the rendered copy can never disagree.
- *What if the signed-in refetch FAILS — starve forever, or resolve on stale data?* **It resolves on stale data**, by construction: `fetchAppConfig` catches everything and returns the cached-or-default config (it "never throws", per its own header), so the query always settles successfully and `.then()` always runs. `resolved` therefore cannot be starved for a signed-in user. The residual is that an offline-at-sign-in user may be reported once with a lower-confidence (possibly anonymous `"A"`) variant. **This is disclosed honestly** in both the hook header (`use-resolved-paywall-variant.ts:42-50`) and doc §3's "Residual, disclosed caveat" paragraph, and §8 explicitly lists it under "what these tests do NOT prove". I judge the fail-open choice correct — blocking forever would silently drop exactly the users most likely to be on poor connections — and the disclosure adequate.
- *Can the fix starve assignment permanently for genuinely-anonymous-forever sessions?* Yes, and that is **correct**: no `distinctId` means no event is possible at all (`analytics.ts:26-32`). The doc covers it — §3 states both emitters wait for `"signedIn"` and never emit while `resolved` is false, and §8 states outright that "a cold start with no stored session never emits either event even though the anonymous config answers 'A'". `paywall-experiment-auth-resolution.test.tsx` test 1 pins it.
