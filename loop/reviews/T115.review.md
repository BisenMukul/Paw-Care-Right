## 4. Safety/UX topology — PASS

- **No dismiss affordance.** `apps/mobile/__tests__/update-gate.test.tsx` "the blocking screen offers no dismiss affordance" doesn't just check for absent testIDs — it serializes the rendered tree, regex-extracts *every* `update-gate-*` testID, and asserts the set is exactly `{update-gate-screen, update-gate-cta}`. Pressing the CTA opens the store URL and the gate is still rendered with `protected-child` null.
- **Android hardware back.** No `BackHandler` is registered anywhere in the gate path (the only one in the app is `check/emergency/[checkId].tsx:34`). Structurally, `UpdateGate` returns early *instead of* `children`, so `<Stack>` never mounts — there is no navigator and no route to go back to. Hardware back therefore backgrounds/exits the app; relaunch re-evaluates and blocks again. It cannot reveal authenticated content. Pinned indirectly by the precedence test asserting `router-stack` is null. See finding LOW-2.
- **Renders before any authenticated route.** `apps/mobile/__tests__/upgrade-gate-precedence.test.tsx` imports the **real** `RootLayout` from `../app/_layout` and deliberately does **not** mock `../src/components/update-gate` (comment at :91-92); only `useAppConfig` is stubbed, via a `jest.requireActual` passthrough so `DEFAULT_APP_CONFIG` stays real. Case 3 (permissive config ⇒ `router-stack` renders) proves case 1 is not vacuous. This also documents the **gate > OTA-restart-prompt** precedence structurally, with no coordination code — the right call.
- **Fail-open.** `useAppConfig()` seeds `initialData` from cache-or-default so config is never undefined; `useUpgradeState` additionally applies per-field `?? DEFAULT_APP_CONFIG.X`, whose gate fields are `0.0.0`/`0.0.0`. Missing config, missing fields, unknown OS, or an unparseable installed version all resolve to `"none"`.
- **Mid-session refresh vs T114 deferral — ruling: cannot happen, and that is correct.** The launch snapshot lives in `use-upgrade-state.ts:29`'s lazy `useState` initializer. I verified the remount question the executor did not: `apps/mobile/src/auth/auth-store.ts` sets `"restoring"` **only** as the initial state (line 44) and no transition ever returns to it, so `AppRoot`'s early-return branch fires once at cold launch and `<UpdateGate>` mounts exactly once for the process lifetime. A `/config` refetch mid-session therefore **cannot** raise the blocking screen over an in-progress symptom check, red-flag, or emergency flow. This preserves T080 decision 1 and is the §7-protective direction; a newly-raised server minimum simply takes effect at the next cold launch. No interaction with T114's deferral guard is required.

A future refactor that rendered the gate *inside* the navigator instead of *around* it would silently lose this. Worth a one-line comment or an explicit test in a later OTA task; not blocking.

**LOW-3 — banner has `px-4 pb-2` with no top padding.** Cosmetic only; it sits directly under `BetaBanner` so it is never the top-most element. Deliberate per T114 Finding 6.

**INFO-2 — a raised server minimum takes effect one launch late.** `useAppConfig`'s `initialData` is cache-or-default, so the launch snapshot uses the *previously fetched* config. Intentional stale-while-revalidate behaviour, and the safe direction. Worth noting in the release runbook alongside the founder delta.
