## 6. Findings (none blocking)

**F1 — inaccurate supporting citation in the exemption comment (minor, fix in a follow-up).** `apps/web/src/strings-detector-lint.spec.ts:81-84,102-104` states the acceptable-use clause "is separately byte-pinned verbatim by `legal-content.spec.ts`". It is not. `apps/web/src/legal/legal-content.spec.ts` byte-pins only `not-veterinary-care` (:180) and `no-medication-guidance` (:187); for acceptable-use it asserts only `expect(body.toLowerCase()).toContain("cruelty")` (:196). The byte-pin the comment describes is in fact supplied by this new spec's own stale-entry check (proven by mutation B). The **§-citation itself ("CLAUDE §7 rule 6 / PRODUCT_SPEC §5") is sound**, and the safety property holds — only the ancillary justification sentence overstates an existing test.

**F2 — allowlist matching is normalized `CODE: excerpt`, not exact leaf value (advisory hardening).** `ALLOWLISTED_NORMALIZED_FINDINGS` is keyed on `stripPath(finding)` = `"<CODE>: <match excerpt>"`, so a **newly added** leaf whose detector `match[0]` is byte-identical to an exempted excerpt would be silently exempted. Demonstrated: a contrived leaf `"For sedation, do-it-yourself grooming guides, ask a vet."` collides with the exempted `HARM_ENABLING: sedation, do-it-yourself` key and is not reported. Why this is not a fail: (a) the brief's operational criterion — mutate the exempted string ⇒ lint FAILS — is met (mutation B); (b) realistically harmful copy is still caught, proven in the same run (`"Here is how to do sedation, do-it-yourself, at home."` produced two unshadowed findings); (c) the exempted excerpts are distinctive 24–40-char phrases, not generic tokens. Recommended one-line hardening for T098: filter by leaf (`EXEMPT_VALUES.has(leaf.value)`) instead of by normalized finding.

**F3 — leaf-count reporting discrepancy.** The executor reported 654 mobile leaves; the measured value is **662** (web 166 is exact). The delta is the `ENUM_OVERRIDES` expansion (2 enum-keyed function leaves → 10 leaves). Journal the corrected number.

**F4 — `ENUM_OVERRIDES` key lists are hand-maintained** (`strings-detector-lint.test.ts:35-38`) with no completeness assertion against `ReminderType` / `ScheduleFrequency`. Today they are exactly complete (verified against `NOTIFICATION_TYPE_LABELS`, `apps/mobile/src/strings.ts:29-37`, and `SCHEDULE_FREQ_LABELS`, :44-48), but a future enum member's label would silently go unscanned. Cheap follow-up: assert the override keys equal `Object.keys` of the corresponding label map.

**F5 — `JSX_RENDER_PATTERN` (`/<VetDisclaimer\s+\/>/`) is deliberately space-required.** It would miss a prop-bearing (`<VetDisclaimer testID=… />`) or space-less (`<VetDisclaimer/>`) render. On the *required* screens this fails closed (the required-screen test goes red), so the safety direction is correct; on non-pinned files it could hide an extra render, which is benign. Documented, not blocking. The spec's own control test (:87-91) proves the pattern rejects prose mentions, which is the property it needs.

**F6 — §1a follow-up (correctly deferred by the plan):** `apps/api/src/chat/chat.service.ts:93,128` hardcodes the display name. Out of scope for T097 per plan §"Out of scope"; carry to the T102/C3 naming pass.

## 7. The api "flake" (duty 6) — documentation for T098

- **T097 did not cause it and cannot have:** `git status --porcelain apps/api` is empty; no T097 file is imported by the api workspace.
- **Not reproduced here:** I ran the api suite twice (once inside the forced full `turbo run test`, once standalone) — **107 suites / 1093 tests passed both times, EXIT 0**. The executor's reported `billing-webhook-fuzz` subscription-row drift (1→4→8) did not appear in either run.
- **Mechanism to investigate in T098** (from reading `apps/api/test/billing-webhook-fuzz.e2e-spec.ts`): `countRows()` (:63-68) takes **global, unscoped** counts — `prisma.processedWebhookEvent.count()` and `prisma.subscription.count()` — and three tests assert `expect(after).toEqual(before)` (:97, :109, :132, :149). The suite's `afterAll` only cleans `processedWebhookEvent` rows for its own `eventIds` (:49) and never deletes `subscription` rows. Any *other* suite that creates a subscription row while these tests hold a `before`/`after` window shifts the global count, so the assertion is order/concurrency-dependent rather than deterministic — consistent with the reported 1→4→8 accumulation. Fix direction for T098: scope `countRows()` to the fixture's own `rcAppUserId`/`eventId` set (or assert deltas on a filtered `where`), rather than global table counts.
