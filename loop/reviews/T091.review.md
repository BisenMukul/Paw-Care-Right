## F1 — HIGH / **blocking**: a reachable class of account is scheduled for deletion, told so, and then *never erased* — permanently and silently

### The defect

`AccountErasureService.eraseFullHousehold` collects the checks to delete **by pet**, not by author:

`apps/api/src/me/account-erasure.service.ts:98-102`
```ts
const checks = await this.prisma.symptomCheck.findMany({
  where: { petId: { in: petIds } },      // <-- petIds = pets of the user's CURRENT household only
  select: { id: true },
});
```

But `SymptomCheck.createdBy` is `onDelete: Restrict` (`apps/api/prisma/schema.prisma:234`), and the invariant
the plan leans on ("every user has exactly one Membership at all times") does **not** mean a user's membership
never *moves*. `HouseholdsService.leaveHousehold` (`apps/api/src/households/households.service.ts:184-207`,
shipped at `POST /households/leave`, `households.controller.ts:71-78`) creates a **new solo household** for the
leaver and drops the old membership — leaving behind every `SymptomCheck` they authored on the old household's
pets, still carrying `createdById = <their id>`.

So for that user the erasure resolves to `FULL_HOUSEHOLD` (OWNER, 0 siblings), collects `checkIds = []`,
and `tx.user.delete` then trips the `Restrict` FK.

### Empirical proof (checker probe P1, zero repo mutation)

I replicated `leaveHousehold`'s exact transaction and then `eraseFullHousehold`'s exact query set against the
real Postgres (`scratchpad/probe1.js`):

```
resolved: role=OWNER siblings=0 -> mode=FULL_HOUSEHOLD
collected: petIds=0 checkIds=0 threadIds=0
BUT the member still owns 1 check(s) via createdById (id e3534b2b-…)

>>> ERASURE OUTCOME: THREW P2003: Foreign key constraint violated on the constraint: `SymptomCheck_createdById_fkey`
>>> member row still present: true
```

### Why this is mandatory-FAIL, not a nit

1. **Reachability is a shipped headline path**, not a corner case: premium household invites you → you join →
   you run a symptom check (the product's core action) → you leave → you delete your account. Each step is a
   shipped feature.
2. **It fails silently and forever.** `AccountDeletionService.sweep` catches per-user erasure failures and
   only `logger.warn`s (`account-deletion.service.ts:75-79`) — no Sentry, no alert. The user's row still
   matches `deletionScheduledAt: { lte: now }`, so **every future daily sweep repeats the same failure**. The
   account is never erased.
3. **The user is left in a half-dead state**: refresh tokens revoked, devices deleted, `analyticsOptOut` forced
   true, `deletionScheduledAt` in the past — but the account, their pets/household, and their authored checks
   all persist indefinitely. `DELETE /me` returned 200 and the confirmation copy promised erasure.
4. **It makes the shipped privacy policy false for this user class** — which is a second mandatory-FAIL trigger.
   `apps/web/src/strings.ts:195` now states: *"You can delete your account yourself at any time in Settings —
   doing so schedules erasure of your account, your pets, your symptom checks … after a 30-day grace window."*
   For this class it never happens. GDPR Art.17 erasure silently fails.
5. **Bitterly ironic detail:** the D1c 409 copy (`apps/mobile/src/strings.ts` `privacy.deleteConflict`) tells
   co-owners to *"Ask the other members to leave (Settings → Family → Leave household)"* — the precise action
   that puts those members into the un-erasable state.

### Prescription (one clause + one test)

In `eraseFullHousehold`, collect the user's authored rows as well as the household's:

```ts
const checks = await this.prisma.symptomCheck.findMany({
  where: { OR: [{ petId: { in: petIds } }, { createdById: userId }] },
  select: { id: true },
});
```

Do the same for the `chatThread` collection at `:104-108` — not for FK reasons (`ChatThread.createdBy` is
`Cascade`) but so the D3 `AiAuditLog` rows keyed to those orphaned threads are actually collected and erased
rather than left to age out.

Add a regression test that is RED before the fix: seed a MEMBER in a shared household, create a check on the
owner's pet, call `POST /households/leave`, then `DELETE /me` + force the sweep, and assert `user.count === 0`
and the orphaned check is gone. (My probe script is a ready-made skeleton.)

## D3 / R4 — explicit adjudication: **hard-delete STANDS**

The plan flagged this as the decision most worth challenging. I rule for the executor. Reasons, weighed:

1. **Art.17 is a right with a one-month clock; audit retention here is a discretionary control.** When they
   conflict on a model that carries *no content*, erasure wins. `AiAuditLog` rows are ids + `promptVersion` +
   `modelId` + `detectorFlags` (closed code set, T090-proven content-free) + costs/status/latency. Tombstoning
   would preserve, at most, "some user ran some check at some time" — near-zero abuse-investigation value once
   the ids are nulled, which is exactly what a tombstone would have to do to be lawful.
2. **The "append-only" objection does not survive inspection.** T090's append-only property means *no UPDATE
   path exists*. Tombstoning would introduce the model's first-ever UPDATE path **and** break its documented
   exactly-one-of-`checkId`/`threadId` invariant. A bulk DELETE path, by contrast, already exists and is
   exercised daily (`AiAuditRetentionService`). Hard-delete is the *less* invasive change to T090's design.
3. **The forgone value is bounded to ≤90 days** by that same retention worker. An abuser who "misuses then
   deletes" gains at most the residue of a window that was already closing, and T090's alert-only anomaly
   counters + Sentry path are unaffected.
4. **The shipped policy is consistent with it.** The retention paragraph now promises erasure of the user's
   data with only a legal/security/billing carve-out; a content-free 90-day operational log is squarely inside
   that carve-out either way, so neither choice makes the policy false.

Implementation is correct: ids are collected **before** the referenced rows vanish (no FK exists — ids are the
only link), and the ordering is pinned by an index-comparison test, not a comment
(`account-erasure.service.spec.ts:105-121`). Both `checkId` and `threadId` legs are covered.

Caveat folded into F1: on the orphaned-check path the audit rows are also missed. The F1 fix resolves it.

1. **F1 (HIGH, blocking)** — `AccountErasureService.eraseFullHousehold` collects `SymptomCheck`s by `petId` of

2. Non-blocking: F2 (no schema-drift completeness guard — the systemic version of F1), F3–F7 as listed above.

All gates were green and all restores byte-verified; F1 is the sole blocking item, and it is a narrow fix-forward.
