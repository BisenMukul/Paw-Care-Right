## 9. Findings

**Finding 1 — MEDIUM — the staged-rollout percentage is unpinned on the command that actually runs.**
Evidence: mutation M3 changed `.github/workflows/ci.yml:435` from `--percent 10` to `--percent 100` and the entire `ota-publish` suite stayed GREEN (28/28). Grep confirms no test asserts `--percent 10` anywhere; the only `10%` a test touches is the step NAME, via `ota-publish-ci.test.ts:402` `block.indexOf("- name: Constrain rollout to 10%")` (used for ordering only). `:477` pins `--percent 50` and `:478` pins `--percent 100|--action end`, but those are the promotion strings in the summary text.
Why it is not HIGH: the shipped command IS `--percent 10`, exactly as the card requires; no acceptance criterion mentions the percentage, and the plan's own AC→proof map never promised this pin, so this is a gap in future-regression cover rather than a defect in what ships. The blast radius if it ever regressed is real though — a silent 100% first-wave production rollout defeats the whole point of §6's staged ladder.
Suggested fix (one line, for T117/T118): `expect(extractStepRunBody(ciYmlSource, "Constrain rollout to 10%")!.join("\n")).toContain("--percent 10 ")`.

**Finding 2 — LOW — `deriveUpdateMessage` rejects a subject that is ALREADY in the required convention form.**
Evidence: `node scripts/lint-update-message.js --from-commit "T116: already in convention form"` → exit 1, `no Txxx/Mx task or milestone id found in the commit subject`. Cause: the conventional-commit strip at `scripts/lint-update-message.js:127`, `/^\w+(\([^)]*\))?!?:\s*/`, matches `T116: ` because `\w+` happily consumes `T116` — so the id token is eaten before the id search at :130. (`--from-commit "T116 plan"`, without the colon, works fine and yields `T116: plan`.)
Impact: a push to main whose subject is literally `Txxx: summary` reddens the preview job. Not hit in practice — CLAUDE §8 mandates `type(scope): TASK-ID description`, and I replayed every commit subject in the available history with zero unexpected failures. The failure is loud and fail-safe (it never publishes a wrong message), so this is robustness, not a defect.

**Finding 3 — LOW — two `console.log` calls introduced, a CLAUDE §8 forbidden pattern.**
Evidence: `.github/workflows/ci.yml:445` and `:447`, inside the `Rollout playbook` step's inline `node -e`. These are the repo's ONLY `console.log` occurrences under `.github/` or `scripts/` (baseline `git show f520b4d:.github/workflows/ci.yml` has none), and `packages/config/eslint.config.mjs:36` sets `no-console: "error"` repo-wide. No lint rule reaches YAML, so the gates cannot catch it. Notably both new scripts correctly use `process.stdout.write`/`process.stderr.write`, so the house style was known. Fix: `process.stdout.write(x + "\n")`. Non-blocking — CI shell glue, no Nest `Logger` available, zero runtime effect on the product.

**Finding 4 — LOW — `extractStepRunOneLiner` is partly vacuous.**
`ota-publish-ci.test.ts:216`'s `/\n\s*run:\s*(?!\|)(.+)$/m` is defeated by backtracking `\s*` to zero width, so for a `run: |` block step it returns the string `"|"` rather than `null`. The injection test's one-liner branch therefore asserts nothing useful for block steps. Harmless: the block branch (`extractStepRunBody`) performs the real check, and I independently verified via a real YAML parser that ZERO run bodies in either job contain `${{`.

**Finding 5 — LOW — `PIPING_STEP_NAMES` is a hardcoded one-element list** (`ota-publish-ci.test.ts:494`), so a future piping publish step is not automatically covered, unlike the set-derived `needs:` pins. The plan's wording implied per-step coverage. The one step that pipes today is covered, and `Rollout playbook` carries pipefail anyway.
