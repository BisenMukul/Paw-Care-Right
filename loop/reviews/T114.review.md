## 9. Rulings on the plan's D1–D5

- **D1 — `criticalOtaVersion` compared to the CURRENT `updateId`: SUPPORTED.** §3's "belt-and-braces signal for clients that fetched before the flag" is best served by comparing against what the client is *running*, not the fetched manifest id; the rejected alternative would miss precisely the case the doc names. Critically, the comparison is evaluated only **after** a successful `fetchUpdateAsync` (`update-controller.ts:183-196`), so a prompt can never appear without a downloaded bundle ⇒ no reload loop. Worst realistic mis-fire (server names `u-9` while the offered bundle is `u-8`, e.g. after a §6 `update:republish`) prompts a restart into a non-critical bundle — harmless, outside any protected flow, and it never suppresses a real critical. Accepted. Sub-note (informational): the cold-start cycle reads `criticalOtaVersion` from `useAppConfig()` at mount, which on a fresh install is `DEFAULT_APP_CONFIG`'s `null` because the network `/config` typically lands later, so the mirror path realistically fires from the *second* launch onward. ## Findings

**1. (MEDIUM — carry-forward, not T114-introduced) `.strict()` client `/config` schema breaks OLD clients when the API adds a field — contradicts OTA_UPDATES §5.4.**
`appConfigResponseSchema` is `.strict()` (`packages/types/src/config.ts:36-46`) and the mobile client parses `/config` with it (`app-config-queries.ts:47-60`). Once the API ships `criticalOtaVersion`, a client running a **pre-T114 bundle** hits an unrecognized-key error, throws, and falls back to cache/`DEFAULT_APP_CONFIG` — silently losing server config delivery: the `features` kill switches, `minSupportedVersion` and the paywall variant. §6's rollback playbook calls the kill switches "the instant mitigation while OTA rollback propagates", so the population that most needs them (not-yet-updated clients) is exactly the population that loses them. This contradicts §5.4 ("`/config` responses are backward-compatible **by construction** (Zod schema with defaults on the client)") and defeats §5.1's additive-only intent. Mitigating: the same pattern was established in T079/T106 (not introduced here), it is disclosed as D4, no clients are in the wild pre-beta, §5.3 mandates backend-first deploys, and the failure direction is fail-open/safe for §5. **Recommend** a dedicated fix before the first production OTA (T115–T118): make the client-side parse tolerant (non-strict passthrough + per-field defaults) while keeping the API response strict.

**2. (HIGH) The entire rendering layer of T114 is untested — no gate detects either a dead feature or a prompt that ignores the deferral guard.**
`apps/mobile/src/components/update-ready-prompt.tsx` has **no test file**, breaking the repo's own convention for exactly this class of root-mounted component (`beta-banner.test.tsx`, `offline-banner.test.tsx`, `update-gate.test.tsx`, `upsell-sheet.test.tsx`, `billing-issue-banner.test.tsx` all exist), and nothing asserts the component is mounted at `app/_layout.tsx:124` (the only root-layout test now mocks it to `() => null`). Proven by mutation, not inferred:
- **M4**: deleting `if (!promptVisible) return null;` — so the "Update ready / Restart now" banner renders unconditionally, *including over an in-progress symptom check, the Emergency interstitial, checkout and onboarding* — leaves the full mobile suite **green** (194/194, 1635/1635, 19/19 snapshots).
- **M5b**: deleting both `<UpdateReadyPrompt />` and its import from `_layout.tsx` — the whole feature dead in-app — leaves `test` **green (1635/1635)**, `lint` **EXIT=0** and `typecheck` **EXIT=0**.
The shipped behavior is correct (I verified the gate expression and the hook-level tests; M1/M2 show the hook logic is well pinned), so this is a coverage defect, not a live safety bug. But CLAUDE §8 requires "component/snapshot for critical UI", and this is the card's only UI *and* the render-time enforcement point of §3's hard rule; a one-line regression in either file would ship silently with every gate green. Fix is confined to test files: (a) add `apps/mobile/__tests__/update-ready-prompt.test.tsx` — renders `null` when not visible; renders `testID="update-ready-prompt"` with a critical loader on `["(tabs)"]`; renders nothing with the same loader on `["check","emergency","[checkId]"]`; pressing "Restart now" calls `reloadAsync` once outside a protected flow; (b) in `root-layout.test.tsx` change the passthrough to a `testID`-bearing stub and assert it mounts once inside `update-gate`.
