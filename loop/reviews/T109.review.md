## 4. Safety topology — "never after emergencies"

Emergency-surface census (the question is whether any emergency can happen *without* being
recorded):

- Only two screens render emergency content: `app/check/emergency/[checkId].tsx` and
  `app/check/result/[checkId].tsx`. Chat escalates through `NudgeCard` into the existing
  `/check/[category]` intake and renders no emergency UI of its own
  (`src/components/chat/nudge-card.tsx:12-18`). No other hotline/`EMERGENCY_NOW` surface exists
  (`resolveRegionHotline` has exactly one caller).
- **(a) red-flag result reached without the interstitial** (deep link / history): covered — the
  result screen records on load, `result/[checkId].tsx:50-58`, and the Done gate additionally
  requires `!hasRedFlag` (line 106). The effect commits at first render, strictly before any
  user press, so recording always precedes any possible request.
- **(b) `EMERGENCY_NOW`/`VET_24H` without a red flag**: covered in code by the same effect
  (line 55). This is load-bearing: interstitial routing is red-flag-only
  (`src/checks/use-check-submission.ts:70-71`), so an AI-only emergency verdict is recorded
  **exclusively** by that clause. It is untested — Finding 1.
- **(c) cross-account-on-device**: the gate is device-scoped (MMKV, no account key), so a family
  member's emergency yesterday *does* suppress today's prompt. That is the over-suppressing (safe)
  direction. Honest in `loop/plans/T109.plan.md §9`; not stated in the code comments — Finding 4.
- **(d) suppressed decision reaching the native call via a race**: impossible.
  `request-review.ts:28-33` reads state and returns on any non-`"request"` decision *before* the
  loader is ever constructed or invoked; the whole path to `writeLastPromptedAt` (line 35) is
  synchronous, so two interleaved calls cannot both stamp. AC2.7 pins "suppressed ⇒ native
  untouched and no stamp".

**Ruling: the "never after emergencies" behaviour is correct as written.** The defect surface is
regression protection, not behaviour.

## 5. Numbered findings

### Finding 1 — MEDIUM · The tier-based emergency recording is completely untested
`app/check/result/[checkId].tsx:55` records an emergency for `urgency === "EMERGENCY_NOW" ||
urgency === "VET_24H"`. Mutation **M2** deleted that clause (leaving only the red-flag check) and
the **entire mobile suite stayed green: 208 suites / 1818 tests passed**. Because the emergency
interstitial is only reached when `check.redFlag !== undefined`
(`src/checks/use-check-submission.ts:70-71`), this clause is the *only* thing that records an
AI-determined emergency — i.e. the highest-value half of "never after emergencies" has zero
regression protection. `review-prompt-wiring.test.tsx:85-95` already renders `EMERGENCY_NOW` and
`VET_24H` but asserts only `maybeRequestReview` was not called; adding
`expect(mockRecordEmergencySeen).toHaveBeenCalled()` to that `it.each` would close the gap in one
line. Behaviour is correct — this is a test gap, not a defect.

### Finding 2 — MEDIUM · The reminder-streak call site (one of the card's two triggers) has no wiring test
Mutation **M5** deleted the whole streak block from `app/(tabs)/care.tsx:81-86`
(`recordReminderEvent("completed")` + the `maybeRequestReview("reminder-streak")` call) and the
full mobile suite stayed green: **208 suites / 1818 tests passed**. The executor wrote a wiring
suite for the REASSURE trigger and the emergency recorders (AC3.1-3.4) but none for the care tab,
so the card's second mandated positive moment — plus the snooze reset and the MISSED-reset effect
— is asserted nowhere. The pure logic behind it (`nextStreak`, `hasMissedEntry`) *is* covered;
only the wiring is unproven. The plan's own AC3 table omits it, so this is a plan gap the executor
inherited rather than a plan violation.

### Finding 3 — MEDIUM · No import-time pin on the lazy require (`store-review.ts`), unlike the T113-F3 precedent
`src/review/store-review.ts:38-46` correctly uses the `update-controller.ts` idiom (narrow local
`StoreReviewApi`, no `typeof import(...)`, `require` inside try/catch). But mutation **M4**
replaced it with a top-level `import * as EagerStoreReview from "expo-store-review"` and the full
suite stayed green (**208 / 1818**) — jest resolves the now-installed package, so nothing catches
the regression, whereas on-device/Expo-Go (or with the plan's install-skip fallback in force) a
top-level import crashes at module load, and this module is loaded transitively from `care.tsx`
and the result screen. The repo already has the exact antidote for this class:
`__tests__/ota-lazy-require.test.ts` (`jest.mock("expo-updates", () => { throw ... })` then assert
the module still imports). A ~10-line analogue for `expo-store-review` would close it. Honest gap
note as instructed: **nothing currently catches an eager require.**

### Finding 4 — LOW · `review-state.ts` header overclaims its guarantees
`src/review/review-state.ts:9-10` states "Every exported function is internally guarded so it can
never throw into a caller". There is no `try/catch` in any exported function; the only guard is
inside `createSafeStorage`'s *construction* (`src/storage/safe-storage.ts`), so a native MMKV
handle that throws on `getString`/`set` would propagate into `care.tsx`'s effect and
`handleComplete`. This is idiom-identical to `src/ota/update-throttle.ts:30-43`, so the actual
risk is unchanged from the accepted repo baseline — but the comment is stronger than the code,
which matters precisely because a future author may lean on it when adding a call site inside a
care flow.

### Finding 5 — LOW · R5 residual: the care-tab path has an await window before it fires
See the explicit ruling in §6.

### Finding 6 — INFO · Re-viewing a historical emergency check re-stamps `lastEmergencyAt`
The result-screen effect runs on every mount, so opening a six-month-old emergency check from
history extends the 30-day suppression from *now*. Over-suppression = the safe direction; noted so
it is a conscious property rather than a surprise.

### Finding 7 — INFO · A `MISSED` entry in the loaded agenda window resets the streak on every `data` change
`care.tsx:79-84` re-runs on each `data` identity change, so while any `MISSED` occurrence sits in
the today→+30d window the streak is pinned at 0 and the streak trigger is effectively unreachable
that day. Consistent with plan R2's "consecutive" semantics; flagged for the founder because it
lowers the observed trigger rate further than the 60-day throttle alone implies.

## 6. R5 adjudication — §7 adequacy of "no deferral guard" · **RULING: ADEQUATE**

No import of `src/ota/update-deferral.ts` exists in the diff (verified). Safety therefore rests on
call-site placement. Assessment of each site:

1. `result/[checkId].tsx:99-108` — `router.replace("/(tabs)/timeline")` runs **first**, then the
   request fires **synchronously** on the user's own Done tap, gated to non-fallback,
   non-red-flag, REASSURE. No await, so no window in which the user can be elsewhere. Cannot
   interpose on intake, waiting, the emergency interstitial, or a safe fallback.
2. `emergency/[checkId].tsx:35-38` — records only; it can never request. Correct polarity.
3. `care.tsx:74-92` — fires after `await completeMutation.mutateAsync(...)`. This is the one real
   residual: if the user navigates from the care tab into `/check/[category]` while the mutation
   is in flight, the OS sheet could surface over a `DEFERRED_ROOT_SEGMENTS` route.

Ruling on (3): **LOW, not HIGH.** §7 forbids delaying emergency care, burying the disclaimer,
suppressing the emergency interstitial, or gating safety content. An OS review sheet over a
*pre-submission intake form* does none of these: no AI content, disclaimer, or emergency
interstitial is delayed or hidden, and the sheet is user-dismissable in one tap. No call site can
fire during or after an emergency surface (§4 above), which is the §7-relevant constraint. I
therefore do not rule any call site as firing mid-§7-flow. The mitigation the plan promised — a
structural-safety comment at each site — is present and accurate
(`result/[checkId].tsx:100-105`, `emergency/[checkId].tsx:35-37`, `care.tsx:74-79, 82-86`).
Recommendation (non-blocking): if a future call site is added, or if the care path is ever moved
to a longer-running await, import the segment guard rather than re-arguing placement.
