# Plan — T092: Store privacy declarations prep

## Objective (from card)
Write `docs/store-privacy.md`: Apple privacy nutrition labels + Play Data Safety answers **derived from the code that actually runs** — a data-type → purpose → shared? → retention table where every row cites a real code anchor, plus a grep-verified appendix of what PostHog, Sentry and RevenueCat actually receive. Doc-only card, plus one small drift-guard spec (D5) so the appendix cannot silently rot.

**This is a documentation card. No product code, no config, no dependency, no copy change.** Two files exist in the file list and nothing else may be touched.

---

## Decisions the planner made (scrutinise these — counter-arguments in "Risks")

- **D1 — Code is the only source of truth; the shipped policy is a *cross-check*, not an input.** Where `apps/web/src/strings.ts` (T086 privacy policy) and the code disagree, the doc records the code answer **and** logs the discrepancy in a dedicated section (§8 "Discrepancies found against the shipped policy") with a `LEGAL-REVIEW (C3)` marker. The doc does **not** edit the policy (that would be a copy change outside this card). Two discrepancies are already known and MUST be verified then recorded (see step 4): (i) the policy says we collect "your name", but `User` (`apps/api/prisma/schema.prisma:66-97`) has **no name column** — email/appleSub/googleSub/locale/region only; (ii) the policy claims EXIF/location metadata "is stripped from your images before upload", while the only client-side image code is a resize + JPEG re-encode (`apps/mobile/src/pets/compress-image.ts:28-43`) — re-encoding *does* drop EXIF in practice, but there is no explicit strip step and no test pinning it. Both are recorded as findings, not fixed here.
- **D2 — Pet health data is declared under Apple's "Other Data", with the over-declaration alternative documented and flagged, not silently chosen.** Apple's "Health & Fitness → Health" definition is scoped to *the user's own* health/medical data (HealthKit/Clinical Health Records/health research/"user-provided health or medical data" about the person). Symptom intake, triage results, health-log entries and med records here describe an **animal**, not the user. The doc therefore proposes **"Other Data"** (linked to user, purpose = App Functionality, not used for tracking) as the provisional answer, and immediately below it prints a labelled block: the alternative mapping ("Health & Fitness → Health", i.e. over-declaring), the argument for each, and a `LEGAL-REVIEW (C3)` marker saying **counsel decides, the loop does not**. Rationale for the provisional default: it is the reading Apple's own text supports; the doc's job is to surface the ambiguity honestly, and over-declaring in a machine-read label carries its own review consequences (Health-category expectations, HealthKit questions) that counsel should weigh. Neither option changes how the data is protected in product.
- **D3 — "Shared" is answered per each store's own definition, and every recipient is listed either way.** Apple counts disclosure to a service provider as *collection*, not *tracking*; Google's Data Safety counts transfer to a processor acting on our instructions as **not** "shared". So the inventory table's `Shared?` column always reads `<store answer> — recipients: <list>` (e.g. `No (processors) — recipients: Ollama Cloud, Gemini, S3`), so the honest recipient list is visible regardless of which store word is used. The processor-vs-third-party status of the **AI providers** is the one that can flip the Play answer to "shared"; that gets a `LEGAL-REVIEW (C3)` marker (their terms, not our code, decide it).
- **D4 — Absence claims must name their guard.** Any "not collected"/"never sent" row in the doc must cite the mechanism that makes it true — e.g. `scrubSentryEvent`'s structural `request` allowlist (`packages/analytics/src/sentry/scrub.ts:139-163`), the wholesale breadcrumb `message` drop + `console`-category drop (`scrub.ts:171-210`), `sendDefaultPii: false` + pinned `beforeSend`/`beforeBreadcrumb` (`sentry/options.ts:44-59`), the typed-event-map compile gate (`packages/analytics/src/events.ts:16-33`), `AnalyticsService.captureForUser`'s fail-closed consent read (`apps/api/src/analytics/analytics.service.ts:50-80`), the client consent gate (`apps/mobile/src/analytics/analytics.ts:13-19`). A bare "we don't collect X" with no anchor is a defect.
- **D5 — Ship the drift-guard spec (`packages/analytics/src/store-privacy-doc.spec.ts`).** The card is doc-only and requires no test, but its acceptance criterion is literally *"cross-checked list matches PostHog/Sentry/RC data actually sent"* — a claim that decays the moment someone adds an event property. A ~60-line spec that (a) parses `AnalyticsEventMap` out of `events.ts` and asserts set-equality with the doc's appendix table (event names **and** their property names, both directions), and (b) asserts every code anchor cited in the doc resolves to a file that exists on disk, converts a one-off manual check into a permanent one for near-zero cost and zero new deps. It adds no runtime code and touches no product file. **Why it lives in `packages/analytics`:** that package owns both the event map and the Sentry scrubbers, so the guard sits next to the thing it guards. **Why source-text parsing rather than a runtime list:** `AnalyticsEventMap` is a TS `interface` (compile-time only); exporting a runtime array of event names would be a product-code change this card does not authorise.
- **D6 — Provisional status is stated at the top.** Bundle ids and the store name are provisional until C3/T102 (CLAUDE §1a); the doc's header says so and uses `com.pawcareright.app` / `Paw Care Right +` exactly as CLAUDE §1a fixes them.

```markdown

| Event | Properties sent | Emitted from |
|---|---|---|

```

(The rows above are the *format*, not a licence to copy them unverified — Phase 1 step 1 produces the authoritative content. Optional properties in the interface, e.g. `paywall_view.householdId?`, are listed without the `?`.)

**Parsing contract for `store-privacy-doc.spec.ts`** (pure string work, `node:fs` + `node:path` only, no new deps):
- Source side: read `./events.ts`; take the block between the line `export interface AnalyticsEventMap {` and the next line that is exactly `}`; a top-level event is a line matching `/^ {2}(\w+): \{$/`; its properties are the following lines matching `/^ {4}(\w+)\??:/` until the line `  };`.
- Doc side: read the text between the `BEGIN:posthog-events` / `END:posthog-events` comments; skip the header and separator rows; for each `|`-delimited row take column 1's single backticked token as the event name and every backticked token in column 2 as its properties.
- Both parses must be asserted non-empty before any comparison (this is what makes M1–M3 real).
- Anchor extraction: match backticked tokens against `/^(apps|packages|docs)\/[\w./-]+\.(ts|tsx|prisma|md)(:\d+(-\d+)?)?$/`, strip the `:line` suffix, dedupe, assert non-empty, then `fs.existsSync(path.resolve(repoRoot, p))`.
- `repoRoot = path.resolve(__dirname, "../../..")`.
- No `any`, no `@ts-ignore`, no `console.log`; use `describe`/`it`/`expect` in the existing style of `packages/analytics/src/*.spec.ts`.

**Doc conventions:** `LEGAL-REVIEW (C3)` is the literal marker token (matches the T086 `LEGAL-REVIEW` convention in `apps/web/src/legal`). Display name `Paw Care Right +`, identifiers `com.pawcareright.app` / `pawcareright` (CLAUDE §1a). Anchors are written as backticked `path:line` or `path:line-line`.

Accepted anyway because the card's acceptance criterion is a *correspondence* claim between doc and code, which is precisely what decays silently and precisely what a test can hold. Costs: ~60 lines, no deps, no runtime code. - **R4 (D5 — source-text parsing is brittle).** The parser depends on house formatting in `events.ts` (2-space indent, one key per line).
