## 1. Design decisions (each is a decision the CHECKER should scrutinize; rationale + the evidence I checked)

### D1 — Shake detection: **NOT implemented via a new native dependency in this card.**
Evidence: `apps/mobile/package.json` contains **no** `expo-sensors`, no `react-native-shake`, no accelerometer access of any kind. React Native core exposes device-shake only to its dev menu (native side); `DeviceEventEmitter` has no public production shake event; `PanResponder`/Reanimated cannot read device motion. **There is no way to detect a shake with the deps in tree.**

Decision: ship the feature with the **beta-banner CTA + a Settings row as the primary, always-available entry points**, and land a swappable detector seam `apps/mobile/src/feedback/shake-detector.ts` exporting `subscribeToShake(onShake): () => void`, whose implementation in this card returns a no-op unsubscribe and documents the gap in its header comment. `app/_layout.tsx` wires it via a `useShakeToReport()` hook so enabling shake later is a one-file change.

Why not just add `expo-sensors` (~57.x, first-party Expo SDK module, actively maintained, huge adoption — it *would* satisfy §2.7 on merit):
1. It is a **native module**. Under T113's `runtimeVersion: { policy: 'fingerprint' }` (docs/OTA_UPDATES §1), adding it changes the native fingerprint → the internal TestFlight/Play builds produced by T101 **cannot receive this feature over OTA**; a full rebuild + re-submission is required. Paying that during C3 beta distribution for an S card's convenience entry point is a bad trade.
2. Install requires network through the agent proxy; a failed/partial `pnpm add` leaves a lockfile referencing an unfetchable package and breaks `pnpm i` — a CLAUDE §5 P0 breakage — for a non-essential input path.
3. §2.7 requires a journal justification line, and the executor is barred from writing `loop/journal.md`.

**This is a knowing partial implementation of the card's "Shake-to-report" wording and must be adjudicated by the CHECKER, not silently accepted.** If the checker rules the dep must land, the exact justification line for the orchestrator to journal is:

> `T104 dep: expo-sensors@~57.0.x — first-party Expo SDK 57 module (Accelerometer), actively maintained, required for shake-to-report; NOTE it changes the native fingerprint (OTA_UPDATES §1) so T101's beta builds need a rebuild.`

### D2 — Screenshot: **no auto-capture; user-attached image via the existing picker.**
Evidence: no `react-native-view-shot`, no `captureRef`, no `expo-screen-capture` in tree; `expo-image-picker@~57.0.4` and `expo-image-manipulator@~57.0.4` ARE in tree and already used (`src/pets/compress-image.ts`, `src/checks/photo-upload-machine.ts`). Decision: the feedback screen offers "Attach an image" → `expo-image-picker` → compressed through the **existing** `compressImage` helper → presigned PUT to S3 → the returned key is submitted with the report. Same trade-off shape as D1 (auto-capture needs a native dep + fingerprint change); the gap is documented in the screen's header comment. Screenshot attach is user-initiated per-attachment, so it is inherently consented; the separate consent toggle (D3) governs **logs** only, which is what the AC actually tests.

### D3 — Logs: a **closed-code ring buffer**, and consent is enforced **server-side**.
Evidence: mobile has no log buffer and no logger; the only error sinks are `captureError` (`src/observability/sentry.ts`), `src/startup-guard.ts`, `src/error-boundary.tsx`. Decision: add `apps/mobile/src/observability/log-buffer.ts` — a 50-entry in-memory ring of `{ at: string; level: "error" | "warn"; code: LogEventCode; errorName?: string }` where `LogEventCode` is a **closed string union** (`"startup_fatal" | "startup_nonfatal" | "render_error" | "captured_error"`) and `errorName` is accepted only if it matches `/^[A-Za-z0-9_$]{1,64}$/` (otherwise dropped). **There is no free-text field anywhere in the entry shape** — the buffer is structurally incapable of carrying an owner's symptom text, a pet name, or a token, which is the only design that survives T089's PII posture (`packages/analytics/src/sentry/scrub.ts` drops breadcrumb `message` wholesale precisely because free text is unscrubbable). Fed from the three existing sinks listed above (3 one-line call sites). The api re-validates the same closed shape with Zod and rejects anything else — a compromised/old client cannot post free text into the log column.

**Consent (the tested AC):** `attachLogs: boolean` defaults **false** in the UI; the mobile submit path sends `logs` **only** when the toggle is on; and independently the **service** rejects with `400` any payload where `attachLogs !== true` **and** `logs` is present and non-empty. Server-side rejection is the AC — UI gating alone is not.

### D4 — API shape: a new `feedback` module, user-scoped (not household-scoped).
Mirrors `apps/api/src/me/privacy.controller.ts` (per-user, no `@HouseholdScoped()`, global `JwtAuthGuard` applies, never `@Public()`). Two endpoints, mirroring the photos presign idiom (`apps/api/src/photos/`):
- `POST /v1/feedback/screenshot-upload-url` → `{ uploadUrl, key }`, key = `feedback/<userId>/<uuid>.jpg`.
- `POST /v1/feedback` → creates the `FeedbackReport` row → `{ reportId, createdAt }` (201).

Namespace check `isKeyInFeedbackNamespace(userId, key)` mirrors `photos.constants.ts#isKeyInPetNamespace` (a key outside the caller's own prefix → 400), and `storage.objectExists(key)` → 404 if never uploaded. **No BullMQ worker**: the write is a single row insert, not long-running work — §6's worker rule does not apply. Body size is bounded by DTO limits (message ≤ 2000 chars, ≤ 50 log entries), so no inline heavy work exists.

### D5 — "Sentry breadcrumb link" concretely means **ids in both directions, never raw breadcrumbs.**
T089's scrubber makes shipping breadcrumb *content* to the server impossible-by-design (`message` dropped wholesale, `console` category dropped entirely). So:
- **Report → Sentry:** the client reads the current Sentry event id and release and submits them as `sentryEventId` (32 lowercase hex, validated) + `sentryRelease` (the `bombaypetcompany@{version}+{buildId}` string from `buildSentryRelease`). Stored on the row; a human pastes the id into Sentry search to reach the exact event. No org/project slug config is invented.
- **Sentry → report:** at submit time the client adds one **content-free** Sentry breadcrumb `{ category: "feedback", level: "info", data: { category: <BUG|IDEA|OTHER> } }` (no `message` key at all) so a subsequent crash's event shows "the user filed a report just before". A test asserts this breadcrumb survives `scrubBreadcrumb` unchanged in meaning and carries no free text.

Both helpers live in the existing `apps/mobile/src/observability/sentry.ts` (`getLastSentryEventId()`, `addFeedbackBreadcrumb()`), each a safe no-op when Sentry never initialized (empty DSN — the jest default), matching that file's established `if (!sentryModule) return;` idiom.

### D6 — Beta banner: root-mounted, flag-gated, **non-dismissible**, normal flow.
Rendered in `app/_layout.tsx` immediately **after** `<OfflineBanner />` inside the same `<View className="flex-1">`. Not dismissible (no persistence store needed — smallest correct thing; it disappears when the beta flag is off). Gated by a new `betaBanner: boolean` config field (`EXPO_PUBLIC_BETA === "1"`), default **false** so nothing changes for non-beta builds and no existing snapshot/behaviour shifts. Safe-area: `OfflineBanner` already applies `insets.top`; `BetaBanner` applies `paddingTop: isOffline ? 0 : insets.top` via the already-exported `useIsOffline()` so the two never double-pad and neither is ever `absolute`. A11y: the banner text is plain `Text`; the CTA is a `Pressable` with `accessibilityRole="button"` + `accessibilityLabel` from `strings`, `maxFontSizeMultiplier={1.5}` on text (existing banner idiom). `accessibilityRole="alert"` is **not** used (unlike OfflineBanner) — a permanent beta notice is chrome, not an alert.

### D7 — Erasure: new model joins the T091 cascade, **and so does its S3 prefix.**
`FeedbackReport` gets `user User @relation(..., onDelete: Cascade)` → FK-cascaded, so it is added to `CASCADE_COVERED_MODELS` in `apps/api/src/me/account-erasure-cascade-completeness.spec.ts` (this DMMF guard fails on any unaccounted model — it is not optional). FK cascade does **not** reach S3, so `feedback/${userId}/` is added to the `listKeys` set in **both** erasure branches of `apps/api/src/me/account-erasure.service.ts` (lines ~131 FULL_HOUSEHOLD and ~184 USER_ONLY, alongside the existing `exports/${userId}/`). **Out of scope, flagged:** feedback reports are deliberately *not* added to the T091 export bundle (`account-export.service.ts`) — support tickets a user filed are operational data, and widening the export bundle is unrequested scope. Recorded in §7 founder delta for a privacy-counsel call.
