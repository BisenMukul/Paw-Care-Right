# Plan — T085: Web programmatic SEO pages (`/can-{species}-eat/{item}`)

## Objective (from card)
Statically generate one page per (species × toxin item) from the T035 dataset in `apps/web`
(Next.js App Router): verdict hero, nuance section, emergency/hotline CTA when the verdict is
toxic or emergency, app-store CTA, non-dismissible disclaimer, schema.org FAQPage JSON-LD,
cross-links, plus sitemap coverage.
**Accept:** (AC1) build renders **all** pages, asserted by count · (AC2) Lighthouse SEO ≥ 95 on a
sample · (AC3) **every** toxic/emergency page shows the hotline CTA (tested on a sample set).

## Safety statement (PRODUCT_SPEC §5 / CLAUDE.md §7 — read before step 1)

1. **This card TOUCHES a §5 surface** (disclaimer + emergency/poison-hotline escalation) — but only by
   **adding** the web equivalents of surfaces that already exist on mobile. It removes, weakens,
   softens or gates **nothing**. No existing safety component, rule table, hotline row, detector or
   string anywhere in the repo is edited. It is therefore *not* a SAFETY-ESCALATION block, but the
   checker should scrutinise §5 items 1, 3 and 4 hardest.
2. **Every page renders `<VetDisclaimer/>`** (§5.1 / §7.3). Web version is a plain `<div>`/`<p>` — no
   button, no `onClick`, no `hidden`, no collapse, no client component ⇒ structurally non-dismissible.
   Copy is **verbatim** the mobile wording so the two surfaces cannot drift.
3. **Escalation renders before content** (§5.3/§7.4). On `toxic`/`emergency` pages the hotline CTA is
   the **first** element inside `<main>`, above the verdict hero — the web analogue of the Emergency
   interstitial "before any AI content".
4. **No fabricated hotline numbers.** The hotline block is rendered **from `REGION_HOTLINES`**, never
   from literals in a component, and it ends with the "region not listed ⇒ contact your nearest
   emergency vet" line (the web analogue of `FALLBACK_REGION_HOTLINE`).
5. **No dosing, ever** (§5.4/§7.2). Nothing on these pages states an amount with a mass/volume unit.
   Note that `human-med` is a toxin **category** — items like ibuprofen appear as page subjects. That
   is the *opposite* of a drug recommendation (the page says "not safe, call a vet"), so a drug-name
   detector must **not** be applied here; the dosing/diagnosis/reassurance scan (below) is.
6. **No "possible causes"/diagnosis language.** The word `diagnos*` must not appear in any rendered
   byte (§7.1).
7. **No de-escalating reassurance.** Banned in rendered output: "will be fine", "don't/do not worry",
   "nothing to worry about", "perfectly/completely/totally safe", "no need to see/call/contact a vet".
8. **No home treatment.** The only "what to do" copy is *contact a vet / contact a helpline / do not
   wait for symptoms / do not try to treat this at home / do not make your pet vomit unless a vet tells
   you to*. No first aid, no "give water/milk/bread", no induced emesis instruction.
9. **All toxicology prose comes from the dataset** (`note`, `quantityNuance`) — the executor writes
   **zero** new factual claims about any item. Every other sentence is a verdict-tier-generic
   constant in `strings.ts`. Inventing item-specific toxicology is an automatic fail.
10. **App-store honesty** (§5.7). No store links exist before C3/T099 ⇒ the app CTA is a
    non-linking "Coming soon" badge. Fabricating an App Store/Play URL is forbidden and tested against.

## Key decisions (restated as risks at the end)

- **D1 — Page count is derived (`toxins.length * 2`), never the literal 600.** See table above.
- **D2 — Route shape: two literal directories, `app/can-dogs-eat/[item]/page.tsx` and
  `app/can-cats-eat/[item]/page.tsx`.** App Router segments cannot mix a literal and a param
  (`can-[species]-eat` is not valid), so the alternatives were: (a) two literal dirs, (b) a top-level
  `app/[prefix]/[item]` dynamic segment, (c) a catch-all `app/[...slug]`. (b) and (c) both make a
  *root-level* dynamic segment that competes with `/privacy`, `/terms`, `/sitemap.xml` and would emit
  soft-404s for arbitrary two-segment URLs — an SEO defect and a routing hazard. (a) is the only
  option that keeps the URL literal exactly as the card specifies, keeps every other route
  unshadowed, and lets `generateStaticParams` be exact per species. Duplication is ~20 lines each and
  both files delegate to one shared module, so there is no logic duplication.
- **D3 — `dynamicParams = false` on both routes.** Unknown items return a real 404 instead of an
  on-demand-rendered soft-404. Also guarantees the prerender manifest is the complete page set.
- **D4 — All markup lives in *synchronous* presentational components under
  `apps/web/src/components/food/**`, taking a plain `FoodPageModel` prop.** `page.tsx` is a thin async
  adapter (`await params` → build model → `notFound()` or render). Reason: Next 15 page components are
  async server components, which `react-dom/server`'s `renderToStaticMarkup` cannot render. Splitting
  it this way makes the entire visible surface unit-testable with **zero new test dependencies**
  (`react-dom` is already a dependency), and is the standard container/presenter split anyway.
- **D5 — Lighthouse verification is two-layered and honestly labelled.** (i) `lighthouserc.json` is
  extended with 3 sample programmatic URLs and a real `categories:seo >= 0.95` assertion — that is the
  literal AC and the artefact **T095** activates in CI. (ii) Because a real Lighthouse run needs Chrome
  + a served build and is **not** part of `pnpm test`, a deterministic **SEO contract test** pins every
  structural signal the Lighthouse SEO category audits (title, meta description, canonical, `lang`,
  crawlable links with discernible text, no `noindex`, valid parseable JSON-LD, no image without
  `alt`). The executor attempts one real `lhci autorun`; **if Chrome is unavailable it must record that
  fact verbatim in the journal and MUST NOT claim a score it did not measure.**
- **D6 — Hotline presentation is a static list of all 5 seeded regions, not geo-detection.** Geo-IP
  would need a new dependency and a request-time header, which destroys SSG (the entire point of the
  card) and Lighthouse/CDN caching. The dataset also refuses to fabricate numbers for unknown regions.
  So: render every `REGION_HOTLINES` row (name, region code, `tel:` link, fee note) plus the
  "not listed ⇒ nearest emergency vet" line. Rendered **from the array**, so a future 6th region
  appears automatically (and the test counts against `REGION_HOTLINES.length`, so it can't be faked).
- **D7 — The hotline CTA renders iff verdict ∈ {`toxic`, `emergency`}**, per the card ("emergency CTA
  when toxic"). `caution` and `safe` pages still carry the disclaimer **and** a verdict-appropriate
  "contact your vet if…" line, so no page is ever a dead end. (Risk R4.)
- **D8 — Item names are rendered **verbatim** from `row.name`** (e.g. "Onion and other allium plants"),
  never lower-cased or pluralised. Case-mangling proper nouns/brand-ish names is worse than a capital
  letter mid-sentence, and any transformation is a place for the executor to invent text.
- **D9 — All 233 items get pages, every category** (human-food, plant, household-chemical, human-med,
  pest-bait, other). Restricting to food+plants gives 312 pages, further from the card's intent, and
  "can dogs eat ibuprofen / lilies / antifreeze" are genuine, high-intent search queries whose correct
  answer is exactly this page. (Risk R5.)
- **D10 — FAQ question set is fixed and dataset-derived** (2 or 3 entries; Q2 only when
  `quantityNuance` exists). The JSON-LD is built from the **same** model object the visible FAQ section
  renders, and a test asserts set-equality — Google requires FAQ markup to match visible content.
- **D11 — Test runner: Jest + ts-jest in `apps/web`, node environment, `renderToStaticMarkup`.**
  Jest/ts-jest are the constitution's testing stack (§3) and already in the lockfile at the exact
  versions used by `packages/data` — this is *wiring an existing tool into a workspace that currently
  has a stub `test` script*, not adopting a new library. **No** `@testing-library/react`, **no**
  `jest-environment-jsdom`, **no** lighthouse programmatic lib.
- **D12 — `apps/web`'s `test` task depends on its own `build`** (`apps/web/turbo.json`, mirroring the
  existing `typecheck` override), so the build-output count assert (AC1) reads a manifest that is
  guaranteed fresh. If the manifest is missing the test **fails loudly** — it never skips.

## Contracts (the executor must match these exactly)

```ts
// apps/web/src/food/species.ts
export interface SpeciesDescriptor {
  segment: "can-dogs-eat" | "can-cats-eat";
  verdictKey: "dog" | "cat";      // key into ToxinRow["verdicts"]
  plural: "dogs" | "cats";        // "Can dogs eat …?"
  singular: "dog" | "cat";        // "if my dog ate …"
  Plural: "Dogs" | "Cats";
}
export const SPECIES_SEGMENTS: readonly SpeciesDescriptor["segment"][];  // dogs first, then cats
export function speciesBySegment(segment: string): SpeciesDescriptor | undefined;

// apps/web/src/food/page-model.ts
export interface FoodFaqEntry { question: string; answer: string; }
export interface FoodCrossLink { href: string; label: string; }
export interface FoodPageModel {
  segment: SpeciesDescriptor["segment"];
  species: SpeciesDescriptor;
  itemId: string;
  itemName: string;               // row.name VERBATIM (D8)
  category: string;               // row.category
  verdict: "safe" | "caution" | "toxic" | "emergency";
  verdictLabel: string;           // short badge
  verdictHeadline: string;        // hero line
  note: string;                   // row.note VERBATIM
  quantityNuance?: string;        // row.quantityNuance VERBATIM
  whatToDo: string;               // verdict-tier constant, NEVER item-specific
  showHotlineCta: boolean;        // === (verdict === "toxic" || verdict === "emergency")   [D7]
  otherSpecies: FoodCrossLink;    // same item, other species
  relatedItems: FoodCrossLink[];  // ≤6, same category, deterministic, excludes self
  canonicalUrl: string;           // `${SITE_URL}/${segment}/${itemId}`
  title: string;                  // `Can ${plural} eat ${itemName}?`
  description: string;            // metaDescription(): ≤155 chars, word-boundary truncated with "…"
  faq: FoodFaqEntry[];            // 2 entries, or 3 when quantityNuance exists   [D10]
}
/** Unknown segment or unknown item id ⇒ null (caller calls notFound()). */
export function buildFoodPageModel(segment: string, itemId: string): FoodPageModel | null;

// apps/web/src/food/json-ld.ts
export function buildFaqJsonLd(model: FoodPageModel): Record<string, unknown>;
//   { "@context":"https://schema.org", "@type":"FAQPage",
//     mainEntity: faq.map(e => ({ "@type":"Question", name: e.question,
//       acceptedAnswer: { "@type":"Answer", text: e.answer } })) }
export function jsonLdScriptContent(value: unknown): string;  // JSON.stringify + all "<" -> "\\u003c"
```

**`relatedItems` determinism (pin exactly).** Take `toxins.filter(t => t.category === row.category)`
in dataset order; find `row`'s index `i`; take the next up-to-6 entries walking forward with wrap-around
(`(i+1) % n`, `(i+2) % n`, …), stopping before returning `row` itself. Href = `/${segment}/${id}`,
label = that row's `name`. Deterministic, self-excluding, always resolves to a generated page.

## Risks & the decisions the planner made (for the checker)

- **R1 (D1) — the card says "~600 pages"; the dataset yields 466.** The estimate predates T035's actual
  cardinality (233 rows). Deriving the assert from `toxins.length * 2` with a 440 floor is the only
  option that is simultaneously true today, true after the dataset grows, and non-vacuous. If the
  founder wants ≥600 pages, that is a *dataset* card (grow toxins to 300), not this one. **Flagged for
  the journal.**
- **R2 (D2) — two near-identical route files.** A reviewer may want one parametrised route. App Router
  cannot express `can-[species]-eat` as a single segment, and a root-level dynamic segment would
  shadow `/privacy` and `/terms` and emit soft-404s. The duplication is confined to a segment constant;
  all logic is shared. If a third species is ever added, a third directory is added.
- **R3 (D5) — the ≥95 Lighthouse number is asserted by `lighthouserc.json`, not by `pnpm test`.** This
  is the honest limit: Lighthouse needs Chrome plus a served build, which is not a unit-test
  environment, and T095 is the card that wires it into CI. The structural SEO contract test is a
  *proxy*, not the score. **Residual risk:** a page could satisfy every structural audit and still
  score <95 (e.g. a crawler-blocking directive introduced later). Mitigation: the sample URLs are in
  the lhci config now, so T095 turns this on with zero further work, and the executor must journal the
  real outcome of its one attempted run.
- **R4 (D7) — `caution` pages get no hotline block.** Faithful to the card ("emergency CTA when
  toxic"), and the caution copy still says "contact your vet for advice". Counter-argument (fail
  upward, §5.2) would put the hotline on caution pages too. The planner chose card-literal + universal
  disclaimer + universal vet line; **if the checker judges §5.2 to dominate, widening
  `showHotlineCta` to include `caution` is a one-line change plus one test edit** and should be
  requested explicitly rather than done silently.
- **R5 (D9) — `/can-dogs-eat/antifreeze` and `/can-dogs-eat/ibuprofen` read oddly.** "Eat" is
  imprecise for chemicals and meds, but these are real ingestion queries with a correct, useful,
  safety-positive answer, and excluding them would drop 77 items (154 pages). Alternative considered
  and rejected: a second URL family for non-foods (scope creep, and dilutes the sitemap).
- **R6 (D11) — adding a Jest setup to `apps/web`.** Three devDeps already present in the lockfile at
  pinned identical versions. §2.7 justification goes in the journal: "`apps/web` had a stub `test`
  script; §3 mandates Jest and §8 requires tests to ship with the code — no new library is introduced,
  the existing runner is wired into one more workspace." If the checker rejects even this, the task
  cannot satisfy §8 and must be blocked rather than shipped untested.
- **R7 (D12) — `apps/web`'s `test` now depends on its own `build`,** which makes `pnpm test` slower
  (a full 466-page prerender). This is the price of literally satisfying "build renders all pages
  (count assert)"; the precedent is the existing `typecheck: dependsOn ["^build","build"]` override in
  `apps/web/turbo.json`. If the build proves too slow for the loop, the fallback is to keep the params
  set-equality test in `pnpm test` and move only the manifest test behind a build-gated script — but
  that weakens AC1, so do **not** do it without the checker's agreement.
- **R8 — build-artefact assertions are coupled to Next's internal manifest shape.** Verified against
  the committed `.next/prerender-manifest.json` (`version: 4`, `routes` keyed by concrete path). A
  future Next major could change it. Mitigation: the test asserts the manifest exists and fails with an
  actionable message; the params-level set-equality test provides an independent, framework-agnostic
  proof of the same fact.
- **R9 — `route-adapters.spec.ts` asserts on source text, not on imported modules.** Importing
  `app/**/page.tsx` in Jest pulls `next/navigation` (ESM) into a CJS test environment. Source-text
  assertions are weaker than behavioural ones; they are backed by the build-output test, which

  palm") and to let the executor start rewriting dataset content.
