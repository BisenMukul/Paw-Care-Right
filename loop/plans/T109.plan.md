## 2. Design

### 2.1 Module layout (4 new source files, all under `apps/mobile/src/review/`)

```
review-trigger.ts   PURE. No storage/native/react imports. All decisions live here.
review-state.ts     Persisted MMKV read/write of the gate state (update-throttle.ts shape).
store-review.ts     Lazy-require wrapper around expo-store-review (update-controller.ts shape).
request-review.ts   Thin integration: read state -> pure decide -> stamp -> request. Never throws.
```

### 2.2 `review-trigger.ts` (the tested AC surface)

```ts
export type PositiveMoment = "reassure-acknowledged" | "reminder-streak";

export interface ReviewGateState {
  lastPromptedAt: number | null;   // epoch ms, null = never prompted
  lastEmergencyAt: number | null;  // epoch ms, null = no emergency ever recorded
  completionStreak: number;        // consecutive reminder completions, >= 0
}

export const REVIEW_THROTTLE_MS       = 60 * 24 * 60 * 60 * 1000; // 60 days (card)
export const EMERGENCY_SUPPRESSION_MS = 30 * 24 * 60 * 60 * 1000; // D1
export const REVIEW_STREAK_THRESHOLD  = 5;                        // card ("5th")

export type ReviewDecision =
  | "request"
  | "suppressed-throttle"
  | "suppressed-emergency"
  | "suppressed-streak";  // the moment is not (yet) a positive moment

export function decideReview(args: { now: number; moment: PositiveMoment; state: ReviewGateState }): ReviewDecision;
export function shouldRequestReview(args: /* same */): boolean;   // decideReview(...) === "request"

/** Pure: next streak value for a reminder event. */
export function nextStreak(current: number, event: "completed" | "snoozed" | "missed"): number;

/** Pure: does a loaded agenda window contain a MISSED occurrence? */
export function hasMissedEntry(entries: readonly { status: string }[]): boolean;
```

**Decision order inside `decideReview` (emergency first — safety before growth):**
1. `lastEmergencyAt !== null` AND (`lastEmergencyAt > now` **OR** `now - lastEmergencyAt < EMERGENCY_SUPPRESSION_MS`) → `"suppressed-emergency"`.
2. `lastPromptedAt !== null` AND (`lastPromptedAt > now` **OR** `now - lastPromptedAt < REVIEW_THROTTLE_MS`) → `"suppressed-throttle"`.
3. `moment === "reminder-streak"` AND NOT (`completionStreak > 0 && completionStreak % REVIEW_STREAK_THRESHOLD === 0`) → `"suppressed-streak"`.
4. otherwise → `"request"`.

**Clock direction is deliberately fail-CLOSED here** (a future timestamp suppresses) — the
*opposite* of `update-throttle.ts`'s `shouldRecheck`, which fails open. Rationale: a wedged
clock must never *unlock* a review prompt after an emergency; the worst case of failing closed
is that we never ask for a rating, which costs nothing. This is D1 and is asserted by tests.

`nextStreak`: `"completed"` → `current + 1`; `"snoozed"` → `0`; `"missed"` → `0`; never negative.

### 2.3 `review-state.ts` (persistence)

`createSafeStorage({ createMmkv: () => require("react-native-mmkv").createMMKV() })` — same
shape as `update-throttle.ts` (including the `eslint-disable ... // JUSTIFIED:` comment).

Keys (§1a prefix, matching `bombaypetcompany.ota-last-check-at`):
- `bombaypetcompany.review-last-prompted-at`
- `bombaypetcompany.review-last-emergency-at`
- `bombaypetcompany.review-completion-streak`

API (each function internally guarded so it can never throw into a caller — a review counter
must never break a care flow):
```ts
export function readReviewGateState(): ReviewGateState;   // re-validates on read
export function writeLastPromptedAt(at: number): void;
export function recordEmergencySeen(at?: number): void;   // defaults to Date.now()
export function recordReminderEvent(event: "completed" | "snoozed" | "missed"): number; // returns the new streak
```
Re-validation mirrors `readLastCheckAt`: non-finite / non-integer / negative → `null` for
timestamps, `0` for the streak.

### 2.4 `store-review.ts` (native module, lazy + no-op safe)

```ts
export interface StoreReviewApi {                 // narrow LOCAL interface (F12) — this file
  isAvailableAsync?: () => Promise<boolean>;      // typechecks whether or not the package
  hasAction?: () => Promise<boolean>;             // is installed
  requestReview?: () => Promise<void>;
}
export type StoreReviewLoader = () => StoreReviewApi | null;
export const defaultStoreReviewLoader: StoreReviewLoader = /* require in try/catch, null on failure */;
export async function requestStoreReview(loader?: StoreReviewLoader): Promise<boolean>;
```
`requestStoreReview` resolves `true` only if the module loaded, `isAvailableAsync()` resolved
`true`, `hasAction()` (when present) resolved `true`, and `requestReview()` resolved. Any
absence / rejection / throw → `false`, never rethrown.

**Do NOT use `typeof import("expo-store-review")`** — that would make typecheck depend on the
install succeeding (see step 1 fallback and R4).

### 2.5 `request-review.ts` (integration, ~25 lines)

```ts
export async function maybeRequestReview(
  moment: PositiveMoment,
  deps?: { now?: number; loader?: StoreReviewLoader },
): Promise<ReviewDecision | "unavailable">;
```
Order (atomicity): decide → if `"request"`, **`writeLastPromptedAt(now)` BEFORE awaiting**
`requestStoreReview()`, so a re-entrant or duplicated call inside the same 60-day window can
never produce two prompts even if the native call hangs. If the native call reports `false`
(module absent / OS declined), the throttle stamp is **kept** and the function returns
`"unavailable"` — we deliberately do not un-stamp and retry: both stores already rate-limit and
silently no-op, so retrying would hammer a device that will never show the dialog.

Call sites always use `void maybeRequestReview(...)` — never `await`, never block UI.

## 7. Platform honesty note (must appear as a comment in `store-review.ts`)

`StoreReview.requestReview()` is **rate-limited and non-guaranteed by the OS**: iOS caps in-app
review prompts (historically ~3 per 365 days per app per device) and may show nothing at all;
Android's In-App Review API has its own undocumented quota and resolves successfully whether or
not a dialog appeared. Neither platform tells us whether the dialog was shown. Our 1/60-days
throttle is therefore a **floor we impose on ourselves**, not a ceiling we can verify, and
`requestStoreReview()`'s `true` means "we asked", never "the user saw a dialog". Both stores also
forbid incentivising or gating content on reviews — we do neither.

## 8. Risk register (top 5 — every design decision, stated for the checker to scrutinise)

| # | Decision / Risk | Why chosen | Failure mode if wrong |
|---|---|---|---|
| **R1 (D1)** | **Emergency suppression = persisted 30-day window, fail-CLOSED on a backwards clock**, recorded when (a) the Emergency interstitial mounts and (b) a result screen shows a check with a `redFlag` or tier `EMERGENCY_NOW`/`VET_24H`. A session-scoped flag was rejected as strictly *weaker*: a persisted 30-day window contains "this session" and survives process death. | "never after emergencies" needs a definition with an edge; a session flag would let us ask for 5 stars the morning after a pet's emergency. 30 days is the same order as the 60-day throttle. | If the checker judges 30 days as founder policy rather than an engineering call, it is a one-constant change; AC1.12 pins it and the other tests are relative to the constant, so the blast radius is one number. |
| **R2 (D2)** | **Client-side MMKV streak counter** (increment on completion incl. the offline `"queued"` path; reset on snooze; reset when a loaded agenda window contains a `MISSED` entry) instead of a server-derived streak. | F8 + F10: no streak data exists and the agenda window starts *today*, so completion history is not client-visible. A server streak means a new endpoint + query + index ⇒ far beyond an **S** card. | Per-device (not per-account) and blind to misses outside the loaded window, so it can over-count a "streak". Worst case: we ask slightly more often than a perfect streak would — still bounded by the 60-day throttle and the emergency window. Documented, not hidden. |
