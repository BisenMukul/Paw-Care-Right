## 3. Design decisions (minimum set — scrutinise these)

- **D1 — one release function, two call sites.** Add `currentSentryRelease(): string` to
  `apps/mobile/src/observability/sentry.ts`:
  `buildSentryRelease(getAppVersion(), readOtaInfo().updateId ?? getConfig().gitSha)`.
  `initMobileSentry()` and `app/feedback.tsx` both call it. `buildSentryRelease` itself is untouched.
  Rationale: §7 wants `+{updateId}`, but an embedded/Expo-Go launch has `updateId === null` and a
  release of `bombaypetcompany@1.0.0+null` would be worse than T089's `gitSha` fallback; F2 forces the
  shared function.
- **D2 — `ota_*` events ride the existing `captureEvent`; no anonymous distinctId is invented.**
  A signed-out cold start therefore emits nothing (F6). To avoid *losing* `ota_applied` (the one event
  §7 gives properties for), the "an update was downloaded" record is **persisted** and cleared only
  after the event actually fires, so a signed-out apply reports on the next signed-in launch. Records
  older than 7 days are dropped (a stale `latencyMs` is worse than no event).
- **D3 — the controller stays pure; events ride an optional callback.** `runUpdateCycle` gains an
  optional `onEvent?: (event: OtaCycleEvent) => void` inside its existing `deps` object; its **return
  type is unchanged**, so every T114 test keeps passing. `useUpdateFlow` supplies the callback that
  calls `captureEvent`. No analytics import lands in `update-controller.ts`.
- **D4 — `/v1/meta/client-versions` aggregates the `Device` table**, extended with two nullable columns
  (`appVersion`, `otaUpdateId`) reported by the existing `POST /v1/devices` call. No new model (⇒ no
  erasure-guard edit, F10), no new user-identifying data (a version string and an EAS update id are not
  PII), exactly one migration.
- **D5 — freshness is honestly descoped.** Registration is JIT (F9), so a device's reported pair is "as
  of its last push registration", not per launch. A per-launch re-report is **deliberately not built**
  in this M card. Consequence, stated in the endpoint's Swagger description AND runbook §17: **PostHog
  `ota_applied` (§7) is the authoritative adoption curve; this endpoint is a coarse cross-check over
  push-registered devices.** This is the scope decision the checker should challenge first.
- **D6 — admin auth = hashed constant-time shared secret, fail-closed.** New env `ADMIN_API_TOKEN`
  (default `""`); `AdminTokenGuard` mirrors `RcWebhookGuard` but **also rejects when the configured
  token is empty**, so an unconfigured deployment exposes nothing. Header: `x-admin-token`. The route is
  `@Public()` (bypassing the JWT guard) + `@UseGuards(AdminTokenGuard)`.
- **D7 — promotion table shape.** One row per rollout step (`10%`, `50%`, `100%`) so no line ever
  contains both `10%` and `50%` (F7). Criteria cells transcribed verbatim from §1 above.
- **D8 — carry-forwards: fix F11-2, F11-3, F11-4; defer F11-5 with justification.** Findings 2/3/4 are
  small and deterministic. Finding 5 (deriving the piping-step set from yaml text) needs a
  pipe-vs-`||`-vs-echo-text heuristic whose failure mode is false-positive noise in a guard; the single
  piping step today is covered and `Rollout playbook` already sets `-o pipefail`. Deferred deliberately,
  stated in the code comment and the journal — not silently skipped.
