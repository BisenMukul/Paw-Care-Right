## Offline validation strategy (how AC1 is proved without Expo servers)
Investigated (read-only; the planner has no shell, so this is evidence-based, and step 9 makes the executor confirm it empirically before relying on it):
- `eas-cli` is absent from the lockfile-installed tree → any `eas ...` invocation would have to be `npx eas-cli@X`, i.e. a network fetch of a large unpinned CLI at test time.
- Even if fetched, `eas build --profile preview` **cannot** run: it requires an authenticated Expo session (`EXPO_TOKEN`/`eas login`) and an existing EAS project; `eas config`/`eas build --dry-run`-style paths also resolve EAS-hosted environment variables and therefore auth. `eas build:configure` would *mutate* eas.json/app.config — forbidden here.
- `npx expo-doctor` calls the Expo API for version checks → not offline-deterministic; **do not** wire it into `pnpm test`.

**Decision (D1):** the acceptance gate for "config validates (dry)" is a repo-owned, offline, deterministic Jest spec `apps/mobile/__tests__/eas-config.test.ts` that (a) parses `eas.json`, (b) validates it against the documented EAS build-schema constraints (hand-written predicates, no new dep, no `any`), (c) cross-checks it against `app.config.js` and `.env.example`, and (d) scans every committed value for secret-shaped strings. The real `eas build --profile preview` command is documented in the runbook as a **founder-run** verification with its exact expected output, and recorded as a founder to-do. Step 9 additionally has the executor *attempt* the real CLI once, time-boxed, and record the actual failure text in the runbook + journal so the gap is evidenced, not asserted.

**Dependency decision (D2):** do **not** add `eas-cli` to any `package.json`. Rationale for CLAUDE.md §2 rule 7: nothing in `pnpm test`/`build` can use it (no auth, no project), it is a ~100MB dev-machine/CI-runner tool, and pinning it in devDependencies would slow every `pnpm i` for zero gate value. The runbook pins the invocation instead: `npx eas-cli@latest ...` with a "pin the major you used in the journal" note. If the checker rejects D2, the fallback is a root `devDependencies` entry + a one-line journal justification — but that is **not** what this plan authorizes.
