## 1. Locked design decisions (scrutinise these, CHECKER)

**D1 — Extend `docs/release-runbook.md`, do not create a new doc.** New sections `## 12.`–`## 16.` appended after §11. Rationale: the card says "Complete runbook"; §§1–11 + the existing drift guard already are that runbook; a second doc guarantees drift.

**D2 — Flag source of truth = Redis key overriding an env default.** `env` alone is NOT a kill switch (needs a deploy/restart). New service `FeatureFlagsService` resolves each flag as: Redis `GET bombaypetcompany:flags:<key>` → `"off"` ⇒ disabled, `"on"` ⇒ enabled, missing/other ⇒ env default (`FEATURE_CHECKS` / `FEATURE_CHAT` / `FEATURE_PAYWALL`, `z.enum(["on","off"]).default("on")`). Key prefix matches CLAUDE.md §1a (`bombaypetcompany:`).

**D3 — Operator mechanism = documented `redis-cli` command, NOT a new admin endpoint.** Kill: `redis-cli -u "$REDIS_URL" SET bombaypetcompany:flags:checks off`. Restore: `... DEL bombaypetcompany:flags:checks`. Justification (M scope + safety): a new authenticated admin write endpoint is a new attack surface whose compromise would let an attacker disable a safety-adjacent feature, needs a DTO + guard + role + e2e auth/validation tests (a task of its own), and would be unusable exactly when the API is the thing that is unhealthy. `redis-cli` works while the API is degraded and requires infra credentials the founder already holds. **No TTL** on the key — an expiring kill switch would silently re-enable a feature mid-incident.

**D4 — Read caching + sticky-last-known on Redis failure.** `FeatureFlagsService` caches each resolved value in-process for `FLAG_CACHE_TTL_MS = 5_000` (a kill propagates in ≤5s; no Redis round-trip per request on the hot check path). On a Redis error: return the **last value this process successfully read** if there is one, else the env default. Rationale: once a kill has been observed, a Redis blip must not silently revert it; with no prior read the env default is the only honest answer.

**D5 — Which endpoints are gated (safety-critical scoping).** Gated: `POST /v1/pets/:petId/checks` (`checks`), `POST /v1/chat/threads` + `POST /v1/chat/threads/:id/messages` (`chat`). **Deliberately NOT gated:** `GET /v1/checks/:id`, `GET /v1/pets/:petId/checks` (already-produced results, including the `redFlag` Emergency-interstitial payload, must stay readable — CLAUDE.md §7 rule 4), and `POST /v1/checks/:id/followup` (deterministic, escalation-only — killing it would remove an upward path, violating §7 rule 5's fail-upward posture). Write this rationale as a code comment at the guard usage site.

**D6 — Typed rejection = HTTP 503 + new error code `FEATURE_DISABLED`.** `STATUS_TO_CODE[503] = "FEATURE_DISABLED"` in `all-exceptions.filter.ts`; the enum in `packages/types/src/error-codes.ts` grows by one and its pinned spec list is updated. Server-side enforcement is the authoritative backstop so a stale client that never sees the new config field still cannot reach a killed AI path.

**D7 — `/config` gains all three flags; only two are enforced.** `appConfigResponseSchema` gains `features: { checks: boolean; chat: boolean; paywall: boolean }`. `paywall` is **plumbed + documented only** — no API guard, no mobile behaviour change in this task. Explicit statement for the CHECKER: the card's Do-list names three switches, the AC demands "implemented + tested for checks/chat"; gating the paywall server-side would risk the purchase/entitlement path for zero AC credit, so paywall is config-plumbed (operator can flip it, clients can read it) and its intended future use is documented in runbook §14.

**D8 — Mobile fails safe and loudly, never silently.** With `features.checks === false`: `app/check/index.tsx` replaces the `CategoryGrid` with a non-dismissible `FeatureUnavailableNotice` (copy: temporarily unavailable + "contact your vet, or your nearest emergency vet service if this can't wait"); the recent-checks list and its rows stay rendered and tappable (results remain readable). With `features.chat === false`: `app/chat/index.tsx` replaces composer + quick prompts with the same notice; the persistent `<VetDisclaimer/>` still renders. `use-check-submission.ts` gains an `"unavailable"` state for `FEATURE_DISABLED` so a deep-linked/stale intake submit shows the same copy instead of a misleading "Retry".

**D9 — Emergency/hotline reachability is proven, not assumed.** No new emergency screen is invented (that would be a new §5 surface). Proof instead: `app/check/emergency/[checkId].tsx` renders its region hotline content unchanged while `features.checks === false` (mobile test), and `GET /v1/checks/:id` returns 200 with its `redFlag` payload while the `checks` flag is off (api e2e).

**D10 — Client defaults stay fail-open.** `DEFAULT_APP_CONFIG.features` = all `true`. A client that cannot reach `/config` must not lock itself out of a symptom check; the API is the enforcement point.

## 7. Risk register (top 5)

1. **`.strict()` config schema vs stale clients** — an already-installed binary parsing the new `features` field with its old strict schema fails the parse and falls back to cache-or-default (features all-true). Mitigation: the server-side guard is the authoritative enforcement (D6); the mobile default is fail-open by design (D10); `app-config-queries.test.ts` covers the missing/extra-field path. Nothing is publicly shipped yet (T101 = internal only), so real exposure is limited to internal testers.
2. **Redis becomes a dependency of the checks hot path** — a Redis outage now also touches flag resolution. Mitigated by the 5s in-process cache, try/catch + sticky-last-known, and the env default (D4); Redis is already required for BullMQ, so checks cannot complete without it anyway. Residual: a Redis outage during an active kill, in a *freshly restarted* process, reverts to the env default — hence founder to-do 15.
3. **Guard placement could over-gate a safety surface** — putting `@RequiresFeature("checks")` at class level on `ChecksController` would gate `GET /checks/:id` and the follow-up, hiding existing emergency payloads and removing an escalation path (a §5 violation). D5 makes it method-level and Step 10's e2e fails loudly on regression.
4. **Error-code enum churn** — `error-codes.spec.ts` pins the exact list and `503` previously surfaced as `INTERNAL`; any other place switching exhaustively on `ErrorCode` may need a branch. Detectors: Step 9c grep + `pnpm typecheck`.
5. **Runbook drift-guard brittleness** — the container-coverage test parses `docs/ARCHITECTURE.md`'s §2 markdown table, so a future table reformat breaks the test rather than the doc. Accepted (it is the house drift-guard idiom) and softened by the non-vacuity floor plus the explicit hardcoded infra list. Secondary: the heading-word regexes must match the exact words used in §§12–16.
