## 3. Design decisions (each is a deliberate choice — scrutinise in review)

- **D1 — Zero new dependencies; pure-TS deterministic PNG pipeline.** `sharp` is in the tree but only for `apps/api`. Adding it to `apps/mobile` devDependencies would make **every EAS build** install a native image library into the app workspace, so it is rejected. Instead: a small PNG encoder/decoder (8-bit, non-interlaced, colour types 2 and 6 only) over `node:zlib` + a procedural rasterizer, all in TS under `apps/mobile/store-assets/tools/`. Consequence: no `pnpm-lock.yaml` change, no `package.json` dependency change, nothing new to justify under CLAUDE §2.7 (journal still records "zero new deps" explicitly).
- **D2 — Artwork is generated, not a committed binary blob of unknown provenance.** A `generate-assets.ts` CLI rebuilds every PNG byte-for-byte from code. Art = brand-coloured rounded square + a procedurally drawn paw mark (one pad ellipse + four toe ellipses, 3× supersampled). **No text/wordmark is rasterised** (no font rasteriser, and no font dependency) and no third-party/copyrighted material is used. The committed PNGs are flat-colour geometry → single-digit KB each (satisfies "no high-entropy fixtures").
- **D3 — Captions are delivered as data + sidecars, not burned into pixels.** Burning headline text into the screenshot canvas needs a font rasteriser (a real new dependency). The compositor renders the brand background, the caption *band* (correct height/safe area, flat brand colour) and the device-framed capture, and writes the exact caption text next to each PNG (`.txt` sidecar) plus a combined `copy-blocks.md`. The card's deliverable — "marketing string blocks per screenshot" — is delivered as externalised, safety-linted strings; burn-in is a documented design/console step. **This limitation is stated verbatim in the kit README's honest-limits section.**
- **D4 — Device frames are drawn programmatically** (rounded-rect bezel + corner radius + notch/island cut-out as plain geometry), never an Apple/Google device image (copyright/trademark).
- **D5 — The honest split (mirrors T099 §8).** Provable here: asset generation at every required size/spec, spec-pinned dimensions/alpha/byte caps, the compositor exercised end-to-end against synthetic captures produced by our own encoder, caption blocks + safety lint, docs. Founder-only: capturing the 8 real screens from a preview/staging build on a Mac/AVD (`/emulator-test` flow) and re-running the compositor over them. The AC's "from staging build" half closes with a documented founder command, not a fabricated result.
- **D6 — Splash is artwork-only this task.** `expo-splash-screen` is absent from the lockfile (F10); final `splash-icon.png` + `splash-icon-dark.png` + light/dark full-device splash previews are produced, and the exact `plugins` block to add once the package is installed is documented in the README + runbook founder to-dos. `app.config.js` gains no plugin entry.
- **D7 — `android.adaptiveIcon.backgroundColor` changes `#ffffff` → `#1f6350` (brand-700).** The adaptive foreground is a transparent-background cream paw, so the launcher background must be the brand field for the icon to read as the brand mark. This is the only behavioural edit to `app.config.js`. No `monochromeImage` field is added (unverifiable here — `app.config.js` is not typechecked, F11 — so an invented field would pass silently).
- **D8 — Full-resolution compositing is exercised for one shot only in tests.** A 1290×2796 RGBA canvas is ~14 MB; 8 shots × 4 profiles in Jest would be slow. The spec asserts (a) the real profile table's exact store dimensions, (b) one shot composited at every real profile, (c) the whole 8-shot set at a documented `/10` scaled profile list derived from the same table.
- **D9 — Marketing strings live in `apps/mobile/store-assets/marketing-strings.ts`, not `src/strings.ts`.** They are store-listing copy, not app UI copy, and must not ship in the RN bundle. The module is still externalised and i18n-shaped (top-level `en` locale key), and its disclosure line is **imported** from `src/strings.ts` (`strings.check.result.disclaimer(APP_DISPLAY_NAME)`) so the frozen safety wording is single-sourced.

1. **Create the manifest spine.** `apps/mobile/store-assets/tools/asset-manifest.ts`: exported `readonly` array `ASSET_MANIFEST` of `{ id, path (repo-relative), width, height, alpha: boolean, maxBytes, role, spec }` covering all 15 PNGs in §5 (dimensions table in §5.1). 3. **PNG decoder.** `apps/mobile/store-assets/tools/png-decode.ts`: `readPngHeader(bytes) -> { width, height, bitDepth, colourType, interlace }` (IHDR only, cheap — used by the manifest spec) and `decodePng(bytes) -> { width, height, rgba }` supporting bit depth 8, colour types 2/6, interlace 0, all five row filters; every unsupported case throws a message naming the offending field. 4. **Rasterizer + palette.** `apps/mobile/store-assets/tools/raster.ts`: `BRAND_PALETTE` (`field #1f6350`, `fieldDark #0c140f`, `mark #F4EFE6`, `markDark #E7E0D3`, `accent #2f8f74`, `ink #123a30` — values copied from `packages/config/tailwind-preset.mjs`, F9, with a comment citing it) and `renderMark(spec: MarkSpec): Uint8Array` where `MarkSpec = { size, background: string | null, mark: string, markScale, cornerRadiusRatio }`. Geometry (suggested; executor may tune, only the spec assertions bind): unit-square paw = pad ellipse centre (0.50, 0.62) rx 0.26 ry 0.22 + four toe ellipses centres (0.24,0.36) (0.41,0.25) (0.59,0.25) (0.76,0.36), rx 0.105 ry 0.135. Anti-aliasing by 3×3 supersampling. Deterministic: same input → byte-identical output, no randomness, no `Date`.

## 8. Risks (top 5 + the standing ones)

1. **Hand-rolled PNG codec correctness (D1).** A subtle CRC/filter/zlib bug yields files Expo or the stores reject, and our own specs would not notice because they use the same codec. *Mitigation:* only bit-depth-8, non-interlaced, colour types 2/6 are supported, with loud errors otherwise; AC1-a round-trips both colour types; the generated icons are additionally opened by `expo-doctor` in step 20 (an independent reader) and by the founder when uploading. *If the executor finds the codec ballooning past ~120 lines per file, stop and re-plan rather than growing it.*
2. **Caption burn-in (D3).** A reviewer may read "marketing string blocks per screenshot" as pixels-in-image. Delivering strings + sidecars + `copy-blocks.md` instead is a deliberate zero-dependency choice; it is stated in README §9 and here. *If the checker rejects it, the fix is a follow-up card that adds a font rasteriser with a §2.7 justification — not an unplanned dependency added mid-task.*
3. **expo-doctor may not run (network) or may emit unrelated pre-existing warnings.** *Mitigation:* time-boxed, output recorded verbatim, `git status` checked either side, AC1-c named as the standing offline gate, unrelated warnings journalled and **not** fixed (scope creep is a defect, CLAUDE §2.2).
4. **Splash remains unwired (D6/F10)** — `expo-splash-screen` is not in the lockfile, so the final splash artwork is not yet rendered by any build. A reader could call "final splash (all densities)" unmet. *Mitigation:* artwork + full-device previews shipped, exact plugin block documented, founder to-do added; installing an SDK package needs network + a lockfile change that this task deliberately avoids.
5. **`adaptiveIcon.backgroundColor` `#ffffff` → `#1f6350` (D7)** is a visual product decision made by the planner, not the card, and `app.config.js` is not typechecked (F11) so config errors surface only at build time. *Mitigation:* single-value edit, brand-sourced, covered by AC1-c's app.config↔manifest cross-check and step 20's doctor run. Revert to `#ffffff` if the checker prefers no visual change.
6. *(standing)* **Test cost of full-resolution compositing (D8)** — mitigated by the one-full-profile + scaled-set split; if `pnpm --filter mobile test` regresses badly in wall-clock, shrink the scaled profiles further, never delete the assertions.
7. *(standing)* **No simulator/staging build here (F16/D5)** — AC2's real-capture half is founder work by construction; the plan never pretends otherwise.
