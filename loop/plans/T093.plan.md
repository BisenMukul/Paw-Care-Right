# Plan — T093: Accessibility pass

## Objective (from card)

**Do:** Sweep: accessibility labels/roles on interactive elements, dynamic type non-breaking on key screens, contrast tokens audited, touch targets ≥44pt, reduce-motion respected on urgency animations.
**Accept:** a11y lint/test additions pass; manual VoiceOver/TalkBack script results in journal for the 5 core flows.

**Nature of this card:** it is an **audit-first sweep**, not a feature. The repo already carries substantial a11y coverage from SWEEP-1…4 (`touch-targets.test.tsx`, `reduced-motion-gating.test.tsx`, `auth-onboarding-a11y.test.tsx`, `check-flow-a11y.test.tsx`, `sweep4-a11y.test.tsx`, `chat-theme-a11y.test.tsx`, `dual-theme-contrast.test.ts`, `urgency-contrast.test.ts`). The deliverable is therefore: **(a) a written, committed audit that inventories what exists and what is missing; (b) fixes for exactly the gaps that audit finds; (c) permanent guards so the gaps cannot silently reopen; (d) an honest, committed VoiceOver/TalkBack script whose executable half is verified by tests and whose device half is declared a founder to-do.**

**Two hard framing rules the executor may not bend:**
1. **No manual screen-reader run happens in this environment.** There is no simulator, no VoiceOver, no TalkBack. The plan NEVER produces a claim that one was performed. See D2.
2. **The fix list derives from the step-1 audit, not from this plan's guesses.** Every candidate file below is a *permitted* edit, not a *required* one. A file whose audit row reads "no gap" gets a **zero diff**.

## Decisions the planner made (scrutinise these — counter-arguments in "Risks")

- **D1 — `eslint-plugin-react-native-a11y` is OUT; the "a11y lint" half ships as two repo-local guard tests.**
  Reasons, in order: (i) CLAUDE §2 rule 7 — a new dependency needs active maintenance and meaningful adoption; the plugin's rule set targets legacy `Touchable*` JSX shapes and has no NativeWind/`Pressable`-with-`className` awareness, so on this codebase it would fire mostly on patterns we don't use while missing the ones we do (touch-target size expressed as a `min-h-[44px]` *class*, `maxFontSizeMultiplier` numeric bounds, reduced-motion gating, per-flow announcement order); (ii) the house enforcement idiom is already **test-based** (`sweep4-a11y.test.tsx`'s JSON-tree walkers, `touch-targets.test.tsx`'s class assertions) and a checker can prove a test non-vacuous by mutation, which is exactly how this repo's review works; (iii) a lint plugin is static-only and cannot assert what a *rendered* screen announces.
  **Therefore:** `apps/mobile/__tests__/a11y-static-scan.test.ts` (the static/"lint" rules, run by `pnpm test`) + `apps/mobile/__tests__/a11y-sweep.test.tsx` (the rendered per-flow rules). If the checker judges the plugin superior, that is a follow-up card — but adding it here without the above rebuttal being wrong would be a §2.7 violation.

- **D2 — the "manual VoiceOver/TalkBack script results" acceptance criterion is met by SPLITTING it, never by faking it.**
  `docs/qa/a11y-script.md` is a **numbered, per-step script** for the 5 core flows (welcome→sign-in; home→check→result→emergency; activity logging; reminders; chat). Every step row carries one of exactly two tags:
  - `[AUTO: <suite› test name>]` — the step's *executable* half (element has a role; element has a label; labels are in DOM/reading order; state announcements like `selected`/`disabled`/`alert` are present) is asserted by a named test in `a11y-sweep.test.tsx`. The doc↔test correspondence is itself machine-checked (see D5).
  - `[DEVICE-ONLY]` — the part only a real screen reader on real hardware can answer (swipe order under the actual rotor, focus trapping, announcement *audibility*, gesture conflicts, `AccessibilityInfo.setAccessibilityFocus` actually moving focus). These rows carry an unfilled `Result:` column.
  The journal entry states verbatim that **the on-device VoiceOver/TalkBack pass has NOT been run** and is a founder to-do on real hardware, and reports the automated coverage numerically (`N` steps, `M` `[AUTO]`, `N−M` `[DEVICE-ONLY]`). **Any wording that implies a device pass occurred is a defect the checker must fail.**

- **D3 — dynamic type is verified by MECHANISM + a non-crash render, and the plan says out loud what that does and does not prove.**
  Under this workspace's jest (NativeWind 4.2.6 + the `.css` stub) `className` is an **unresolved literal string** — the same fact `design-system.md §7.9` records. So a "render at fontScale 3 and check nothing overflows" test is **impossible**: no layout is computed. Faking one would be vacuous. What IS real and is therefore what we assert:
  1. `allowFontScaling={false}` appears **nowhere** in `apps/mobile/app/**` or `apps/mobile/src/**` (§4.5 law) — static scan.
  2. Chrome text on the four key screens (home, check result, paywall, chat) carries `maxFontSizeMultiplier` and its value is **within `[1.2, 1.5]`** (§4.5: never below 1.2, cap 1.5) — rendered assertion, both bounds, so a stray `0.8` or `3` fails.
  3. No fixed-height text container: no `h-[…px]` / `h-<n>` sizing class on a node whose subtree contains a `Text`, on those four screens (§4.5 "no fixed heights on text containers — min-heights + flex only") — rendered tree walk.
  4. Each of the four screens **renders its key testIDs without throwing** when `useWindowDimensions()` reports `fontScale: 3`. Honest label, in the test's own comment and in the audit doc: *this proves no code path divides by / branches on `fontScale` and crashes; it does NOT prove the layout survives visually — that is a `[DEVICE-ONLY]` row in the script.*
  Precedent for the spy: `care-score-ring.test.tsx` / `today-activity-strip.test.tsx` already `import * as ReactNative` and spy on the module.

- **D4 — reduce-motion on urgency animations: the audit's expected finding is "already compliant", so the deliverable is a REPO-WIDE GUARD plus test coverage for the gated-but-untested sites — not new product code.**
  Planner's pre-audit grep (`withRepeat|entering=|FadeIn|useSharedValue|Animated\.` over `apps/mobile/**` excluding tests) finds **11 animation sites**, and every one already imports `useReducedMotion` from `src/hooks/use-reduced-motion.ts`: `home/animated-gradient-background.tsx`, `home/quick-actions-grid.tsx`, `quick-actions.tsx`, `pet-header-card.tsx`, `skeleton.tsx`, `chat/typing-indicator.tsx`, `intake/intake-form.tsx` (both the `entering` prop **and** the `AUTO_ADVANCE_MS` timer branch and the `scrollTo({animated:!reduced})` call — the FOUNDER-UX-2 pattern), `app/(auth)/welcome.tsx`, `app/pets/[id].tsx`, and the five `app/services/*` preview screens. `home/care-score-ring.tsx` is deliberately **static** (its own comment says so). `_layout.tsx` mounts `<ReducedMotionConfig mode={ReduceMotion.System}/>`.
  **Only 4 of those sites have a reduced-motion test** (`reduced-motion-gating.test.tsx` covers the gradient, both quick-action grids, and `PetHeaderCard`; `skeleton.test.tsx` covers the skeleton). So: extend the gating suite to the uncovered sites, and add a **static scan rule** that any file importing a reanimated animation primitive must also import `useReducedMotion` (allowlist: the hook itself and `app/_layout.tsx`). That converts "currently true" into "cannot regress".
  **The executor must still RE-RUN the grep in step 1 and record the real result.** If it contradicts the above, the code wins and the gap gets fixed.

- **D5 — the Emergency interstitial gets a ZERO-CODE-DIFF, test-only treatment; the disclaimer gets a ZERO-DIFF, evidence-only treatment.**
  `app/check/emergency/[checkId].tsx` reads (planner verified): plain `SafeAreaView`/`ScrollView`/`View`/`Text` + three `PrimaryButton`s. **No reanimated import, no `entering`, no `Animated.*`, no timer.** So the card's "reduce-motion respected on urgency animations" requires **no change there** — the honest deliverable is a *pin*: an assertion in `a11y-sweep.test.tsx` that the emergency screen's rendered tree contains **no node with an `entering` prop and no `Animated`-typed node**, so a future author cannot add an ungated urgency animation to the one screen that must never delay care. This adds zero bytes to the screen and cannot disturb the existing PAWSAATHI-3 no-`dark:` pin, the FIDELITY-2 `bg-red-700` pin, or the `BackHandler` pin (all in `emergency-interstitial.test.tsx`, which must stay green **unmodified**).
  `src/components/vet-disclaimer.tsx` is **not in the file list at all**. Per the T088 item-12 hand-off, its missing `dark:` classes are frozen by PAWSAATHI-3 decision 2 + FIDELITY-2 R6 and pinned by `check-result-snapshot.test.tsx:114-147`. This card contributes **only the contrast evidence** (D6) and the journal hand-off; the aesthetic unfreeze stays a **FOUNDER DECISION**.

- **D6 — contrast audit = inventory first, then extend the existing `dual-theme-contrast.test.ts`; the disclaimer's both-theme evidence lands there by name.**
  `dual-theme-contrast.test.ts` already owns the house WCAG math (self-contained `HEX` map + a preset-drift `describe` that asserts each hex is literally present in `tailwind-preset.mjs`); `urgency-contrast.test.ts` owns the urgency-banner pairs. The executor inventories every token pair actually rendered by the app (grep `text-*`/`bg-*` pairings on the surfaces in scope), diffs it against the pairs already asserted in those two files, and adds a `describe` for **only the un-audited remainder**. Two pairs are named up front and are mandatory:
  - **`VetDisclaimer` in BOTH themes** — `text-brand-900 (#123a30)` on `bg-brand-50 (#f2f8f6)`, asserted under a test name that says *both OS schemes*, with a comment recording **why one number answers both**: the component carries no `dark:` token and its container is **opaque**, so the rendered pair is byte-identical under either `Appearance` value; the surrounding page being `surface-page-dark` cannot bleed through. Verdict: **AA/AAA-compliant in both themes ⇒ the missing `dark:` styling is aesthetic, not an a11y defect.** This exact sentence is what the audit doc and the journal hand-off carry.
  - **Emergency interstitial** — white on `red-700 / red-800 / red-900`, asserted as **theme-invariant** (identical hex under either scheme, per PAWSAATHI-3 decision 1). Evidence only; the screen is untouched.

- **D7 — product edits are bounded to five mechanical shapes, and only where the audit records a gap.** Permitted deltas: (1) add `accessibilityRole="button"` / `accessibilityLabel` / `accessibilityState` to an interactive element that lacks one; (2) add `min-h-[44px]` (the sanctioned arbitrary, §7.2) or `hitSlop={{top:8,bottom:8,left:8,right:8}}` to a sub-44pt target; (3) add `accessibilityRole="header"` to a screen/section title; (4) add `maxFontSizeMultiplier={1.5}` to chrome text; (5) add `accessibilityRole="alert"` to an error/offline banner that lacks it. **Never** a copy change, a class change other than the `min-h-[44px]` addition, a structural change, a re-order, or a logic change. New a11y label strings are **appended** to `src/strings.ts` — no existing key edited (§6 no-hardcoded-strings).

- **D8 — snapshot handling is declared, not discovered.** Prop-only additions still move `.snap` files. The only snapshots this card may re-record are named in "Files" below, and each re-record must be a **pure prop insertion** — the checker should be able to read the `.snap` diff and see only `accessibilityRole=`, `accessibilityLabel=`, `accessibilityState=`, `maxFontSizeMultiplier=`, `hitSlop=` lines added (plus `className` gaining exactly `min-h-[44px]`). Any snapshot delta containing changed text, removed nodes, or reordered children is a defect. If the audit finds **no** gap on a snapshot-bearing surface, **no `.snap` may move at all** — that is the preferred outcome.

## Tests to write (map to acceptance criteria)

### AC1 — "a11y lint/test additions pass"

**`a11y-static-scan.test.ts`** (node-env source scan; `repoRoot = path.resolve(__dirname, "../../..")`):
- › **"no source file disables font scaling"** — scans every `.tsx` under `apps/mobile/app` + `apps/mobile/src`; asserts the scanned-file list is non-empty and that **no** file contains `allowFontScaling={false}` or `allowFontScaling: false`. (§4.5)
- › **"every file using a reanimated animation primitive also imports useReducedMotion"** — a file is "animating" if it matches `/withRepeat|withSpring|withTiming|entering=|exiting=|\bFadeIn|useSharedValue/`; asserts the animating-file set is **non-empty** and that each such file matches `/use-reduced-motion/`. Allowlist (with a comment naming why): `src/hooks/use-reduced-motion.ts`, `app/_layout.tsx` (mounts `ReducedMotionConfig` only).
- › **"no bare hex color literal is introduced in the swept files"** — for the files this card actually edits: asserts no new `#rrggbb` string appears in a `className`/style position (§1.6 last bullet). Scope: assert the rule over the D7 candidate list only, so it cannot fail on pre-existing sanctioned `Ionicons color` call sites — and assert that candidate list is non-empty.
- › **"every [AUTO] tag in docs/qa/a11y-script.md names a test that exists in a11y-sweep.test.tsx"** — step 15's rule; both extracted sets asserted non-empty, then subset containment with the missing names in the failure message.

**`a11y-sweep.test.tsx`** — per flow (5 `describe`s, one per core flow), each with at minimum:
- › **"every interactive element exposes a role or a label"** — walks the rendered tree for host nodes carrying a function-valued `onPress` (use `screen.UNSAFE_root.findAll(n => typeof n.type === "string" && typeof n.props.onPress === "function")`; if that yields zero on a screen known to have buttons, fall back to finding by the `Pressable` composite type and **document which variant was used in a comment**). Asserts `found.length` is **≥ an explicit per-screen minimum written as a literal** (e.g. `expect(pressables.length).toBeGreaterThanOrEqual(4)`), then that each has `accessibilityRole` **or** a non-empty `accessibilityLabel`.
- › **"the screen title is a header"** — `accessibilityRole === "header"` on the title node.
- › **"selected/disabled state is exposed"** — where the flow has chips/toggles: `accessibilityState` present and matching the visual state (both a selected and an unselected element asserted, so a hardcoded `{selected:true}` fails).

## Risks & the decisions the planner made (for the checker to scrutinise)

- **R1 (biggest — a vacuous walker).** A tree walker that matches zero nodes passes every assertion trivially. This is the classic failure mode for "sweep" a11y tests. Mitigation is structural, not advisory: **every** walker-based assertion must be preceded by a literal non-emptiness/minimum-count assertion (`>= <number literal>`), and M3/M5 are designed to be killed by that guard. **Checker: for each new walker test, delete its body's rule assertion and confirm the count assertion alone still fails on an empty match — if a walker has no count assertion, fail the task.**
- **R2 (D1 — rejecting the lint plugin).** Counter-argument the checker should weigh: a real ESLint plugin runs on *every* future file automatically, while a test-based scan only covers the globs it was told about. Accepted anyway because the scan globs are `apps/mobile/app/**` + `apps/mobile/src/**` (i.e. everything), because the plugin's rules do not understand this codebase's `className`-encoded touch targets, and because §2.7 requires justification for a dep whose value here is partly duplicated. If the checker disagrees, the correct remedy is a **follow-up card**, not an in-card dep addition.
- **R3 (D2 — the acceptance criterion literally says "manual … results in journal").** This plan cannot satisfy the criterion as literally written, and says so rather than simulating it. The substitute (committed script + automated executable half + explicit founder to-do) is the honest maximum. **Checker: if you judge this insufficient, the correct verdict is "blocked pending device access", not "pass with a fabricated result" — and if the journal or docs contain any claim of a device run, fail immediately.**
- **R4 (D3 — the fontScale-3 test is weak).** It proves only "no crash". Stated explicitly in the test comment, the audit doc's honesty section, and here. The layout question is a `[DEVICE-ONLY]` script row. The plan deliberately does not dress this up as a layout test.
- **R5 (D7/D8 — snapshot churn).** Prop-only additions still move four snapshot files. Risk: a sloppy re-record hides an unintended structural change. Mitigation: D8's pure-prop-insertion rule plus the explicit `git diff` command above. **Preferred outcome is zero snapshot movement**; if the audit finds no gap on a snapshot-bearing surface, none should move.
- **R6 (the audit could find a genuinely failing contrast pair).** If it does, the tempting fix is a palette change — which would reverse ratified design decisions and churn every snapshot. The plan forbids that: record the finding, name the affected surface, hand it to the founder/next card. **Checker: any diff in `packages/config/tailwind-preset.mjs` is an automatic fail.**
- **R7 (the emergency screen's a11y is imperfect but frozen).** Its titles carry no `accessibilityRole="header"` and its go-now badge no `alert` role. Planner's judgement: the screen is a full-screen takeover with linear reading order and three labelled buttons, so a screen reader still reads it correctly top-to-bottom; adding roles would touch a zero-diff-pinned safety surface for a marginal gain. **Recorded as an audit finding + a `[DEVICE-ONLY]` script row**, not fixed. If the checker judges the header roles genuinely necessary for safe comprehension, that is a **sanctioned-delta follow-up card with founder sign-off**, not a silent edit here.
- **R8 (scope creep).** This card touches ~25 candidate files in a codebase-wide sweep — the highest scope-creep risk in the phase. The D7 five-shape whitelist plus the audit-derived fix list are the containment. **Checker: any product edit that is not one of the five D7 shapes, or whose file has no GAP row in `docs/qa/a11y-audit.md`, is a defect.**
