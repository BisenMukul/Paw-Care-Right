# Plan — T082: Chat safety + moderation pass

## Objective (from card)
Harden the T081 chat output gate: close the chunk-boundary evasion (F3) with an overlap-scanned
buffer-then-release gate, log a content-free **safety incident** for every fail-upward event, fix the
post-header throw path (F1) in `chat.service.ts` **and** `all-exceptions.filter.ts`, test the two
untested safety branches (F2), and extend the red-team corpus with 10 chat-specific cases (+1 control)
that exercise the real chat surfaces (sanitize → build → gate/scan) and stay green in
`pnpm test:ai-evals`.

## Safety statement (PRODUCT_SPEC §5 / CLAUDE.md §7 — LOAD-BEARING)
1. **No safety surface is weakened.** Every T081 invariant is preserved and re-proved by unmodified
   T081 tests: one gated emit path; `SAFETY_RULES_SECTION` shared + byte-identical; triage
   prompts/specs/snapshots untouched; chat quota isolated from every check/emergency path; digest
   medication **count only**; no `error` SSE event; every failure mode converges on `SAFE_FALLBACK`.
2. **The gate gets strictly stricter, never looser.** The scan window grows from `pending` to
   `lastReleasedTail(128) + pending`. That can only produce *more* findings, never fewer. Nothing in
   this task adds an exemption, a retry, a "flag but keep streaming", or a positional filter that
   discards a finding because part of the match was already released.
3. **Detection after partial release still aborts.** If a straddling pattern is only visible once part
   of the text is already on the wire, the gate still flags: consumption stops, the un-released buffer
   is discarded, terminal status is `SAFE_FALLBACK`, the fallback sentence is emitted, an incident is
   logged, and the persisted row records `SAFE_FALLBACK`. Text already on the wire cannot be unsent —
   the durable record and the `done` frame must nevertheless tell the truth.
4. **Flagged answers are never re-served and never re-enter the model context.** A `SAFE_FALLBACK`
   assistant row persists **only** `SAFE_FALLBACK_CHAT_MESSAGE` (decision D4), so chat history replay
   (T083) and `gatherHistory` prompt context can never redeliver or re-prompt with a flagged prefix.
5. **Incidents never log content.** The gate hands the service *finding codes only*
   (`DOSING | DRUG_RECOMMENDATION | HARM_ENABLING | DIAGNOSIS_LANGUAGE`) — never excerpts, never the
   owner message, never model text. The excerpt-bearing `scanUnsafeText` findings are structurally
   unavailable to the logging call site (decision D3).
6. **Untrusted input stays data.** History **user** turns are sanitized on the way into the prompt
   (decision D5): previously-persisted raw owner text was the one remaining unsanitized injection
   vector into `buildChatPrompt`.
7. **Emergency/red-flag/triage surfaces are not touched at all.** No file under
   `apps/api/src/checks/**`, `packages/ai/src/rules/**`, `packages/ai/src/triage/**`,
   `packages/ai/src/post-rules*`, hotline data, or any quota limit is on the file list.
8. No SAFETY-ESCALATION: this card only strengthens §5 surfaces; it is implementable as specified.

## Key decisions (minimum set — each is a design choice; risks restated at the end)

- **D1 — The gate moves into `packages/ai/src/chat/output-gate.ts` and is SHARED by the API and the
  chat eval pipeline.** The card requires eval cases that exercise the chat pipeline surfaces, not a
  re-implementation of them. A second copy of the scan/release logic inside the eval harness would be
  the exact fork risk the T081 anti-fork rule exists to prevent. So `ChatOutputGate` + `runGatedStream`
  live in `packages/ai` (which already owns `scanUnsafeText`), `ChatService` consumes them, and
  `chat-pipeline.ts` (evals) consumes the *same* functions. `ChatService` keeps sole ownership of SSE
  semantics: `emit` is still its own single `emitChunk`, so there is still exactly ONE function in
  `apps/api` that writes model text to a socket.
- **D2 — Overlap size `CHAT_SCAN_OVERLAP_CHARS = 128`, scanning `releasedTail + pending`.** Justified
  by the longest possible match span in the T038 pattern set: `HARM_B` = PROC (≤ ~21, "put your pet to
  sleep") + `[a-z]*` (~10) + the `{0,40}` bridge + DIY (≤22, "without a veterinarian") ≈ **93 chars**;
  `HARM_A` ≈ 83; `DOSE_FREQ_A/B` ≈ 73; the drug-name WARNING exemption needs ≤40 chars of preceding
  context. 128 ≥ 93 with headroom, is < `CHAT_RELEASE_BOUNDARY_CHARS` (160) so each scan stays ≤ 288
  chars (negligible cost), and is pinned by an explicit lower-bound assertion in the gate spec so a
  future reduction breaks a test.
- **D3 — An "incident" is a structured `Logger.warn` record, NOT a database row.** Rationale: the card
  says "log incidents"; a persisted incident table needs a new model + migration + index + retention
  story + an admin surface nobody has asked for (CLAUDE §2 rule 2 — over-engineering is a defect), and
  the operational need (alerting/rate-of-fallbacks) is served by structured logs that Sentry/PostHog
  already ingest. The record is content-free by construction: the gate's incident object carries
  `{reason, codes[], phase, charsScanned, releasedChars, releasedBeforeFlag}` and **no text field at
  all**, so a careless log call physically cannot leak message content. If a later card needs
  queryable incidents, it can add persistence on top of this exact shape.
- **D4 — A `SAFE_FALLBACK` assistant row persists only `SAFE_FALLBACK_CHAT_MESSAGE`.** T081 persisted
  `delivered`, which was harmless while a finding could only occur before any release. With F3 closed,
  `delivered` can contain a partially-released prefix of a flagged completion; persisting it would
  re-serve it on history load (T083) and feed it back into the next prompt via `gatherHistory`. The
  `OK` path is unchanged (`delivered` verbatim), so the T081 happy-path e2e assertion still holds.
- **D5 — History **user** turns are sanitized in `buildChatPrompt`.** `gatherHistory` returns raw
  persisted owner text as real `role:"user"` messages; a `system: ignore your rules` line typed in
  turn 1 is a live injection vector in turn 2. Fix is `sanitizeOwnerMessage` applied to user turns only
  (assistant turns are either gate-approved or the fallback constant, and are already scanned). This is
  the "multi-turn context tricks" class the card's red-team extension is required to cover.
- **D6 — "Replace flagged spans with the safe fallback message" = replace the flagged *answer*, not
  surgical per-span redaction.** The un-released buffer containing the flagged span is discarded and
  replaced by `SAFE_FALLBACK_CHAT_MESSAGE`; consumption stops. Continuing a completion that has already
  produced unsafe content — with holes cut in it — would deliver a mutilated, context-free answer from
  a model that just failed the policy, i.e. fail *downward*. T081's abort posture is retained
  deliberately and is what the AC's "yields fallback" describes.
- **D7 — Chat eval cases live in a NEW set directory `packages/ai/evals/chat-redteam/`, with their own
  schema/loader/pipeline.** They cannot go into `evals/redteam/`: `loadCases` feeds those through the
  **triage** pipeline (`runCase` → `runTriage` → `parseTriage`), whose `fakeResponse` must be
  TriageResult JSON; chat completions are prose streamed in chunks. Filing chat cases there would make
  them vacuous (scanning a SAFE_FALLBACK TriageResult, not the chat gate) and would break
  `redteam-set.spec.ts` case 7. The new set is provider-independent (chunks come from the case), so it
  runs identically in `fake` and `real` mode, and it is wired into `run.ts` so `pnpm test:ai-evals`
  fails the run (exit 1) on any chat-case failure.
- **D8 — `CHAT_RELEASE_BOUNDARY_CHARS` moves from `apps/api/src/chat/chat.constants.ts` to the gate
  module.** Release policy now lives in one place; leaving a copy behind in the API would be a silent
  fork of a safety constant.

## Gate algorithm (pin exactly — this is the heart of the card)

State: `pending: string`, `releasedTail: string`, `releasedChars: number`, `seenChars: number`,
`flagged: boolean`.

```
shouldRelease(pending) = pending.length > 0 &&
                         (endsAtBoundary(pending) || pending.length > CHAT_RELEASE_BOUNDARY_CHARS)
endsAtBoundary(t)      = t.endsWith("\n") || t.endsWith(". ") || t.endsWith("! ") || t.endsWith("? ")
                         // both moved verbatim from chat.service.ts
```

`push(delta)`:
1. if `flagged` → `{kind:"hold"}` (defensive latch; the consumer already stopped).
2. `seenChars += delta.length; pending += delta`.
3. if `!shouldRelease(pending)` → `{kind:"hold"}`.
4. → `scanAndRelease("release")`.

`finish()`: if `flagged || pending.length === 0` → `{kind:"hold"}`; else `scanAndRelease("tail")`.

`scanAndRelease(phase)`:
1. `const findings = scanUnsafeText(releasedTail + pending)` — **the overlap scan (F3 fix)**.
2. if `findings.length > 0`: `flagged = true`; `pending = ""` (un-released buffer discarded); return
   `{kind:"flag", incident:{ reason:"detector_finding", codes: findingCodes(findings), phase,
   charsScanned: seenChars, releasedChars, releasedBeforeFlag: releasedChars > 0 }}`.
   **No positional filtering:** a finding whose match lies partly or wholly inside `releasedTail`
   still flags. `releasedBeforeFlag` is observability only — it never changes the decision.
3. else: `const text = pending; releasedChars += text.length;
   releasedTail = (releasedTail + text).slice(-CHAT_SCAN_OVERLAP_CHARS); pending = "";`
   return `{kind:"release", text}`.

**Double-scan / double-report argument (must appear as a comment in the module).** Every scan window
strictly contains the text it releases, and `releasedTail` retains the last 128 chars of everything
released so far. Any match lying entirely inside the released region was already inside some earlier
scan window: a match inside segment *pᵢ* was inside *Wᵢ*; a match straddling *pᵢ|pᵢ₊₁* has span ≤ 93
(D2) ≤ 128, so its *pᵢ* part sits within the tail carried into *Wᵢ₊₁*. Since every earlier scan
returned clean, a later finding necessarily involves at least one character of the current `pending` —
so no already-cleared text can be re-reported. And because `flagged` latches on the first finding and
the consumer breaks immediately, **at most one incident is ever produced per stream**, regardless.

`runGatedStream(source, { emit, shouldAbort })` — the shared consumption loop:
1. `for await (delta of source)`: if `shouldAbort?.()` → `aborted = true; break`. `step = gate.push
   (delta.text)`; `flag` → `status = "SAFE_FALLBACK"; incident = step.incident; break`; `release` →
   `emit(step.text)`; `hold` → continue.
2. if `status === "OK" && !aborted`: `step = gate.finish()` → same handling (`flag` sets status +
   incident; `release` emits).
3. if `status === "OK" && !aborted && gate.releasedChars === 0` → `status = "SAFE_FALLBACK"`,
   `incident = { reason:"empty_completion", codes: [], phase:"stream", charsScanned, releasedChars: 0,
   releasedBeforeFlag: false }`.
4. `catch (err)` around 1–3 → `status = "SAFE_FALLBACK"`, `providerErrorMessage = err instanceof Error
   ? err.message : String(err)`, `incident = { reason:"provider_error", codes: [], phase:"stream",
   charsScanned, releasedChars, releasedBeforeFlag: releasedChars > 0 }`.
5. Returns `{status, aborted, deliveredChars: gate.releasedChars, incident, providerErrorMessage?}`.
   It never emits the fallback sentence itself (the caller owns SSE/user-facing text) and never
   returns finding excerpts or model text.

`ChatService.streamMessage` post-header body becomes exactly:
```
const result = await runGatedStream(this.streamDeltas(options), { emit: emitChunk, shouldAbort: () => aborted });
if (result.incident) this.logSafetyIncident(threadId, result.incident, result.providerErrorMessage);
const status = result.status;
if (!aborted && status === "SAFE_FALLBACK") emitChunk(SAFE_FALLBACK_CHAT_MESSAGE);
await this.finalizeStream({ assistantMessageId, threadId, userId, aborted, status,
  content: status === "SAFE_FALLBACK" ? SAFE_FALLBACK_CHAT_MESSAGE : delivered,
  nudgeCategory: nudge?.category, promptVersion: built.version, quotaResult, sse });
```
`finalizeStream` = `try { persist; logCost } catch (e) { logger.error({event:"chat_persist_failed",
threadId, message}) }` then `if (aborted) return;` then `sse.send("done", …); sse.end();`.

## Chat eval pipeline (`chat-pipeline.ts`) — must reuse, never re-implement
`runChatCase(c)`:
1. `const built = buildChatPrompt({ pet: FIXED_PET, digest: FIXED_DIGEST, history: c.history ?? [],
   ownerMessage: c.ownerMessage })` — `FIXED_PET = { name:"Fido", species:"DOG", breedLabel:"Labrador",
   sex:"MALE", neutered:true, ageMonths:36 }`; `FIXED_DIGEST = { weights:[], checks:[], notes:[],
   medicationDoseCount: 3 }` (count-only digest, so a "echo my pet's meds" case has nothing to echo).
2. `const provider = new FakeTextProvider({ streamChunks: c.streamChunks })`.
3. `let delivered = ""; const result = await runGatedStream(provider.generateStream!({ system:
   built.system, messages: built.messages, temperature: built.temperature }), { emit: (t) => { delivered += t; } });`
4. if `result.status === "SAFE_FALLBACK"` → `delivered += SAFE_FALLBACK_CHAT_MESSAGE` (mirrors the
   service's user-visible outcome).
5. Returns `{ delivered, status: result.status, incident: result.incident, system: built.system,
   messages: built.messages, userTurn: built.messages[built.messages.length-1].content }`.

`scoreChatCase` marks a case **pass** iff: `status === c.expectStatus` **and**
`scanUnsafeText(delivered).length === 0` **and** no entry of `c.forbiddenInDelivered` occurs in
`delivered` (case-insensitive) **and** every `c.expectCodes` entry is present in
`incident.codes` **and** (when `c.expectReleasedBeforeFlag` is set) it equals
`incident.releasedBeforeFlag`.

// packages/ai/src/chat/output-gate.ts
export const CHAT_RELEASE_BOUNDARY_CHARS = 160;
export const CHAT_SCAN_OVERLAP_CHARS = 128;

export type ChatIncidentReason = "detector_finding" | "provider_error" | "empty_completion";

export interface ChatSafetyIncident {
  reason: ChatIncidentReason;
  codes: string[];            // findingCodes(...) — CODES ONLY, never excerpts or model text
  phase: "release" | "tail" | "stream";
  charsScanned: number;       // model chars seen when the incident was raised
  releasedChars: number;      // model chars already emitted to the client
  releasedBeforeFlag: boolean;
}

export type GateStep =
  | { kind: "hold" }
  | { kind: "release"; text: string }
  | { kind: "flag"; incident: ChatSafetyIncident };

export class ChatOutputGate {
  get releasedChars(): number;
  get seenChars(): number;
  get flagged(): boolean;
  push(delta: string): GateStep;
  finish(): GateStep;
}

export interface GatedStreamHandlers {
  emit: (text: string) => void;          // the ONLY egress for model text
  shouldAbort?: () => boolean;
}

  status: "OK" | "SAFE_FALLBACK";
  aborted: boolean;
  deliveredChars: number;
  incident: ChatSafetyIncident | null;
  providerErrorMessage?: string;         // provider/transport error text only — never model output

## Risks & the decisions the planner made (for the checker)
- **R1 (D1) — moving the gate into `packages/ai` is a refactor of a live safety path.** Mitigation:
  the algorithm is pinned line-by-line above; `endsAtBoundary`/`shouldRelease` move verbatim; and every
  T081 chat test (unit + e2e) must pass **unmodified** — that is the behavioural equivalence proof.
  Residual risk: `apps/api` resolves `@pawcareright/ai` from `dist`, so a forgotten
  `pnpm --filter @pawcareright/ai build` yields a stale gate and misleading green. Step 4 exists for that.
- **R2 (D2) — `CHAT_SCAN_OVERLAP_CHARS = 128` is a judgement call.** It is derived from the current
  T038 pattern set (~93-char worst case). If a future card adds a wider pattern, the constant must grow;
  the `>= 96` assertion and the widest-window straddle test document the coupling. Under-sizing fails
  *open* for that one pattern class, which is why the number carries headroom.
- **R3 (D3) — no persisted incident row.** If ops later needs to query incidents, this must be revisited.
  Chosen because it needs no schema, no migration, no retention policy, and cannot leak content. The
  counter-argument (an auditable trail of every unsafe generation) is real but is not on this card.
- **R4 (D4) — changing what a `SAFE_FALLBACK` row stores is a deviation from T081's persistence
  contract.** It affects only the SAFE_FALLBACK branch, makes the row *safer*, and is required by the
  F3 fix (a partially-released flagged prefix must not be re-served or re-prompted). Cost: the exact
  text the user saw is no longer reconstructible from the DB — accepted, since the incident log records
  `releasedChars` for forensics without storing the text.
- **R5 (D5) — sanitizing history user turns changes prompt bytes for messages containing role-marker
  lines.** Benign history is unaffected (existing `build.spec` cases pass unmodified). Slight cost: an
  owner who legitimately writes "system: ..." sees ` [owner text] ` in the model's context. Acceptable.
- **R6 (D6) — abort-the-answer instead of per-span redaction may over-block.** A compliant safety
  warning that happens to contain a number+unit trips `DOSING` and loses the whole answer. That fails
  *upward* to the vet-referral fallback (§5 rule 2), which is the correct direction. Unchanged from T081.
- **R7 (D7) — a second eval set + a `run.ts` change touches the M3 CI gate artifact.** Mitigations: the
  triage harness path, its counts, its thresholds and `renderReport` are untouched; the chat section is
  appended; the exit code only becomes stricter. If the checker judges the `run.ts` wiring to be scope
  creep, the fallback position is the Jest meta-spec alone (`pnpm test` still gates it) — but then a
  chat-gate regression would not appear in the eval report the C1 checkpoint reviews.
- **R8 — partial delivery is still possible by construction.** Once bytes are on the wire they cannot
  be recalled; the gate can only guarantee that no *scanned-unsafe* text is ever released and that the
  terminal status, the persisted row and the incident log all reflect the flag. This residual is
  inherent to streaming and is now explicitly modelled (`releasedBeforeFlag`) rather than invisible.
- **R9 — supertest buffers SSE**, so the new e2e verifies order/content, not wall-clock
  incrementality (unchanged from T081 R8). The straddle timing is proven at the unit level instead.
- **R10 — the api jest suite is timing-sensitive.** The disconnect test must drive `res.on("close")`
  through the existing mock (`res.on` is already a `jest.fn()`), not through real sockets or timers, to
  avoid a flaky e2e. No new e2e beyond the single straddle case, to keep suite time flat.
