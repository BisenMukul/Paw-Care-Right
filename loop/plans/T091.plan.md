# Plan — T091: Privacy: consent, export & deletion

## Objective (from card)
Ship the three GDPR/CCPA surfaces promised by SPEC §5.6: a real analytics opt-out (mobile switch → client emission off **and** server flag → server emission off), `POST /me/export` (async worker → JSON bundle + link stub in the dev log), and `DELETE /me` (grace-period soft delete → scheduled hard-cascade job that erases DB rows **and** S3 objects), with honest confirmation UX.

This is an **L** card. It is split into two execution blocks. **BLOCK A (steps 1–33) is API + shared types and is independently green/committable.** If the executor stalls, stop at the end of BLOCK A with all gates green rather than half-finishing BLOCK B (steps 34–44, mobile + web policy alignment).

## Decisions the planner made (scrutinise these — details + counter-arguments in "Risks")

- **D1 — Household semantics of `DELETE /me`.** The codebase has a hard invariant (`households.service.ts:49-62`): *every user has exactly one `Membership` at all times*. So there are exactly three cases:
  - **(a) Caller is a MEMBER of someone else's household → allowed.** Erase the user + their personal rows + the `SymptomCheck`s and `ChatThread`s **they created** (with results/follow-ups/messages/audit rows/their orphaned photo objects). The household, its pets, health logs and reminders survive — they belong to the owner.
  - **(b) Caller is OWNER and is the household's *only* membership → allowed.** Full household cascade (pets, checks, health logs, reminders, invites, subscription), then the user.
  - **(c) Caller is OWNER and the household has ≥1 other membership → BLOCKED, `409 CONFLICT`.** Honest copy: "You own a shared household. Ask the other members to leave (Settings → Family → Leave household), then delete your account — or email {privacy contact} and we'll handle it for you." Rationale: auto-transferring ownership silently hands another human billing control + all household data; cascading the household deletes *another person's* pets. Both are worse than an honest block. This mirrors the existing `leaveHousehold` OWNER-block precedent (`households.service.ts:191-193`) and keeps T086's shipped email escape hatch true.
- **D2 — Grace period = 30 days**, exported as `ACCOUNT_DELETION_GRACE_DAYS` in `packages/types` (one constant, read by api + mobile + the web policy copy). The shipped T086 policy says only "within a reasonable period" — it pins no number — so this is a fresh decision, flagged for C3 counsel. Soft-delete sets `User.deletionScheduledAt = now + 30d`, revokes **all** refresh tokens, deletes **all** `Device` rows (no push to a closing account), and forces `analyticsOptOut = true`. **A successful sign-in during the grace window cancels the pending deletion** (clears `deletionScheduledAt`) — disclosed verbatim in the confirmation copy before the user confirms.
- **D3 — `AiAuditLog` rows are HARD-DELETED, not tombstoned.** The cascade collects the user's `checkId`s/`threadId`s *before* deleting those rows, then `deleteMany({ checkId: { in } })` / `({ threadId: { in } })`. Reason: (i) Art.17 erasure is unambiguous and trivially test-provable; (ii) "append-only" in T090's schema comment means *no UPDATE path exists anywhere* — nulling the ids would introduce the very first UPDATE path into that model and break its documented exactly-one-of-`checkId`/`threadId` invariant, whereas a **bulk DELETE path already exists** (`AiAuditRetentionService`); (iii) the audit rows carry no content and self-expire at 90 days, so the security/abuse value forgone is bounded. Cost/abuse aggregates are unaffected — `CostLogService` writes only global daily Redis counters (`pawcareright:cost:daily:*`), never per-user rows (`quota.util.ts:26-29`), so there is no per-user CostLog table to erase.
- **D4 — Export bundle scope.** Household-scoped rows the caller can legitimately see (their one household's pets, health logs, reminders + events) + user-scoped rows (checks they created with results/follow-ups, chat threads/messages they created, notification prefs, subscription summary, devices *minus the push token*). **Never** another household's rows and **never** another member's email/user record. Photos ship as `{ key, downloadUrl }` with 7-day presigned GETs.
- **D5 — Server-side consent gate.** `AnalyticsService` gains `async captureForUser(userId, event, props)` which reads `User.analyticsOptOut` and returns early when true. There are exactly **two** server emit sites (`workers/check-runner.processor.ts:93`, `billing/rc-webhook.service.ts:103`) — both already async and off the request hot path — so no cache/new infra is needed.
- **D6 — Export objects expire.** Bundles live at `exports/<userId>/<exportId>.json`; the same daily sweep that hard-deletes due accounts also purges `AccountExport` rows + objects older than `ACCOUNT_EXPORT_RETENTION_DAYS = 7` (matches the link TTL). Without this, a full personal-data JSON would sit in S3 forever, directly contradicting the shipped retention promise.

## Risks & the decisions the planner made (for the checker to scrutinise)

- **R1 (D1c — blocking an owner's deletion).** Refusing an erasure request is legally sensitive: GDPR Art.17 is a right, not a courtesy. Mitigations: the block is narrow (only an owner with live co-members), the copy gives two concrete routes (members leave, or the privacy email that the shipped T086 policy already advertises), and the alternatives are worse (silent ownership transfer = handing a stranger billing + data; household cascade = deleting another person's pets). Flag for C3 counsel. **Checker: verify the 409 copy is honest and non-blaming, and that a sole owner and a member are both genuinely unblocked.**
- **R2 (D2 — 30 days is a fresh number).** The shipped policy pins no figure. 30 days is the market norm and inside the GDPR "one month" expectation, but it is a counsel decision. It is a single exported constant so C3 can change it in one place. Risk if the web copy hardcodes "30" instead of importing the constant → step 41 requires the import.
- **R3 (D2 — sign-in cancels deletion).** An accidental cancel would silently keep an account the user asked to erase. Mitigated: soft-delete revokes all refresh tokens and deletes devices, so no silent background refresh can trigger it; a re-sign-in requires an email OTP or an Apple/Google tap; and the cancel behaviour is stated in the confirmation copy *before* the user confirms. **Checker: verify the copy states it and that the test proves a normal sign-in for an undeleted user writes nothing extra.**
- **R4 (D3 — hard-deleting audit rows).** This permanently removes safety/abuse evidence for a user who deletes their account, which an abuser could exploit (misuse, then delete). Counter-weight: rows expire at 90 days anyway, contain no content, and the alternative (nulling ids) introduces the first-ever UPDATE path into a model documented as having none while breaking its exactly-one-of invariant. **Checker: this is the decision most worth challenging — if you prefer tombstoning, fail and say so.**
- **R5 (D4 — 7-day presigned photo links inside the bundle).** Anyone holding the bundle holds working photo links for 7 days. Accepted: it is the user's own export, the bundle object itself is presigned and purged after 7 days (D6), and the alternative (5-minute links) makes the export useless.
- **R6 (erasure ordering: S3 before DB).** If the process dies between the S3 phase and the DB commit, rows survive pointing at missing objects (photo views 404) until the job retries. The reverse order would leave *unreferenced personal photos* in the bucket with no pointer to find them again — strictly worse for privacy. Retry with backoff + idempotent erase resolves the window.
- **R7 (shared photo keys in the member case).** If a member's check photo key is also a surviving `Pet.photoKey` or health-log key, deleting it would corrupt the household's data. Step 14 requires an explicit surviving-reference set; if the executor cannot compute it reliably, it must skip user-only S3 deletion entirely and stop with a blocked note rather than guess.
- **R8 (server consent read on the emit path).** `captureForUser` adds one indexed primary-key read per server-side event. Both call sites are async and off the request hot path; still, it is a new DB read in the check-completion worker. Failing closed on a read error means a Redis/DB blip loses analytics events — the correct trade for a consent gate.
- **R9 (`AccountExport` retention sweep, D6).** Slight scope expansion beyond the card's literal words, justified because leaving full personal-data JSON bundles in S3 forever would contradict the retention paragraph this same task is updating.
- **R10 (test-environment coupling).** The AC1 suite needs real Postgres + MinIO + Redis, like `test/photos.e2e-spec.ts`. If MinIO is unavailable in CI, the storage assertions cannot be faked — the executor must **not** downgrade them to mocks; it should stop and write `loop/plans/T091.blocked.md`.
- **R11 (unverified assumptions the executor must check, not assume).** (i) whether OTP and social sign-in share one session-issuing method (step 31); (ii) whether `useAuthStore.signOut()` tolerates an already-revoked refresh token (step 39); (iii) whether `apps/web` can import `@pawcareright/types` in the legal string module under the Next build (step 41). Each has a stated fallback in its step — none is a licence to improvise a different feature.
