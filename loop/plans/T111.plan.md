## 2. Design (minimum decisions; each restated in §7 for scrutiny)

**D1 — Web auth: HTTP Basic at the Next middleware layer, fail-closed, no session.**
`apps/web/middleware.ts` (must sit at the app root, since `app/` is at the root) with `export const config = { matcher: ["/admin", "/admin/:path*"] }`. All logic lives in pure, jest-testable functions under `apps/web/src/admin/` (middleware.ts stays a ~10-line delegator, because jest `roots` is `src` only).
- Credentials from two env vars: `ADMIN_ALLOWED_EMAILS` (comma-separated) and `ADMIN_DASHBOARD_PASSWORD` (one shared secret).
- **Fail-closed:** if either is missing/empty/whitespace, or the allowlist parses to zero entries, every `/admin*` request is 401 regardless of what the caller sends (the T117 `AdminTokenGuard` D6 precedent).
- Username = the operator's email, compared **case-insensitively after trim** against the allowlist; password compared **constant-time**. A failure never reveals which half failed.
- Constant-time compare uses `globalThis.crypto.subtle.digest("SHA-256", …)` on both sides then a fixed-length byte loop — available in the Edge runtime **and** Node ≥18 (jest `testEnvironment: node`), so no runtime pinning and no `node:crypto` (Edge-unavailable). Same "hash both sides, then compare" shape as `AdminTokenGuard`, so a length difference leaks nothing.
- 401 carries `WWW-Authenticate: Basic realm="admin", charset="UTF-8"` and an empty body.
- No cookie, no session, no sign-in page, no redirect: basic-auth per request is the whole mechanism.

**D2 — Data path: web server component → API `/v1/admin/*` behind the existing `AdminTokenGuard`.** The API owns every query (indexed, bounded, paginated per CLAUDE §6). The web app fetches **server-side only** (`fetch(..., { cache: "no-store", headers: { "x-admin-token": … } })` inside async server components with `export const dynamic = "force-dynamic"`). The admin token and the basic-auth password are read from `process.env` **without** a `NEXT_PUBLIC_` prefix, so they can never be inlined into client JS; no admin page/component carries `"use client"`. Web env: `ADMIN_API_BASE_URL` (default `http://localhost:3000`) + `ADMIN_API_TOKEN` (same value the API validates).

**D3 — Three GET endpoints, one new Nest module (`apps/api/src/admin`), prefix `/v1/admin`:**
1. `GET /v1/admin/kpis?days=<1..90, default 30>` → `{ days, generatedAt, daily: AdminKpiDay[], tiers: AdminTierSnapshot }`, where `AdminKpiDay = { day, devicesCreated, checksCreated, checksDone, checksFallback, fallbackRate: number|null, billingEventsProcessed, subscriptionsUpdated }` and `AdminTierSnapshot = { totalUsers, premiumSubscriptions, expiredOrInactiveSubscriptions, activeReferralGrants }`.
2. `GET /v1/admin/users/lookup?email=<string>` → `AdminUserSummary` (D4 field list) or `404 NOT_FOUND`.
3. `GET /v1/admin/ai-audit?limit=<1..100, default 50>&cursor=<uuid?>` → `{ rows: AdminAuditRow[], nextCursor: string|null }`, keyset over `orderBy: [{ createdAt: "desc" }, { id: "desc" }]` with Prisma `cursor: { id }, skip: 1` — stable because the table is append-only.

All three: `@Public()` + `@UseGuards(AdminTokenGuard)` + `@Get` only, class-validator DTOs, Swagger decorators, and Zod response schemas in `packages/types` parsed by the service before returning (the T117 `clientVersionsResponseSchema.parse` idiom).

**D4 — `AdminUserSummary` fields (ids/codes/counts only, never content):** `userId, email, createdAt, locale, region, analyticsOptOut, deletionScheduledAt, householdIds[], entitlement` (reused verbatim from `BillingService.getEntitlement`, a read-only call), `counters: { pets, symptomChecksTotal, symptomChecksFallback, chatThreads, chatMessages, reminders, healthLogs, devices, feedbackReports, accountExports, referralGrantsActive }`. **Explicitly excluded:** pet names, symptom/intake text, chat message content, triage results, photo keys, feedback message bodies, tokens. A spec pins the exclusion list.

**D5 — Indexes (one additive migration; no column/behaviour change):** `Device.createdAt`, `SymptomCheck.createdAt`, `Subscription.lastEventAt`, `ProcessedWebhookEvent.processedAt`, `AiAuditLog([createdAt desc, id desc])`. Every new query pattern gets its index in the same migration (CLAUDE §6). No data migration, no destructive statement.

**D6 — Scope calls (deliberate exclusions).**
- The T117 `/v1/meta/client-versions` panel is **NOT** added. It is another card's surface, the founder's D5 freshness decision is open, and the card text does not list it. Noted in §8.
- No `surface`/date filters on the audit browser (card says "browser with pagination"), no CSV export, no charts, no auto-refresh, no nav beyond three links.
- No new dependency in any workspace.

## 7. Risks (top 5 — the design decisions the checker should scrutinise)

**R1 — "MRR events" cannot be revenue (highest scrutiny).** T072/T073 persist no amount, currency, or event type; only `ProcessedWebhookEvent{eventId, processedAt}` plus the last `rawEventJson`. I chose **event counts** (`billingEventsProcessed`, `subscriptionsUpdated`) with an explicit on-screen limitation note, rather than (a) inventing a revenue number or (b) adding a write path to capture one (which would violate "strictly read-only"). If the checker judges the card demands currency MRR, this card is blocked pending a new billing-event ledger card. The executor must **not** quietly parse `rawEventJson` for a price field: it is the *last* payload only, unindexed, and unvalidated for that field.

**R2 — basic-auth is the whole mechanism.** Credentials travel base64 on every request; there is no session, lockout, or `/admin`-specific rate limit (the API side is still behind the global throttler; the web middleware is not). Acceptable only because the deployment terminates TLS and the allowlist is tiny (mitigation in §8). Adding a lockout counter would be scope beyond the card.

**R3 — tier distribution is the RC-mirror snapshot, not `pickEntitlement`.** Household-shared family plans and T108 referral grants make a user's *effective* entitlement differ from their own `Subscription` row. The panel therefore reports subscription-row counts plus an `activeReferralGrants` count and labels itself a snapshot, while the per-user lookup uses the real `BillingService.getEntitlement` so support answers stay accurate. Risk: an admin reads the aggregate as exact user-tier truth.

**R4 — amending `disclaimer-placement.spec.tsx` is the most dangerous edit here.** The carve-out is narrow (three pinned admin paths), is compensated by a new "admin sources contain no §5 tokens" assertion, and leaves the rule fully in force for every non-admin route. If the executor widens it to a directory glob, or drops the exact-map assertion, the checker should fail the task.

**R5 — Next middleware runtime + build-time prerender.** Middleware may run on the Edge runtime where `node:crypto` is unavailable — hence the `crypto.subtle` design (D1). If `crypto.subtle` proves unavailable in the executor's Next/Node combination, the fallback is to keep the same pure-function API and compare fixed-length digests from a small pure implementation — **not** to drop constant-time comparison and **not** to add a dependency. Separately, admin pages MUST carry `export const dynamic = "force-dynamic"`, or `next build` will try to prerender them and fail when the API is unreachable in CI.

*Secondary (stated, not top-5):* the new indexes are additive only; `/v1/meta/client-versions` is deliberately excluded (D6); an unknown audit cursor maps to 400, not 500; `?email=` values are logged nowhere.
