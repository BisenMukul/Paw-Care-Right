## 3. Interfaces/contracts (match exactly)

### `packages/types/src/semver.ts`
```ts
export type VersionOrder = -1 | 0 | 1;
/** `null` = at least one side is unparseable (fail-open signal for callers). */
export function compareAppVersions(a: string, b: string): VersionOrder | null;
/** `true` ONLY when both parse AND current < target. Any doubt ⇒ `false`. */
export function isVersionBelow(current: string, target: string): boolean;
```
Grammar, applied to the **trimmed** input: `/^(\d+)\.(\d+)\.(\d+)(?:\+([0-9A-Za-z][0-9A-Za-z.-]*))?$/`. Rules in order:
1. No match on either side ⇒ `null` (covers `1.0`, `1.0.0.0`, `v1.0.0`, `1.x.0`, `1.0.0-beta`, `1.0.0+`, `""`, `garbage`).
2. Compare `major`, then `minor`, then `patch` numerically.
3. Cores equal ⇒ compare build metadata **only if both sides have one and both match `/^\d+$/`** → numeric compare (`+7 < +10`; `+007 == +7`). Otherwise build metadata is **ignored** and the result is `0` (semver §10 precedence + fail-open: never gate on a build number that is not visible on both sides).

### `packages/types/src/config.ts`
```ts
export const NO_GATE_VERSION = "0.0.0";
export const platformAppVersionsSchema = z.object({ ios: z.string(), android: z.string() }).strict();
export type PlatformAppVersions = z.infer<typeof platformAppVersionsSchema>;

// SERVER CONTRACT — stays .strict(): the API must never send an undocumented field.
export const appConfigResponseSchema = z.object({
  paywall: z.object({ variant: paywallVariantSchema }),
  minSupportedVersion: z.string(),
  hotlinePackVersion: z.number().int().nonnegative(),
  features: featureFlagsSchema,
  criticalOtaVersion: z.string().nullable(),
  minAppVersion: platformAppVersionsSchema,           // T115
  recommendedAppVersion: platformAppVersionsSchema,   // T115
}).strict();

// CLIENT PARSE PATH (docs/OTA_UPDATES.md §5.4; T114 checker Finding 1):
// tolerant of unknown/future keys at BOTH levels, with defaults for the
// fields T115 introduces, so an old bundle can never lose the `features`
// kill switches just because a newer server grew a field.
export const appConfigClientSchema = appConfigResponseSchema
  .extend({
    features: featureFlagsSchema.strip(),
    minAppVersion: platformAppVersionsSchema
      .strip()
      .default(() => ({ ios: NO_GATE_VERSION, android: NO_GATE_VERSION })),
    recommendedAppVersion: platformAppVersionsSchema
      .strip()
      .default(() => ({ ios: NO_GATE_VERSION, android: NO_GATE_VERSION })),
  })
  .strip();
export type AppConfigClient = z.infer<typeof appConfigClientSchema>;
```
`.strip()` (not `.passthrough()`): unknown keys are **dropped**, so nothing unvalidated reaches `AppConfig` or the MMKV cache. Function-form `.default(() => …)` so the fallback object is never a shared mutable reference. The header comment must state the go-forward rule for T116–T118: *server additive-only + client `.strip()` + a client default for every new field ⇒ §5.4 "backward-compatible by construction".*

### `apps/mobile/src/config/version-gate.ts`
```ts
export type UpgradeState = "blocked" | "recommended" | "none";
export interface UpgradeStateInput {
  appVersion: string;                         // may carry "+build"
  platformOS: string;                         // Platform.OS
  minSupportedVersion: string;                // legacy scalar (T079) — still honoured
  minAppVersion: PlatformAppVersions;         // T115
  recommendedAppVersion: PlatformAppVersions; // T115
}
/** android ⇒ `.android`; every other OS ⇒ `.ios` (mirrors `resolveStoreUpdateUrl`). */
export function resolvePlatformVersion(versions: PlatformAppVersions, platformOS: string): string;
export function resolveUpgradeState(input: UpgradeStateInput): UpgradeState;
// existing exports keep their signatures, now delegating to the shared util:
export function compareVersions(a: string, b: string): -1 | 0 | 1 | null; // = compareAppVersions
export function isUpdateRequired(current: string, min: string): boolean;  // = isVersionBelow
```
`resolveUpgradeState` order (min beats recommended; every uncertainty ⇒ `"none"`):
1. `"blocked"` if `isVersionBelow(appVersion, minSupportedVersion)` **or** `isVersionBelow(appVersion, resolvePlatformVersion(minAppVersion, platformOS))`.
2. else `"recommended"` if `isVersionBelow(appVersion, resolvePlatformVersion(recommendedAppVersion, platformOS))`.
3. else `"none"`.

## 8. Risks & the design decisions the planner made (scrutinize these)

**Top-5 risks**
1. **R1 — a mis-set env var bricks the app for every user.** `MIN_APP_VERSION_*` above the live store version renders a non-dismissible screen with a CTA that cannot fix it. Required mitigations, all in this plan: every default is `0.0.0` (no gate); every uncertainty (malformed value, missing field, unknown platform, unparseable installed version, absent config) resolves to `"none"`; the decision is a **launch snapshot**, so a bad value pushed mid-session cannot swallow a live app (T080 guarantee preserved); the AC2 table pins every fail-open row. Residual risk is operational → §9.
2. **R2 — §5 interaction: the gate sits above the Emergency interstitial.** A blocked launch shows the upgrade screen instead of *any* route, including emergency surfaces. This is pre-existing T079/T080 behaviour (documented in `update-gate.tsx`'s header) and unchanged in kind by T115 — but T115 **widens the ways it can trigger** (2 new server fields + build numbers). Mitigation is R1's fail-open chain: it can only trigger on an explicit, well-formed server value strictly above the installed version. The banner path adds no §5 risk (dismissible, normal document flow, no overlay, cannot cover hotline numbers).
3. **R3 — the F1 client-schema change has the widest blast radius in the diff.** Every `/config` consumer flows through `fetchAppConfig`. If `.strip()`/`.default()` are misapplied, a malformed body could parse into a bogus config instead of falling back to cache. Mitigation: the client schema is *derived* from the strict server schema (single source of field types); the "still rejects a missing pre-existing field" non-vacuity test; and the untouched `paywall-config.test.tsx` / `emergency-interstitial.test.tsx` as independent canaries. Note the fix protects **T115+ bundles onward**; bundles already built with the strict client schema stay affected (acceptable: nothing is in the wild pre-beta, and §5.3 mandates backend-first deploys).
4. **R4 — coverage theatre on the new root-mounted banner (T114 Finding 2 repeat).** A root-mounted component with no spec and no mount assertion can be deleted with every gate green. Mitigation: dedicated spec + `testID`-bearing stub and a mount assertion in `root-layout.test.tsx`, plus mutation M-B below.
5. **R5 — `packages/types` dist skew (T113/T114 landmine).** Consumers resolve gitignored `dist/`; forgetting the rebuild yields confusing "export missing" failures or a green run against a stale schema. Mitigation: step 6 is a mandatory rebuild, repeated after any `packages/types/src/` edit, and the executor must report `dist/index.js` freshness (mtime + a grep for `recommendedAppVersion`) in the hand-off.

**Mutation proofs the executor must run at step 21** (atomic edit → targeted run → restore → verify sha1):
- **M-A** — in `resolveUpgradeState`, drop the `minAppVersion` branch ⇒ expect RED in the AC2 table, the new `update-gate` case, and the AC3 flow test.
- **M-B** — in `upgrade-recommended-banner.tsx`, delete the `state !== "recommended"` guard ⇒ expect RED in the banner spec (proves the banner cannot appear when blocked or up-to-date).
- **M-C** — in `packages/types/src/config.ts`, point the client parse back at the strict schema ⇒ expect RED in the types F1 suite **and** the mobile F1 test (proves the §5.4 fix is pinned, not decorative). Requires a `types build` before and after.

**Design decisions (minimum set; each is a choice, not an inevitability)**
- **D1 — F1 fix = a derived, `.strip()`-mode CLIENT schema with defaults for the new fields; the server schema stays `.strict()`.** Rejected: relaxing `appConfigResponseSchema` itself (the API would then be free to ship undocumented fields and the e2e contract test would lose its teeth); hand-rolling a tolerant parser in `app-config-queries.ts` (duplicates field types, drifts). `.strip()` over `.passthrough()` so unknown data never reaches `AppConfig` or the MMKV cache. The nested `featureFlagsSchema` is relaxed **too**, because a future 4th kill switch is exactly the F1 bug one level down.
- **D2 — per-platform shape is `{ios: string, android: string}` with `"0.0.0"` = "no gate"**, not `string | null`. Rationale: identical convention to the existing `minSupportedVersion`/`MIN_SUPPORTED_VERSION` default, so no null-normalisation layer is needed anywhere and the fail-open value is expressible in a plain env var. Cost: `"0.0.0"` is a magic sentinel (named `NO_GATE_VERSION`).
- **D3 — semver grammar is `x.y.z` + optional `+build`; pre-release tags are treated as MALFORMED (⇒ `null` ⇒ no gate).** Store marketing versions cannot contain a `-tag`, and full pre-release precedence would be unused code (CLAUDE §2: over-engineering is a defect). Build metadata is numerically compared **only** when both sides carry a numeric build; otherwise it is ignored (semver §10) — the fail-open direction.
- **D4 — no second comparator: `version-gate.ts` is rewritten to delegate to the shared util and to host `resolveUpgradeState`.** Rejected: deleting `version-gate.ts` (loses its 15 fail-open regression cases) and leaving its old parser in place (two comparators drift; the T115 module would make it dead code). Its existing test file, untouched, is the behaviour-preservation proof — including the deliberate capability change that build-metadata inputs, formerly `null`, are now comparable (covered by AC1).
- **D5 — the installed version is `"<marketing>+<nativeBuild>"` via `Constants.platform`.** Without a build number a min-version gate cannot force-upgrade a bad TestFlight/internal build, because `app.config.js` pins `version: "1.0.0"` while EAS auto-increments the build number remotely — which is precisely why the card names build-number edge cases. `expo-application` would be a new dependency, so `Constants.platform.{ios.buildNumber, android.versionCode}` is used instead; when absent (Expo Go/jest/web) the plain marketing version is used and the util ignores the other side's build ⇒ no gate.
- **D6 — the banner is root-mounted top (sibling of `<BetaBanner/>`) with NO route-based deferral.** T114's deferral guard exists to stop *reloads* interrupting protected flows; a static, dismissible, in-flow banner interrupts nothing, and `OfflineBanner`/`BetaBanner` already render on the emergency route unconditionally. Rejected: reusing `isFlowDeferred` (couples an unrelated module and hides the banner in flows where it is harmless).
- **D7 — dismissal is session-only zustand (`upgrade-banner-store.ts`), not persisted.** Mirrors `billing-banner-store.ts` exactly ("returns on next launch if the condition persists"), which is right for a recommendation, and avoids per-version dismissal bookkeeping the card never asked for.
- **D8 — the blocking decision ORs the legacy `minSupportedVersion` with the new per-platform `minAppVersion`, and `min` beats a lower `recommended`.** Keeps T079's field working (§5.1 additive-only, no removal) and makes a misconfigured `recommended < min` resolve to `"blocked"` — the higher-urgency, spec-consistent direction (urgency fails upward; *version parsing* fails open).
