### Honesty ledger — read before writing anything

1. **The planner could not run `pnpm audit`.** The planner role has `Read, Grep, Glob, Write` only — no
   Bash. **There is therefore no verified vulnerability baseline in this plan, and none is invented.**
   Establishing it is **Step 1**, and it is a hard gate: the executor records the *verbatim* output and
   disposes of every high/critical before anything else is written. A gate that is born red is
   dishonest; so is a number nobody measured.
2. **`pnpm audit` needs the network** (npm advisories endpoint). If it cannot reach the registry in this
   container, that is not permission to skip it — record the exact error, and if the baseline genuinely
   cannot be established, STOP and write `loop/plans/T096.blocked.md`. Do **not** ship a CI gate whose
   local behaviour you have never observed.
3. **Allowlisting is the last resort, not the first.** Order: (a) upgrade the direct dependency; (b) if
   the vulnerable package is transitive and a patched version exists, `pnpm.overrides`/re-resolve — but
   **only** if it does not move a version pinned by the locked stack (CLAUDE §3); (c) only if there is no
   fixed version, or the fix breaks the locked stack, allowlist it with a written justification, a named
   reachability analysis, and an expiry ≤ 90 days.
4. **A fuzz test that finds a real hole means the hole gets fixed, not the test softened.** If a fuzz
   case produces a `500`, a cross-tenant leak, or a state write it should not, STOP and write
   `loop/plans/T096.blocked.md` naming the file that would need to change — do not widen the assertion.
5. **Secret-looking fixtures must be assembled from concatenated parts** (e.g. `"AKIA" + "…"`), never
   written as one literal. `.claude/hooks/gate_exec.sh` scans the executor's own diff for exactly these
   patterns and will hard-fail the task otherwise. This is a real, observed constraint, not a style note.

## Ordered steps

### Phase A — establish the baseline (nothing else may be written first)

**1. Run the audit and record it verbatim.**
```
pnpm audit --audit-level high 2>&1 | tail -40
pnpm audit --audit-level high --json > /tmp/audit.json 2>&1; echo "exit=$?"
```
Paste the full human-readable summary line(s) (e.g. `N vulnerabilities found. Severity: … high … critical`)
into `loop/journal.md` **exactly as printed**. Then, for each high/critical advisory, record: GHSA id,
CVE id, package + version, path (direct or transitive, via which dependency), and whether a patched
version exists.

**2. Dispose of every high/critical**, in this order, one at a time:
- **Upgrade** the direct dependency to the patched version → re-run `pnpm i` → re-run the audit →
  re-run `pnpm typecheck && pnpm lint && pnpm test && pnpm build`. Any upgrade that moves a
  CLAUDE §3-locked technology's major version is **not** allowed here — STOP and write the blocked file.
- **Transitive with a fixed version** → still prefer upgrading the *parent* dependency. Do not reach for
  `pnpm.overrides` unless the parent has no release; an override that forces an untested version of a
  transitive package is a bigger risk than the advisory in many cases — if you use one, justify it in the
  journal with the same rigour as an allowlist entry.
- **No fix available, or the fix breaks the locked stack** → allowlist (step 3).
Re-run `pnpm audit --audit-level high` after each disposition. The loop terminates when it **exits 0**.

**3. Allowlist (only for what step 2 could not fix).** For each remaining advisory add an entry to
`docs/security/audit-allowlist.json` (contract below) **and** the matching GHSA id to root
`package.json` → `pnpm.auditConfig.ignoreGhsas`. `reason` must state why it cannot be fixed;
`reachability` must state, concretely, whether our code reaches the vulnerable code path (e.g. "dev-only
transitive of `@nestjs/cli`; never present in the built API image"). "Low severity in practice" with no
argument is not a justification. `expiresOn` = today + ≤ 90 days.

> If step 1 shows **zero** high/critical advisories (the likely outcome): the allowlist file is created
> with `{"entries": []}`, **no** `pnpm` block is added to root `package.json`, and the journal states the
> clean baseline verbatim. That is a legitimate, honest outcome — do not invent an entry to exercise the
> mechanism; the fixture tests exercise it instead.

### Phase C — secrets scan

**6. `scripts/scan-secrets.js`** — CommonJS, no dependencies, Node 22. Contract below. Rules (each with
an `id` + `description`): private key blocks; AWS access key id; `sk-ant-…`; `sk-…` (32+); Google
`AIza…`; GitHub `gh[pousr]_…`; Slack `xox[baprs]-…`; Sentry DSN carrying a secret half; and one
**generic** rule — a quoted assignment to a key matching `api[_-]?key|secret|password|passwd|token|
credential` whose value is ≥20 chars **and** contains at least one digit and one letter **and** is not in
the placeholder denylist (`example`, `test`, `dummy`, `fake`, `placeholder`, `changeme`, `your-`, `xxx`,
`local`, `dev-secret`). The entropy + placeholder conditions are what make this rule usable on a repo
full of fixtures — verify empirically in step 8, and tune the *rule*, never the repo.
Skip: `pnpm-lock.yaml`, `node_modules/`, `dist/`, `.next/`, `coverage/`, `.expo/`, binary extensions
(`png|jpg|jpeg|gif|ico|woff2?|ttf|pdf|zip`). Skip any line containing `pragma: allowlist secret`.
Exit 1 and print `path:line:ruleId` (never the matched value) when anything is found.

**7. `githooks/pre-commit`** — `#!/bin/sh`, `set -eu`, executable bit set, runs the scanner over
`git diff --cached --name-only --diff-filter=ACM`. Header comment: this is opt-in and advisory; the
authoritative gate is the CI job.

**8. Run the scanner over the whole tracked tree** (`node scripts/scan-secrets.js --tracked`) and get it
to **zero findings**. Every finding is one of: (a) a real secret → STOP immediately, do not commit,
write the blocked file tagged with the file path (rotation is a human decision); (b) a false positive →
tighten the rule, or, if the line is a legitimate fixture, append `pragma: allowlist secret` **on that
line** and note it in `docs/security/README.md`. Record the final rule set + any pragma sites in the doc.

**9. `docs/DEV_SETUP.md`** — add the `git config core.hooksPath githooks` one-liner and one sentence on
what it scans. No other edit to this file.

### Phase F — ADR

**17. `docs/adr/0001-mobile-tls-certificate-pinning.md`.** Sections: `Status` (**Deferred — not
implemented**, dated), `Context`, `Decision`, `Consequences`, `Revisit triggers`. Content it must
actually make the argument for, not merely mention:
- *Threat model*: platform trust store already authenticates `pawcareright.app`; pinning only adds
  defence against a user-installed/enterprise MITM root or a mis-issued CA.
- *Cost in this stack*: RN/Expo networking uses the OS TLS stack; pinning needs native config (OkHttp
  `CertificatePinner` / iOS ATS or TrustKit) delivered by a config plugin + prebuild, i.e. a new native
  dependency (CLAUDE §2 rule 7) and a departure from the managed-workflow assumption.
- *OTA interplay* (`docs/OTA_UPDATES.md`, referenced, **never edited**): a pin lives in native code, so a
  certificate rotation or a wrong pin cannot be repaired by an OTA JS update — it requires a store
  release. That is a self-inflicted availability risk against a threat we have no evidence of.
- *Third-party SDKs* (RevenueCat, Sentry, PostHog, Expo Updates) open their own connections we do not
  control, so pinning our own API only covers part of the surface.
- *What we rely on instead*: HTTPS everywhere, short-lived access tokens + refresh rotation (T012–T017),
  tokens in the OS keychain, server-side entitlement mirror, no card data in the app.
- *Revisit triggers*: leaving managed workflow for other reasons; handling card data directly; any
  observed MITM/interception incident; an enterprise/regulated deployment requirement.
It must state explicitly that **nothing is implemented by this ADR**.

## Risks & the decisions the planner made (for the checker to scrutinise)

- **D1 — Suppression uses pnpm's native `pnpm.auditConfig.ignoreGhsas` in root `package.json`, with
  `docs/security/audit-allowlist.json` as the justification file, kept in sync by a test.**
  Rejected alternative: a wrapper script that diffs `pnpm audit --json` against a JSON allowlist. That
  would re-implement pnpm's severity/dedup logic (a second, subtly different gate) and lets the "gate"
  drift from what `pnpm audit` actually reports. Native suppression means the CI command is literally the
  card's `pnpm audit`, and the allowlist file supplies what pnpm has no field for: reason, reachability,
  owner, expiry. *Risk:* two files must stay consistent — mitigated by the sync test (M5/M6) failing in
  **both** directions. *Verify:* `ignoreGhsas` exists in pnpm ≥10.4 and we are on 10.34.3; if the
  installed pnpm rejects the key (observable immediately — the audit will still report the advisory),
  fall back to `ignoreCves` and keep everything else identical, noting the switch in the journal.
- **D2 — the `security` job installs with `--frozen-lockfile --ignore-scripts` before auditing.**
  `pnpm audit` can in principle resolve from the lockfile alone, but that is not a behaviour I could
  verify here, and a gate whose failure modes are unknown is worse than a 60-second install. *Risk:*
  slightly slower CI. Accepted.
- **D3 — the audit gate is a required, unconditional job, not gated on any secret.** Same reasoning as
  T095's D3: the AC is a gate, and a skippable gate is a false green. *Risk:* a newly published advisory
  can turn CI red on a PR that changed nothing — that is the intended behaviour of this control, and the
  playbook in `docs/security/README.md` (upgrade → override → allowlist+expiry) is how it gets cleared.
  It must never be cleared by lowering `--audit-level`.
- **D4 — the secrets scanner is ~100 lines of repo-owned CommonJS, not `gitleaks`.** gitleaks means a new
  binary/action (org licensing for the action, a supply-chain dependency inside the control that exists
  to protect the supply chain) for a repo with one language family and a known set of credential shapes.
  *Risk:* a hand-rolled rule set has worse recall than gitleaks' hundreds of rules. Accepted and stated
  in `docs/security/README.md`; the rule set is a documented starting point, extended when a new
  credential type enters the stack. The generic high-entropy rule is where recall/precision is traded —
  hence M19/M20 pin both halves.
- **D5 — the malformed-JSON webhook case asserts status only, not the error envelope.** body-parser's
  `SyntaxError` is raised in Express middleware before Nest's router, so `AllExceptionsFilter` never sees
  it and the body is Express's, not `{error:{code,message,requestId}}`. Asserting the envelope there
  would be asserting a behaviour the framework does not have. *Risk:* a reader may think the envelope is
  unenforced — it is enforced everywhere else, by every existing suite. If the observed status is 5xx
  rather than 400, that is a genuine finding and step 12 says STOP.
- **D6 — fuzzing is a seeded, hand-rolled corpus, not `fast-check`.** `fast-check` is present in the
  store only as a transitive dependency; importing it from `apps/api` would be an undeclared dependency
  under pnpm's strict layout, and declaring it is a new dependency (§2 rule 7) for what is, here, a
  bounded input space (key strings, JSON shapes). A fixed seed also makes CI failures reproducible,
  which random property generation notoriously is not. *Risk:* less input diversity than a real
  property-based generator. Accepted; the corpus is explicitly enumerated, so its coverage is auditable.
- **D7 — the fuzz suites are expected to find nothing, and that is the honest expected outcome.** The
  guards they target (`isKeyInPetNamespace`, the hashed `timingSafeEqual` compare, the
  `ProcessedWebhookEvent` PK dedupe, the DTO validators) were all built deliberately in T017/T023/T070/
  T073. The deliverable is the *pinning* of those properties against future regressions (see the mutation
  table), not a bug count. Manufacturing a "finding" to look thorough would be the dishonest outcome.
- **D8 — the persisted-store list is pinned by name, so adding a store fails the test.** *Risk:* an
  unrelated future task gets an unexpected red test. That is intentional friction: a new persistence site
  in an unencrypted store is exactly the change that deserves a human look, and the fix is one line in
  `docs/security/mobile-storage-audit.md` plus the reviewer's attention.
- **D9 — the pre-commit hook is opt-in (`core.hooksPath`), not auto-installed.** Auto-installation needs
  husky or a postinstall that rewrites developer git config — a new dependency and a surprising side
  effect. *Risk:* a developer who never runs the config line gets no local protection; CI still catches
  it before merge, which is where the card's gate lives.
- **D10 — no `apps/api/src/**` file is on the file list.** This makes the task purely additive
  (tests + docs + CI + one script), so the checker can verify "no behaviour changed" by inspection. The
  cost is that any real defect found becomes a re-plan rather than a same-commit fix. Given this is a
  *security* task, a discovered defect deserves its own plan, review, and commit message anyway.
