## 2. Design decisions (grant semantics) — every one is a decision the checker should scrutinise

**D1 — Grant is a parallel, RC-free grace window.** New model `ReferralGrant` with `startsAt`/`expiresAt`. Nothing in T108 reads, writes, or derives from `Subscription`. `pickEntitlement` gains a third, independent input. This is the literal implementation of the AC "RC entitlement unaffected (server-side grace only)".

**D2 — Precedence: own > family > grant > none.** A grant never overrides a real RC row and never alters the `expiresAt` reported for an RC-sourced entitlement. New source value `"grant"`.

**D3 — Grant math = chained, non-overlapping windows.**
`computeGrantWindow(existingGrants, now)`: `startsAt = max(now, max(existing.expiresAt))`, `expiresAt = startsAt + 14d`. So N grants ⇒ exactly N×14 days of coverage, never overlapping, never lost to concurrency.

**D4 — Effective grant expiry = contiguous chain fold.**
`resolveGrantExpiry(grants, now)`: sort by `startsAt`; `cursor = now`; for each grant with `startsAt <= cursor`, `cursor = max(cursor, expiresAt)`; return `cursor > now ? cursor : null`. This reports the true chain tip (e.g. 3 stacked grants → +42d) rather than only the currently-active window.

**D5 — Cap = 3 grants RECEIVED per user, lifetime ⇒ +42 days maximum, ever.** `REFERRAL_GRANT_MAX_PER_USER = 3` counts rows where `userId = recipient`, regardless of whether the user was inviter or joiner on each. This is the card's "max 3 grants/user", read as grants-received (the only reading under which the cap actually bounds anything for both sides).

**D6 — Cap breach is a silent skip, never an error.** If a recipient is at cap, no row is written for that side and the join proceeds; the other side may still be granted. A referral cap must never fail a household join (T026 behaviour is unchanged for every existing test).

**D7 — Issuance is synchronous, inside the existing accept transaction.** Pure DB writes, no external calls ⇒ CLAUDE §6's "long-running work goes through BullMQ" does not apply. Being in the claim transaction gives exact-once semantics for free and means the inviter (who is offline) is granted without any queue.

**D8 — Idempotency = invite claim + `@@unique([inviteId, userId])` backstop.** A `P2002` on grant insert is swallowed as "already granted" (no-op), never surfaced.

**D9 — Grant while a paid subscription is active gives no visible benefit.** The window runs on wall-clock from issue; if RC covers a later date, `pickEntitlement` reports the RC row (D2). Documented in `docs/referral-grants.md` and in Risks (R2) — the alternative (chaining onto RC's `expiresAt`) would couple grant math to RC state, which the AC forbids.

**D10 — A grant confers full PREMIUM tier** (via the single quota seam), including the ability to mint invites. Bounded by D5. Documented as a residual vector (R3) rather than special-cased — special-casing would require plumbing `source` through `quota.types.Entitlement`, i.e. scope the card does not ask for.

**D11 — Model is deliberately lean**: `id, userId, counterpartyUserId?, inviteId?, startsAt, expiresAt, createdAt`. No `role` enum, no `days` column (derivable). `counterpartyUserId` and `inviteId` are `onDelete: SetNull` so **erasing the other party never revokes an already-earned grace window**; `userId` is `onDelete: Cascade` (T091 erasure).

## 3. Abuse guards + residual vectors (honest set)

Implemented guards:
1. **Lifetime cap 3 grants/user** (D5/D6) — the card's named guard.
2. **Idempotency** — single-use invite claim + `@@unique([inviteId, userId])` (D8): one accept can never double-grant either side.
3. **Self-grant impossible** — inherited from T026: `sole.householdId === invite.householdId` ⇒ 409 before the transaction, so a user can never accept their own household's invite; and the two recipients are de-duplicated defensively in the service.
4. **Invite minting stays premium-only + owner-only** (T026/T075, unchanged) — a referral chain cannot start from a free account.

Residual vectors, documented in `docs/referral-grants.md` §5 and NOT fixed in this card:
- **Alt-account farming**: a premium owner invites 3 accounts they control → +42d for themselves, +14d each for the alts. Hard-bounded by the cap; the economic ceiling is 42 free days per identity.
- **Leave/rejoin cycling**: A invites B, B leaves (T077), A re-invites B. Each cycle consumes one of B's and one of A's three lifetime grants ⇒ bounded by the same cap. A pair-uniqueness guard was **considered and rejected as scope beyond the card** (see R4 — checker may overrule).
- **Grant-funded invite minting** (D10): a granted user can mint invites during their grace window, growing the graph; every participant is still individually capped at +42d.
- No velocity/IP/device heuristics — deliberately out of scope for M; called out in the founder delta.

## 8. Risk register (top 5)

**R1 — `pickEntitlement` signature change breaks a caller I did not find.** Mitigation: the only production caller is `BillingService`; `entitlement.util.ts` has no dedicated spec (its coverage lives in `billing.service.spec.ts`). `pnpm typecheck` is the backstop. If a third caller appears, the executor must stop and report — not silently edit an unlisted file.

**R2 — D9 (grant burns while paid) may be judged user-hostile.** A grant issued to an actively-subscribed inviter provides no visible benefit and silently elapses. Chosen because the alternative couples grant math to RC's `expiresAt`, which the AC forbids. Documented in `docs/referral-grants.md` §2 and flagged for the founder (§9). Checker: this is the single most contestable decision in the plan.

**R3 — Grant confers invite-minting rights (D10)**, so grace can propagate through the graph. Bounded per identity by the cap; not special-cased because gating on `source` would require widening the quota `Entitlement` shape (out of card scope).

**R4 — No pair-uniqueness guard.** Leave/rejoin cycling between the same two users is possible until each hits the cap. Deliberate minimality; documented as a residual vector. If the checker deems the cap insufficient, the fix is a single `findFirst({ where: { userId, counterpartyUserId } })` skip in `ReferralGrantService` — the column already exists.

**R5 — Migration folder naming vs. the scope gate.** `prisma migrate dev` names folders with a live timestamp this plan cannot predict, and `gate_exec.sh` matches every changed path literally against this file. Mitigated by step 5's `--create-only` + deterministic rename to `20260730170000_t108_referral_grant`. If the rename is skipped, the gate fails as out-of-scope.

Secondary (stated, not top-5): `ReferralGrant` rows are **not** added to the T091 account-export bundle (`account-export.service.ts` has a fixed schema and no DMMF completeness guard). The rows carry only ids and two timestamps. Recorded in `docs/referral-grants.md` §6 as a known gap for the checker/founder to accept or reject.

## 9. Founder delta
