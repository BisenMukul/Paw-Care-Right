### 2.4 90-day retention job

**Step 18.** `workers/ai-audit-retention.contract.ts` (mirrors `reminder-consistency.contract.ts`, no logic):
```
AI_AUDIT_RETENTION_QUEUE        = "pawcareright-ai-audit-retention"
AI_AUDIT_RETENTION_JOB_NAME     = "ai-audit-retention"
AI_AUDIT_RETENTION_SCHEDULER_ID = "ai-audit-retention-daily"
AI_AUDIT_RETENTION_PATTERN      = "30 3 * * *"      // 03:30 UTC daily, off the hourly-tick minute
AI_AUDIT_RETENTION_DAYS         = 90
AI_AUDIT_RETENTION_BATCH_SIZE   = 1000
AI_AUDIT_RETENTION_MAX_BATCHES  = 100               // bounded per run; the next run continues
```

**Step 19.** `workers/ai-audit-retention.service.ts`:
```ts
export interface RetentionReport { cutoff: Date; deleted: number; batches: number; exhausted: boolean }

@Injectable()
export class AiAuditRetentionService {
  constructor(private readonly prisma: PrismaService) {}
  async purge(now: Date): Promise<RetentionReport>;
}
```
- `cutoff = new Date(now.getTime() - AI_AUDIT_RETENTION_DAYS * 86_400_000)`. `now` is a **required parameter** (injected clock — house pattern from `ReminderConsistencyService.checkConsistency(now)`), never `Date.now()` inside.
- Loop up to `MAX_BATCHES`: `findMany({ where: { createdAt: { lt: cutoff } }, select: { id: true }, take: BATCH_SIZE, orderBy: { createdAt: "asc" } })` → break if empty → `deleteMany({ where: { id: { in: ids } } })` → accumulate. Break when the batch is shorter than `BATCH_SIZE`.
- **`lt: cutoff`, strictly — a row exactly at the boundary or newer is never deleted.**
- Logs one `Logger.log({ event: "ai_audit_retention_done", cutoffEpochMs, deleted, batches, exhausted })`.
- Idempotent: a second run over already-purged data deletes 0 and returns `{ deleted: 0, batches: 0 }`.

## 8. Safety statement (PRODUCT_SPEC §5 — supreme)

**Mandatory-FAIL surface: "emergency unreachable under limit."** `ThrottlerGuard` is the first global guard and runs before `JwtAuthGuard`, before the controller, and therefore before the deterministic red-flag rules in `ChecksService.create`. Any throttle class on `POST /pets/:petId/checks` can 429 a red-flag intake before `evaluateRedFlags` ever runs, which makes the Emergency interstitial unreachable — a direct violation of §5 rule 3 ("deterministic emergencies … before any AI content") and of the golden rule that nothing may delay emergency vet care. This plan therefore:

1. `@SkipThrottle()`s the three escalation-capable check routes (create / followup / result read) and **deletes** the pre-existing unused `THROTTLE_CHECKS` (10/day) constant so no future task can wire it there by accident.
2. Governs those routes with **alerting, not blocking**: the checks/user/hour anomaly counter returns `void`, is wrapped in its own try/catch, and is called *after* persist+enqueue — it is structurally incapable of producing a 429, a throw, or a delay in the red-flag response. Existing per-user metering (`QuotaService`) already exempts red-flag checks.
3. Keeps the `<VetDisclaimer/>`, safe-fallback, dosing-prohibition, and hotline surfaces **completely untouched** — no prompt, no user-facing string, no triage/gate logic is modified by this task.
4. Enforces T089 PII discipline in the new table: `AiAuditLog` has **no content column**. Only ids, prompt/model versions, enumerated detector *codes*, costs, latency, and a status enum are stored; `detectorFlags` is built by a pure function from a closed code set and is proven free of `failureReason`/error-message/chat-content passthrough by test. The Sentry anomaly alert carries a fixed literal message plus id/count tags only.
5. Preserves the two "must not throw" invariants: `AiAuditService.record` never throws, so a chat stream still emits `done` (T082 F1) and a triage job still terminalizes (T043) even when the audit insert fails. Audit writing is deliberately **synchronous and non-throwing** rather than queued, so an audit row is never silently lost to a Redis outage.

If Step 5's verification shows the mobile app cannot render emergency hotline numbers without a live `GET /config`, the executor must stop and file `loop/plans/T090.blocked.md` tagged `SAFETY-ESCALATION` rather than widen or narrow any exemption on its own.

## 9. Risks & the design decisions the planner made (scrutinize these)

- **D1 — `@SkipThrottle()` on the check routes instead of a tight class.** This *loosens* IP-level protection on three authenticated routes relative to today's 100/60 s. Accepted because §5 outranks abuse control on exactly this surface, and the compensating controls (JWT auth, `QuotaService` 402, the new hourly anomaly alert) are per-user and red-flag-safe. **Risk:** an authenticated attacker can hammer check-create harder than before. Mitigation is alerting, not blocking — by design.
- **D2 — Anomaly threshold = 20 checks/user/hour, alert-only, fired exactly at `count === threshold`.** The number is a judgement call with no spec anchor. Strict equality means exactly one alert per bucket (no storm) but also means a counter that jumps past the threshold via a race would miss the alert. Accepted: this is observability, not enforcement.
- **D3 — `AiAuditLog` has no foreign keys.** Deliberate: `Cascade` would let a pet/check deletion erase the audit trail; `Restrict` would break T091's deletion cascade. **Risk:** orphaned `checkId`/`threadId` values after deletion, and no referential integrity. The retention job is then the only deleter — which is exactly the append-only property the card asks for. T091 must decide separately whether GDPR deletion needs to reach these id-only rows.
- **D4 — Exactly-one-of (`checkId` XOR `threadId`) is enforced by a TypeScript discriminated union + unit test, not a SQL `CHECK` constraint.** A raw `CHECK` in the migration would create schema.prisma↔DB drift that breaks `prisma migrate dev`. **Risk:** a raw-SQL writer could insert a malformed row; there is no such writer, and `AiAuditService.record` is the only write path.
- **D5 — Audit writes are synchronous and non-throwing, not queued.** One indexed INSERT on paths that already do several DB writes; queueing would add a queue, a worker, and a DLQ for a single insert, and would risk losing the audit row during exactly the Redis outage you'd want audited. **Risk:** a slow DB adds latency to the chat finalize path (after `done` is computed, before it is sent). Bounded by the same DB the adjacent `chatMessage.create` already hits.
- **D6 — The alert sink is `Logger.warn` + `Sentry.captureMessage` (new `captureApiMessage` helper).** Sentry is the only alerting sink that exists (T089). **Risk:** slight scope growth in `observability/sentry.ts`; mitigated by mirroring `captureApiException` exactly and keeping the message a fixed literal.
- **D7 — `status` and `latencyMs` columns beyond the card's literal field list.** The card lists checkId/threadId, promptVersion, modelId, detectorFlags, costs. A cost/flag record without the run outcome is not auditable, and `latencyMs` is already computed by `runTriage`. **Risk:** mild scope creep; both are code/number columns with no PII.
- **D8 — `THROTTLE_AUTH_REFRESH` at 30/60 s.** Looser than the strictest class on purpose: refresh is called precisely when access tokens expire, often concurrently. Too tight would log real users out — a reliability regression masquerading as a security win. **Risk:** 30/min/IP is generous behind carrier-grade NAT; still 3.3× tighter than today.
- **D9 — Per-IP tracking retained for all throttle classes.** `ThrottlerGuard`'s default tracker is the client IP; per-user tracking would need a custom guard subclass. **Risk:** shared-NAT users share a bucket on the auth classes. Accepted as pre-existing T017 behaviour; per-user limits are `QuotaService`'s domain.
- **R10 — e2e throttle tests are stateful across cases.** `apps/api/test/breeds.e2e-spec.ts` already notes that suites share the 100/60 s window. The new `rate-limits.e2e-spec.ts` deliberately saturates windows and must therefore isolate itself (unique IPs via `X-Forwarded-For` if the app trusts proxies, or a Redis/throttler-storage reset between cases) so it does not poison other suites. **Executor: verify how `ThrottlerGuard` resolves the tracker in this app before writing the suite; if per-case isolation is impossible, keep the §5 red-flag exemption case (M5) as an e2e and move the numeric-limit cases (M1) to a guard-level unit test — but the §5 case must remain end-to-end.**
