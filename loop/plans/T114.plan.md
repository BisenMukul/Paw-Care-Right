## 1. Spec extraction — docs/OTA_UPDATES.md §3 (read-only; the requirement source)

Exact obligations, in flowchart order (lines 28–45):

| # | Requirement (§3) | Implementation obligation |
|---|---|---|
| S1 | `Cold start → checkForUpdateAsync`, **non-blocking, 3s budget** | The check runs from an effect after mount, never gates rendering; a check that has not resolved within 3000 ms is abandoned for this cycle ("none/timeout → Continue normally"). |
| S2 | `available → fetchUpdateAsync in background` | Fetch only after `isAvailable === true`; no budget on the fetch; failures swallowed. |
| S3 | `critical flag? update metadata OR /config` | Two independent signals: a `[critical]` marker carried by the update metadata, OR `/config.criticalOtaVersion`. Either one ⇒ critical. |
| S4 | `no → Apply silently on NEXT launch` | Non-critical = do nothing at all (expo-updates already launches the newest fetched bundle next cold start). No prompt, no reload, no UI. |
| S5 | `yes → User mid-flow? (symptom check / paywall / emergency)` → `Defer prompt until flow completes` | The deferral guard sits **between** "critical" and "prompt": critical NEVER bypasses it. |
| S6 | `no → Restart prompt "Update ready" → Updates.reloadAsync` | `reloadAsync` is called **only** from an explicit user tap on the prompt. |
| S7 | Foreground re-check on `AppState → active`, throttled once per 6h, **persisted timestamp** | 21_600_000 ms; timestamp survives process death (MMKV). |
| S8 | "**Never** interrupt an in-progress symptom check, the Emergency interstitial, checkout, or onboarding with a reload — the deferral guard is a hard rule with tests." | Hard rule. `checkout` maps to this repo's `paywall` route + the root `UpsellSheet` purchase surface; `onboarding` maps to `(auth)/*` + `add-pet/*` + `push-rationale`. |
| S9 | `criticalOtaVersion` is "belt-and-braces … for clients that fetched before the flag" | The `/config` mirror must work even when the fetched manifest carries no marker. |

**Critical-vs-deferral precedence (explicit, per §3 + CLAUDE §7):** deferral wins, always. The flowchart routes the `critical: yes` edge *into* the mid-flow test, and the §3 bullet calls the guard "a hard rule". Therefore: (a) no prompt renders while any protected flow is active, even for a critical update; (b) `reloadAsync` is re-guarded at tap time, so a race (flow entered between render and tap) still cannot reload; (c) nothing in this card ever calls `reloadAsync` automatically.

**Safety posture (CLAUDE §7 / PRODUCT_SPEC §5):** this card adds no AI content, no triage, no dosing, no disclaimer/emergency surface changes. Its only §5 contact point is the *negative* guarantee that an update prompt/reload can never appear over a check, the Emergency interstitial, checkout, or onboarding. Uncertainty therefore fails toward **not interrupting**: unknown criticality, unreadable manifest, missing config field, provider error, or timeout all resolve to the silent path. This is the safe direction here (a silent apply-next-launch can never delay emergency care; a surprise reload can).

## 7. Risk register (design decisions for the checker to scrutinise) — top 5

1. **D1 — `criticalOtaVersion` semantics.** Decision: it holds the EAS `updateId` that MUST be running; critical ⇔ marker present **OR** (`criticalOtaVersion !== null` AND `!== Updates.updateId`). §3 only says the flag is "mirrored in `/config.criticalOtaVersion` … for clients that fetched before the flag", so the comparison target is an inference. Rejected alternative: compare against the *fetched* manifest id only — that misses exactly the "fetched before the flag" case the doc names. Failure mode if wrong: a critical update prompts one launch later (silent-apply still delivers it) — never a safety regression.
2. **D2 — the `[critical]` marker path is duck-typed.** The publish-message convention belongs to T116, and expo-updates exposes no single documented manifest field for the update message. Decision: search a small candidate-path set for `[critical]`, case-insensitive; any read failure ⇒ `false` (non-critical). The `/config` mirror is the reliable signal, which is precisely the role §3 assigns it. Consequence: marker-only criticals may degrade to silent-apply.
3. **D3 — deferral is route-derived (+ upsell visibility) and deliberately over-inclusive.** Decision: block on root segments `check`, `checks`, `paywall`, `(auth)`, `add-pet`, `push-rationale`, plus `useUpsellStore().visible` for the non-route purchase surface. Rejected alternative: an imperative hold registry each flow pushes to (more code, more places to forget, and a missed `release()` would wedge updates forever). Consequences: the prompt is also deferred on `check/history` and `checks/[id]` (read-only) — a deliberate false positive in the safe direction; and `chat` is NOT deferred (§3 does not list it) — flagged for the checker.
4. **D4 — `.strict()` schema growth is a coordinated release.** A client on this build talking to a pre-T114 API rejects `/config` and falls back to cache/default (fail-open: no critical prompt, `minSupportedVersion` "0.0.0" ⇒ no blocking gate). Consistent with the T106 precedent and OTA_UPDATES §5.3's backend-first deploy order, but a real skew window. Rejected alternative: `.optional()` with a client default (breaks the strict-schema, no-silent-shape-drift convention this file documents).
5. **D5 — global `expo-updates` jest mock in `jest.setup.ts` (`isEnabled: false`).** Required because `_layout.tsx` now reaches the module in every root-layout test. `isEnabled: false` makes the controller short-circuit so existing tests stay byte-identical, and `use-ota-info.test.tsx`'s local mock still wins. It is a shared-fixture change touching the whole mobile suite; failure mode is broad and loud (gate 6), not silent.

Also noted (not top-5): `dismiss()` is session-scoped, not persisted, so a critical prompt can reappear next launch (deliberate); cold start always checks — only the *foreground* re-check is throttled (§3 bullet 1); `docs/OTA_UPDATES.md` retains stale `Paw Care Right +` / `pawcareright@…` brand strings that this card must neither edit nor copy.
