**5. `apps/web/lighthouserc.json`.** Target shape (URLs and `upload` unchanged from today):
```jsonc
{
  "ci": {
    "collect": {
      "url": [ /* the existing 4, unchanged */ ],
      "numberOfRuns": 3,
      "startServerCommand": "pnpm --filter @pawcareright/web start"
    },
    "assert": {
      "assertMatrix": [
        { "matchingUrlPattern": ".*",
          "assertions": { "categories:seo": ["error", { "minScore": 0.95 }] } },
        { "matchingUrlPattern": "^https?://[^/]+/$",

    },
    "upload": { "target": "temporary-public-storage" }

```
`assertMatrix` and `assertions` are mutually exclusive in `@lhci/cli` — the matrix is required because
the card scopes perf to the landing but SEO to the sample. `numberOfRuns: 3` is lhci's default; pinning
it explicitly makes the median-of-3 (variance protection) a *contract* rather than a default that a
future upgrade can move. **Verify the landing pattern actually matches** by running
`lhci assert --config=apps/web/lighthouserc.json` against step 1's collected results and confirming the
performance assertion is reported as *evaluated* (not silently matching zero URLs) — a matrix entry that
matches nothing passes vacuously, which is exactly the failure mode this task must not ship.

**8. `.github/workflows/ci.yml`** — add:
```yaml
  # T095: web performance/SEO budgets. This job is a REQUIRED gate (the card's
  # AC is "CI budget job green"), so unlike T089's Sentry upload it is never
  # skipped. It needs no secret and no external service: Chrome is preinstalled
  # on ubuntu-latest, lhci collects against a locally served build, and the
  # report is kept as a workflow artifact instead of lhci's cloud upload.
  web-perf-budget:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 10.34.3 }
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm i --frozen-lockfile
      - run: pnpm --filter @pawcareright/web build
      - name: Collect Lighthouse runs
        run: pnpm --filter @pawcareright/web exec lhci collect --config=./lighthouserc.json
      - name: Assert performance + SEO budgets
        run: pnpm --filter @pawcareright/web exec lhci assert --config=./lighthouserc.json
      - name: Upload Lighthouse reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: lighthouse-${{ github.run_id }}
          path: .lighthouseci/
          retention-days: 30
          if-no-files-found: warn
```
`collect` + `assert` are run **separately instead of `autorun`** precisely so the job never touches
lhci's `temporary-public-storage` — that is the one step that would need outbound network to a third
party and could redden CI for a reason unrelated to performance. `upload.target` stays in the config for
the founder's local `lhci autorun`. Copy the pnpm/node versions from the existing `build` job verbatim.
Note `lhci collect` runs the `startServerCommand` itself; the preceding `build` step is what makes
`next start` valid.

## Risks & the decisions the planner made (for the checker to scrutinize)

- **D1 — `assertMatrix` replaces `assert.assertions`.** The card scopes perf ≥90 to the *landing* and
  SEO ≥95 to the *programmatic sample*; `@lhci/cli` cannot express per-URL thresholds with a flat
  `assertions` block, and the two keys are mutually exclusive. *Risk:* this **breaks T085's existing pin
  test**, which reads `ci.assert.assertions`. Mitigation: step 6 rewrites that one test against the
  matrix with equal-or-greater strength, and M6 proves the SEO number is still pinned from both specs.
  Rejected alternative: keep flat `assertions` and apply perf ≥90 to all 4 URLs — stricter than the card
  and likely to fail on the 466-page programmatic template for reasons the card does not ask us to fix.
- **D2 — the CI job runs `lhci collect` + `lhci assert`, not `lhci autorun`, and keeps reports as a
  GitHub artifact.** T089's discipline is "no external service may redden CI"; `autorun` posts to lhci's
  `temporary-public-storage`. *Risk:* the founder's local `autorun` and CI now take slightly different
  paths (same config, same assertions). Accepted — the enforcing half is identical.
- **D3 — this job is a REQUIRED gate, deliberately NOT gated on a secret.** T089's `if: env.SECRET != ''`
  pattern exists for *optional observability*; here the AC is literally "CI budget job green", so a
  skippable job would be a false green. Chrome is preinstalled on `ubuntu-latest` and no secret is used.
  *Risk:* lighthouse variance on a shared runner could flake a PR near the threshold; `numberOfRuns: 3`
  + median is the mitigation, and the landing is a static, image-free, font-free page that should score
  far above 0.90. If it does flake in practice, the fix is a perf fix or a documented re-plan — **not**
  a lower number.
- **D4 — the cold-start budget is enforced in code but not measured here.** `COLD_START_BUDGET_MS` +
  `evaluateColdStart` are real, unit-tested logic; the adb script is real; the *measurement* is
  founder-deferred because no device exists. *Risk:* a reader could mistake "tests green" for "budget
  met". Mitigation: `docs/PERFORMANCE.md`'s measurement log has an explicit "not measured — no device"
  row, and the journal must say so in the same words. M17 stops the parser from ever inventing a number.
- **D5 — bundle attribution is hand-rolled (no new library).** `source-map-explorer` is not in the
  lockfile and `source-map` is only transitive (pnpm strict layout would not resolve it from
  `apps/mobile`). ~60 lines of VLQ + span attribution, unit-tested against a fixture map, is smaller
  than the justification a new dependency would need under §2 rule 7. *Risk:* subtle decoder bugs →
  wrong byte table. Mitigation: M15/M16 plus the Σ-equals-total invariant.
- **D6 — `tsx@^4` added as a mobile devDependency**, at the exact spec already resolved for `apps/api`.
  This is the T085 jest/ts-jest precedent (wiring an in-lockfile tool into another workspace), and step
  16 requires proving the lockfile resolution count is unchanged. *Risk:* the checker may read any
  package.json delta as a new dependency — hence the explicit count check and a journal line.
  Rejected alternative: a plain `.mjs` script added to eslint's ignore list — cheaper, but it would put
  untyped, unlinted logic in the repo, against §3.
- **D7 — the heavy-dep audit is expected to find nothing removable.** Every listed dep has live import
  sites (`nitro-modules` is mmkv@4's native peer; `expo-dev-client` is build-time by design). The
  deliverable is therefore the **audit table plus the honest finding**, not a removal. *Risk:* "no
  before/after delta" reads like the work was skipped. Mitigation: the audit table in
  `docs/PERFORMANCE.md` cites import counts and `file:line` evidence per dep, and the journal states the
  negative result explicitly. Manufacturing a removal to produce a delta would be the dishonest outcome.
- **D8 — image cache policy is a real before/after.** Before: `cachePolicy` appears **zero** times in
