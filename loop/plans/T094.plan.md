### Step 3 — The outbox (mechanism decision D1 below)

3.1 `apps/mobile/src/offline/outbox-store.ts` — copy the `active-pet-store.ts` shape verbatim (same
`createSafeStorage` lazy-require + eslint JUSTIFIED comment, same `createJSONStorage(() => mmkvStorage)`).

```ts
export interface OutboxCompletion {
  /** `${reminderId}:${dueAt}` — the SAME merge key the api upserts on (ReminderEvent.reminderId_dueAt)
   *  and the same key `patchEntryStatus` matches on. Dedupes double-taps at enqueue time. */
  id: string;
  reminderId: string;
  dueAt: string;    // ISO, exactly the string the agenda entry carries
  queuedAt: string; // ISO
  attempts: number;
}

export interface OutboxState {
  items: OutboxCompletion[];
  /** No-op when an item with the same `id` is already queued (duplicate completion, offline double-tap). */
  enqueue(vars: { reminderId: string; dueAt: string }): void;
  remove(id: string): void;
  markAttempt(id: string): void;
  clear(): void;
}
```
persist name: `"pawcareright.reminder-outbox"`, `partialize: (s) => ({ items: s.items })`.
`MAX_OUTBOX_ATTEMPTS = 5` exported from this file.

3.2 `apps/mobile/src/offline/flush-outbox.ts`:

```ts
export interface FlushOutboxResult { synced: number; dropped: number; remaining: number; }
export function flushOutbox(): Promise<FlushOutboxResult>;
```
- Module-level in-flight promise: a second concurrent call returns the same promise (a reconnect flap
  must not double-flush).
- Returns `{0,0,items.length}` immediately if `getIsOfflineSnapshot()` is true.
- Iterates a snapshot of `items` **sequentially** (never `Promise.all` — keeps the client's single-flighted
  401 refresh sane and preserves user order), calling
  `apiClient.post<AgendaEntry>(\`/v1/reminders/${item.reminderId}/complete\`, { dueAt: item.dueAt })`.
- Outcome rules (exact, testable):

| Outcome | Rule | Why |
|---|---|---|
| resolves | `remove(id)`; `synced++` | server truth applied |
| `ApiError` 401 | **STOP the loop**, keep every remaining item | the api client already ran the single-flight refresh and, on failure, `onSessionExpired()`; spinning here would hammer a dead session. Items survive to the next flush after re-auth. |
| `ApiError` 400/403/404/409/410/422 (any 4xx except 401/408/429) | `remove(id)`; `dropped++`; continue | **terminal**: the reminder was deleted server-side (404) or the `dueAt` is no longer an occurrence (400). Retrying can never succeed. |
| `ApiError` 408/429 or `httpStatus >= 500` or `httpStatus === 0` | `markAttempt(id)`; if `attempts >= MAX_OUTBOX_ATTEMPTS` ⇒ `remove` + `dropped++`; else **STOP the loop** | transient/poison split; network is bad ⇒ try again next reconnect |
| non-`ApiError` throw | treat as the transient row above | defensive; matches `classifyError`'s house fallback |

- After the loop, **if `synced + dropped > 0`**: `void queryClient.invalidateQueries({ queryKey: agendaKeys.all })`
  so a dropped (stale) completion cannot leave a false "DONE" tick on screen — the agenda re-reads server
  truth. This is the fail-upward half of the design.
- No `console.log`. If any diagnostic is wanted, use nothing at all (mobile has no Logger); silence is fine.

3.3 `apps/mobile/src/offline/use-outbox-flush.ts`:
```ts
export function useOutboxFlush(): void;
```
`const isOffline = useIsOffline();` + a `wasOfflineRef`. Effect on `[isOffline]`: if `!isOffline` and
(first run **or** `wasOfflineRef.current === true`) ⇒ `void flushOutbox()`. Always write the ref.
Covers cold start with pending items *and* reconnect. No timers, no polling.

### Step 5 — Chat `AbortController` (folded item 1) — exact semantics

In `apps/mobile/src/chat/use-chat-stream.ts` only:

5.1 `runStream` gains a parameter `signal: AbortSignal` and passes it through as
`{ onFrame: …, signal }` to `apiClient.streamSse` (the plumbing already forwards it —
`stream.ts:75`, `expo-sse-transport.ts:55`).

5.2 `.catch` guard order — **this order is load-bearing**:
```
1. if (sawDone) return;                      // UNCHANGED (T083 fix-forward, use-chat-stream.ts:153)
2. if (signal.aborted) {                     // NEW
     useChatStore.getState().removeMessage(petId, assistantId);
     return;                                 // NOTE: no setState at all — never "dropped"
   }
3. …existing removeMessage + setState(classifyError(err))…
```
Semantics, stated for the checker:
- **Abort after a terminal `done`** (guard 1, already shipped) ⇒ **total no-op**. The completed answer —
  including a `SAFE_FALLBACK` — is preserved, never deleted, never retry-prompted. This is exactly the
  T088 hazard ("naive abort would delete a server-persisted, quota-charged answer") and guard 1 is what
  makes the new abort safe to add at all.
- **Abort before `done`** (guard 2) ⇒ the *partial* assistant bubble is removed (the store's own contract:
  a partial is "not a truthful record of a completed answer" — `chat-store.ts:32`; and leaving a truncated
  AI health answer on screen is the §5-unsafe option), and the hook enters **no** terminal state, so no
  Retry affordance is ever offered for a stream the *user* ended. `dropped` remains reserved for genuine
  transport failure.
- Abort is therefore distinguishable from a transport drop by the `signal.aborted` flag, not by inspecting
  the error — `normalizeNetworkError` collapses both to `httpStatus: 0`, so error-shape sniffing would be
  wrong.

5.3 Lifecycle: `const controllerRef = useRef<AbortController | null>(null);` — a fresh controller per
attempt in both `send` and `retry`, stored in the ref, its `signal` handed to `runStream`.
`useEffect(() => () => { controllerRef.current?.abort(); }, [petId])` — cleanup fires on unmount **and**
on a `petId` change (navigating to another pet's chat), which is the "navigation" half of the card.
Do not abort in `send`/`retry` themselves (the composer is disabled while streaming; adding a pre-abort
would be speculative).

5.4 The chat store is **non-persisted** (`chat-store.ts:37`), so nothing here writes to device storage and
no cold-start replay is affected.

## Risks & the design decisions the planner made (scrutinize these)

**D1 — Queue mechanism: a small zustand-persisted outbox, NOT TanStack Query mutation persistence.**
The TanStack route (`networkMode` + `onlineManager.setOnline` + `setMutationDefaults` + persisted paused
mutations + `resumePausedMutations`) is real and needs no new dependency — `@tanstack/react-query-persist-client`
is already installed and v5's default `shouldDehydrateMutation` is `state.isPaused`. I rejected it because
wiring `onlineManager` flips the network semantics of **every query and mutation in the app at once**:
queries would *pause* offline instead of erroring, so the ~15 screens whose offline UX is built on
`isOffline && !data` / `isError` branches (and their tests across 163 suites) would change behaviour in one
commit. That is the rewrite this audit card explicitly is not. The outbox touches exactly one mutation, has
no blast radius, and mirrors 6 existing persisted stores. **Cost of my choice:** two mechanisms for
"offline" now coexist (query-cache persistence for reads, outbox for this one write). Recorded in the audit
§5 as the consolidation candidate if a second write ever needs queuing.

**D2 — Banner placement: root layout, in normal flow, above `<Stack>`.** "Global" per the card, and in-flow
so it can never obscure the Emergency interstitial's hotline numbers (§5 / §7 rule 4) — an absolutely
positioned overlay could, which is why M9 pins it. **Risk:** wrapping the navigator in `<View className="flex-1">`
is a real (if standard) layout change to the app root; if it breaks rendering, that is a stop-and-flag, not
a workaround. **Second risk:** the banner now also appears over the Emergency screen. I judged an in-flow,
non-interactive "you're offline" strip to be *honest and helpful* there (hotline calls still work offline
while AI content does not) rather than harmful — but this is a judgement call the checker should test.

**D3 — Per-screen banners are kept, creating deliberate redundancy.** On a screen like Care, the user may
briefly see both the global strip and `agenda-offline-banner`. Removing the ~15 per-screen banners would
touch ~15 files plus their tests plus snapshots — exactly the rewrite the card forbids, and would lose their
*data-staleness* copy ("showing your last saved agenda"), which says something the global strip does not.
Rationale recorded in the audit; consolidation is a follow-up card.

**D4 — Route declarations: documented convention + guard, not 15 new declarations.** Honest reading is that
bare `<Stack.Screen name>` entries configure nothing under file-based routing, so the "~15 undeclared
routes" finding is cosmetic. Adding them risks changing initial-route resolution for zero gain. **Risk:** if
the checker judges the existing 13 bare declarations to be load-bearing in some way I did not find, this
verdict is wrong — the guard test in 6.3 is written so that either verdict keeps the §5 `gestureEnabled`
option pinned.

**D5 — Abort semantics: guard order `sawDone` → `signal.aborted` → classify.** A user-initiated abort is
neither a completion nor a transport failure, so it gets its own outcome: discard the partial, enter no
terminal state. **Risk:** the "never retry-prompts" half is only weakly observable in jest (post-unmount
`setState` is a React no-op), so the load-bearing assertion is "a freshly mounted hook's `retry()` issues
zero `streamSse` calls" plus the store shape — stated in the audit's honesty section rather than implied to
be a direct state assertion. **Second risk:** removing the partial bubble means a user who navigates away
mid-answer and returns finds their question with no answer and no retry. I judged that safer than leaving a
truncated AI health answer rendered as if complete (§7 rule 5, fail upward); the alternative — a "this
answer was interrupted" affordance — is new UI this card has no mandate for.

**D6 — Auth expiry stops the flush rather than dropping items.** A queued completion is a user intention;
losing it silently on a token expiry would be worse than replaying it after re-auth (the endpoint is
idempotent, so a replay is provably harmless). **Risk:** if the user signs in as a *different* account, the
queued item will 404/403 on the next flush and be dropped by the terminal rule — acceptable, and covered by
the 404 test.

**D7 — MAX_OUTBOX_ATTEMPTS = 5 is an arbitrary bound.** Without it a poison item retries forever; the exact
number is a judgement call, not derived from anything. Stated so the checker can challenge it.

**R1 — `docs/qa/state-audit.md` honesty.** The single biggest failure mode of this card is a checklist of
green ticks nobody can verify. The three `state-audit-doc.test.ts` guards (1:1 screen coverage, cell shape,
cited-title existence) exist precisely so a fabricated tick fails CI. If the executor cannot find a real
test for a state, the correct output is `GAP` or `N/A — reason`, **never** an unsupported tick.

**R2 — `pnpm build` ordering.** Mobile consumes `@pawcareright/api-client` from `dist`; the new
`getIsOfflineSnapshot` export will not typecheck in mobile until api-client is rebuilt (T083 R10 hazard).
Build api-client before running the mobile suite.

**R3 — Screen count drift.** This plan says 47 screens from a 51-file glob. If the executor's glob disagrees,
**the code wins** — record the real number in §1 and note the discrepancy, as T093 did for the 11→14
animation-site count.

## Safety statement (PRODUCT_SPEC §5 / CLAUDE §7)

This card weakens no safety surface. `<VetDisclaimer/>`, the Emergency interstitial, the red-flag rules, the
hotline resolution and the safe-fallback copy are all **zero-diff** and their pinned suites must stay green.
The global banner is non-interactive, non-dismissible chrome laid out **in normal flow** specifically so it
can never obscure emergency content (pinned by M9 + the "no absolute positioning" test). No new user-facing
string may contain "diagnosis"/"diagnose", a drug name, a dose, or any claim about a pet's condition. The
offline queue records only a completion the **user** tapped — it never marks a medication given on its own
and never suggests one — and it **fails upward**: a completion the server rejects (deleted reminder, stale
occurrence) is dropped and the agenda is invalidated so a false "done" tick cannot persist on screen. The
chat abort change strictly *adds* protection: the `sawDone` guard stays first, so an already-decided
`SAFE_FALLBACK` answer can never be erased or converted into a Retry prompt by an abort. If any step turns
out to require touching an emergency, disclaimer, or dosing surface, the executor must stop and write
`loop/plans/T094.blocked.md` tagged SAFETY-ESCALATION rather than proceed.
