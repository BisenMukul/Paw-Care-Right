## 1. Investigation findings (facts the plan is built on — verified by reading, not assumed)

1. **Actual CI job set** (`.github/workflows/ci.yml`): `build`, `mobile-fingerprint`, `ai-evals`, `web-perf-budget`, `web-e2e`, `security`. Triggers: `push: branches:[main]` + `pull_request`. `concurrency: group: ci-${{ github.ref }}`, `cancel-in-progress: true`.
2. **`mobile-fingerprint` is PR-only** (`if: github.event_name == 'pull_request'`, ci.yml:103). On a push to main it is **skipped**, and in GitHub Actions a job whose `needs:` target was skipped is itself skipped. Therefore it **must not** appear in the publish jobs' `needs:` — otherwise the preview publish would silently never run. This is a load-bearing exclusion and gets its own pinned test + comment.
3. **`/health` has no build id.** `apps/api/src/health/health.service.ts` returns `{status:"ok",db:"ok",redis:"ok"}`. OTA_UPDATES §5.3 requires the promote job to check that `GET /health` *includes the required API build id*. `AppConfigService.gitSha` already exists (`env.schema.ts:51`, `GIT_SHA` default `"dev"`) and `ConfigModule` is `@Global()`, so exposing it needs no module wiring.
4. **The health URL is `/v1/health`**, not `/health` (`app.setup.ts:59` `setGlobalPrefix("v1")`; `app.e2e-spec.ts:32` confirms). The pre-flight curl must use `/v1/health`.
5. **No YAML parser is resolvable offline.** `yaml@2.9.0` / `js-yaml@{3.15,4.3}` exist only inside `node_modules/.pnpm/**`; there is no `node_modules/yaml` at the root or in any workspace, so `require("yaml")` from a jest spec fails. Adding one would be a new dependency (CLAUDE §2 rule 7) purchased for a single assertion. AC1 is therefore proved by a **hand-rolled structural validator with a non-vacuity self-test** (see §5 AC1) plus honest disclosure that GitHub's own parser is the closing evidence.
6. **Pinned-spec idiom to copy**: `apps/mobile/__tests__/ota-config.test.ts` (locally-typed `require` for `node:fs`/`node:path`/`node:child_process`, `export {}`, `declare const __dirname`, `extractStepRunBody`, `spawnSync` of the *exact* CI invocation). Job-block slicing idiom: `sliceJobBlock` in `apps/api/test/security-ci-gate.spec.ts:104`.
7. **Root-script precedent**: `scripts/scan-secrets.js` — zero-dep CJS, `"use strict"`, exports helpers for tests, CLI when invoked directly, invoked in CI as `node scripts/scan-secrets.js --tracked` (no `package.json` script entry). New scripts follow this exactly.

## 2. Design decisions (each one is a Risk the CHECKER should scrutinise)

**D1 — Both publish jobs live in `.github/workflows/ci.yml`, not a new workflow file.**
`needs:` cannot cross workflows, and the card requires the preview publish to be *gated on all checks*. A separate workflow would have to duplicate every gate (drift hazard, doubled infra) or gate on nothing. `workflow_dispatch` (with inputs) is added to the existing `on:` block; the gates run in the dispatched run itself, which is exactly how OTA_UPDATES §8.1 ("every OTA publish passes the full CI gate suite") is satisfied for production.

**D2 — Concurrency is hardened so a push can never cancel an in-flight manual publish.**
Today `group: ci-${{ github.ref }}` + `cancel-in-progress: true` means a push to main starts a run that cancels an in-progress `workflow_dispatch` run on the same ref — i.e. it could kill a production publish between `eas update` and `eas channel:rollout`, leaving an unconstrained update. Change to `group: ci-${{ github.event_name }}-${{ github.ref }}` **and** `cancel-in-progress: ${{ github.event_name != 'workflow_dispatch' }}`. Both halves are required (the group split stops a push from targeting the dispatch run; the expression stops a second dispatch from cancelling the first).

**D3 — `[critical]` resolution: DESCOPE the manifest-marker publish path. `/config.criticalOtaVersion` is the single authoritative runtime signal; `[critical]` is a message-text convention only.** (Orchestrator directive / T114 review Finding 4.)
Evidence and reasoning, honest about what is verifiable offline:
- *Verifiable here:* `hasCriticalMarker` probes `extra.updateMessage`, `extra.expoClient.extra.updateMessage`, `metadata.updateMessage`. Nothing in this repo writes any of those. `eas update --message` stores the message in the EAS API (surfaced by `eas update:list` / the dashboard); it is not a field of the served update manifest. So the probe is inert unless the message is routed into the **evaluated Expo config**.
- *The only available routing is dangerous:* the sole way to make the probe live is `app.config.js` → `extra.updateMessage = process.env.EXPO_UPDATE_MESSAGE`, which lands at `extra.expoClient.extra.updateMessage`. That makes a **per-publish-varying value part of the evaluated app config**, which is an input to `@expo/fingerprint`'s config source. If `extra` participates in the hash — the safe default assumption, and **not verifiable offline** without a real fingerprint experiment — then `runtimeVersion` changes on every publish and **no binary can ever receive an OTA update**: a total, silent OTA outage. Catastrophic downside, redundant upside.
- *The upside is genuinely redundant:* `/config.criticalOtaVersion` is already implemented end-to-end (T114: types → api env → mobile), is server-instant (no publish, no adoption delay), and OTA_UPDATES §3 itself names it the belt-and-braces signal.
- *Consequences the executor must implement:*
  (a) `hasCriticalMarker` **stays** in the client, unchanged in behaviour — it is fail-safe (it can only ever *raise* urgency) and free. Its doc-comment is updated to record this ruling (comment-only edit, no behaviour change, no test change).
  (b) The linter enforces `[critical]` as an exact lowercase suffix so human/dashboard scanning and `eas update:list` are unambiguous (the client's probe is case-insensitive, i.e. a superset — no conflict).
  (c) Whenever a published message carries `[critical]`, the job summary **must** print the mandatory follow-up: set `CRITICAL_OTA_VERSION` to the new update id and redeploy/restart the API, because that — not the message — is what actually prompts users.
  (d) A pin test asserts no workflow step writes an `updateMessage`/`EXPO_UPDATE_MESSAGE` into the app config, so the descoped path cannot be silently reintroduced without a fingerprint experiment.
- *Non-goal (explicitly not in this card):* running the `extra`-vs-fingerprint experiment. Recorded in §8 Risks for T117/T118.

**D4 — `/health` gains `buildId` (additive).** Without it the card's cited §5.3 pre-flight is unimplementable. `HealthService` injects `AppConfigService` and returns `buildId: this.appConfig.gitSha` (default `"dev"`). Additive-only, matching §5.1. `/health` has no Zod contract in `packages/types` today (it is a plain `HealthStatus` interface, pre-existing); this plan does **not** introduce one — that would be a bigger, unrequested refactor. Flagged for the checker.

**D5 — Preview publish is EXPO_TOKEN-gated (skip + summary note); production publish HARD-FAILS without the token.**
Preview follows the T089 Sentry precedent exactly (`if: env.EXPO_TOKEN != ''` / `== ''` pair) so tokenless environments (this sandbox, forks) stay green; the *gating structure* — the `needs:` list — is the pinned invariant, not the publish call. Production is human-triggered, so a silent skip would be a false success: it exits non-zero with an explicit message.

**D6 — The message lint step is UNCONDITIONAL in the preview job** (it needs no token), so the convention has teeth on every push to main even here. Consequence: a main-branch commit subject with no `Txxx`/`Mx` reference fails the job. That is intended (§8.4: "so every shipped bundle maps to journal history") and consistent with CLAUDE §4 "one task, one commit"; merge-commit subjects are called out in Risks.

**D7 — Two small zero-dep scripts, not one multi-purpose one:** `scripts/lint-update-message.js` and `scripts/check-api-build.js`. Both are directly unit-testable via `spawnSync` with the *exact* CI invocation (T113 lesson), which inline `node -e` in YAML is not.

**D8 — Rollout command follows OTA_UPDATES §6 / the card literally** (`eas update --branch production` then `eas channel:rollout … 10%`). The exact `channel:rollout` flag set cannot be verified offline (no `EXPO_TOKEN`, `eas-cli` not vendored). Pinned tests assert only the presence of `channel:rollout`, `--percent 10` and `--non-interactive`; the first real run is a founder to-do. Risk R3.

## 4. Ordered steps

### Phase A — the two scripts (build them first; the workflow calls them)

**Step 1 — `scripts/lint-update-message.js`.**
Zero-dep CJS, `"use strict"`, shebang `#!/usr/bin/env node`, header comment citing T116 + OTA_UPDATES §8.4 + CLAUDE §1a naming.
- Convention (from OTA_UPDATES §8.4 `Txxx/Mx: summary [critical?]`), implemented as one exported const:
  `const UPDATE_MESSAGE_PATTERN = /^(T\d{3}|M\d{1,2}): \S.*?( \[critical\])?$/;`
  plus these explicit rules, each with its own rejection reason string: no leading/trailing whitespace; single line (no `\n`/`\r`); length ≤ 120; `[critical]` allowed **only** as the exact lowercase suffix (reject `[CRITICAL]`, `[Critical]`, or `[critical]` anywhere but the end); summary must be ≥ 3 non-space characters after the colon.
- Exports (for readability/testability): `UPDATE_MESSAGE_PATTERN`, `validateUpdateMessage(message) -> {ok:boolean, reason?:string}`, `deriveUpdateMessage(commitSubject) -> {ok:boolean, message?:string, reason?:string}`.
- `deriveUpdateMessage`: take only the text before the first newline; find the first `\b(T\d{3}|M\d{1,2})\b`; strip a leading conventional-commit prefix `^\w+(\([^)]*\))?!?:\s*`; remove that id token and any immediately following `:`/`-`/whitespace from the start of the remainder; collapse internal whitespace runs to one space; trim; preserve a trailing ` [critical]` if the subject ended with it (case-insensitively normalised to lowercase). Fail (`ok:false`) when no id token is found or the summary is empty. **Guarantee: the returned message contains no newline** (needed for `$GITHUB_OUTPUT`).
- CLI:
  - `node scripts/lint-update-message.js --message "<msg>"` → exit 0, or exit 1 printing `lint-update-message: <reason>` on **stderr** and the expected form.
  - `node scripts/lint-update-message.js --from-commit "<subject>"` → print the derived message on **stdout with no trailing prose** (so `MESSAGE="$(…)"` is safe), exit 0; on failure exit 1 with the reason on stderr.
  - Any other/absent argument → exit 1 with a usage line on stderr (mirrors `fingerprint-diff.sh`'s "unknown argument" behaviour).
- No `|| true`-style masking anywhere. Match `scan-secrets.js`'s exact printing style (it is a CLI script, not app code).

**Step 2 — `scripts/check-api-build.js`.**
Zero-dep CJS, same house style. Header cites OTA_UPDATES §5.3 ("deploy backend first; the promote job checks `GET /health` includes the required API build id").
- Exports `checkApiBuild({body, expected}) -> {ok:boolean, reason?:string}`.
- Rules, all fail-closed: body must be non-empty and `JSON.parse`-able (a parse error is a rejection, never an exception escaping); `status` must be exactly `"ok"`; `buildId` must be a non-empty string; `expected` must be a non-empty string; `buildId === expected` (exact, no trimming, no prefix matching — a short-sha input must not "nearly" match).
- CLI `node scripts/check-api-build.js --body "<json>" --expect "<sha>"` → exit 0 or exit 1 with `check-api-build: <reason>` on stderr. Unknown args → exit 1 usage.

## 8. Risk register (top 5)

**R1 — AC1's "yaml valid" is proved by a hand-rolled structural validator, not a real parser.** No `yaml`/`js-yaml` is resolvable from any workspace (verified: present only under `node_modules/.pnpm/**`), and adding one for a single assertion violates CLAUDE §2 rule 7. Mitigation: the validator checks the failure modes that actually bite (tabs, duplicate job keys, missing `runs-on`/`steps`, dangling `needs:`), carries a non-vacuity self-test on runtime-built broken fixtures, and the honest residual — "GitHub's own parser is the closing evidence on first push" — goes in the runbook and the ledger. *Checker: this is the weakest AC proof in the plan; scrutinise the self-test.*

**R2 — D3 rests on one offline-unverifiable claim** (that EAS-served manifests never carry the publish message) and one deliberately conservative assumption (that a per-publish-varying `extra` would move the fingerprint). If the first is wrong we merely keep a redundant signal unused; if the second is wrong we forgo a marginal feature. Both errors are safe-direction — the whole path degrades to silent-apply-next-launch, exactly as T114's review found. The unsafe direction (a per-publish fingerprint change silently disabling all OTA delivery) is the one D3 refuses to risk. The experiment is recorded for T117/T118, not attempted here.

**R3 — The `eas update` / `eas channel:rollout` invocations cannot be executed here** (no `EXPO_TOKEN`; `eas-cli` not vendored; runbook §8 already records the T099 auth-boundary evidence). Wrong flags would surface only on the founder's first real publish. Mitigation: follow OTA_UPDATES §6 and the card literally, `--non-interactive` everywhere, tests pin presence not semantics, and a founder to-do confirms the flag set. Note the race the doc itself prescribes: publishing to `--branch production` before the rollout constraint exists leaves a brief 100% window — flagged for the founder and for T117.

**R4 — Adding `buildId` to `/health` touches the API and a shared e2e assertion.** Additive-only (§5.1), no new env key, no module wiring (`ConfigModule` is `@Global`). The specific trap: hardcoding `buildId: "dev"` in `app.e2e-spec.ts` passes locally and fails in CI (`GIT_SHA: ${{ github.sha }}`) — step 6 mandates `expect.any(String)`. Secondary: `/health` still has no Zod contract in `packages/types`; introducing one is out of scope and deliberately not done.

**R5 — Workflow-level blast radius.** `ci.yml` is pinned by four existing specs (`sentry-ci-gate`, `security-ci-gate`, `coverage-gate`, `lighthouse-budget`/`e2e-gate`) using substring assertions; appending jobs should not disturb them, but the api **and** web suites must be re-run, not just mobile. The D2 concurrency change and the new `workflow_dispatch` trigger alter behaviour for every existing job (they now also run on a manual dispatch) — intended (§8.1), commented, but a real change to shared infrastructure. Footgun from D6: a main-branch commit subject with no `Txxx`/`Mx` reference (e.g. `Merge pull request …`) fails the preview job; acceptable under CLAUDE §4, and merge-subject handling is left to T117 if merge commits are ever adopted.
